# SECURITY.md — 위협 모델 & 보안 점검 기록

이 문서는 "레포가 public + 오픈소스로 유지된다"는 전제 위에서, 실제로 성립하는 공격
경로가 무엇이고 무엇이 아닌지를 정리한다. **패치 완료 기록이 아니라 위협 모델 문서** —
점검 시점(2026-09-12)의 결론과 미해결 항목을 남겨서, 다음에 이 주제를 다시 열 때
같은 조사를 반복하지 않기 위함이다.

## 1. 신뢰 경계 (Trust Boundary)

레포가 public이어도 실제 배포에 영향을 줄 수 있는 값들은 레포 밖에 있다.

| 시크릿 | 위치 | 레포에 있는가 |
|---|---|---|
| `YOUTUBE_API_KEY`, `GITHUB_TOKEN`, `TELEGRAM_BOT_TOKEN`, `INGEST_SECRET`, `GROQ_API_KEY` 등 | GCP Secret Manager + 로컬 `deploy/env.sh` | **아니오** — `deploy/env.sh`는 `.gitignore` 처리, `git log --all -p -- deploy/env.sh` 로 히스토리 전체 확인해도 커밋된 적 없음. 레포엔 빈 값뿐인 `deploy/env.example.sh`만 있음 |
| `/tick`, `/wake` 호출 인증 | Cloud Scheduler/Tasks OIDC 서명 (`src/backend/oidc.py`) | 코드 로직만 공개, 서명 자체는 위조 불가 |
| `/ingest` 호출 인증 | `X-Ingest-Secret` 헤더 (`src/backend/telegram_app.py`) | 값은 Secret Manager 전용 |
| `data` 브랜치 쓰기 | GitHub Contents API + fine-grained PAT (`src/backend/gh_store.py`) | PAT은 레포에 없음 |

**결론**: 코드를 clone하는 것 자체로는 위 표의 어떤 값도 얻을 수 없다. "레포를 clone해서
배포/데이터 브랜치/제어채널을 조작할 수 있다"는 최초 가설은 **성립하지 않는다** — 코드
공개와 자격증명 노출은 별개 층위.

## 2. 검토했던 시나리오와 결론

### 2.1 "clone만으로 임의 조작 가능한가" → 아니오
위 1절 표 참고. 직접적인 쓰기 경로 4개(deploy, `/tick`/`/wake`, `/ingest`, `data` 브랜치
커밋) 전부 레포 밖 시크릿이 있어야 통과한다.

### 2.2 "구글 계정이 다른 기기에서 로그인되면 IAM 권한을 그대로 쓸 수 있는가" → 맞음, 그러나 별개 문제
구글 계정 자격증명 자체가 탈취/공유되면 그 세션은 본인 인증과 동일하게 취급되어
GCP IAM 권한을 그대로 행사할 수 있다. **이건 레포가 오픈소스인 것과 무관한, 계정
보안 위생 문제**다 (다른 모든 GCP 프로젝트·Gmail·Drive에도 동일하게 해당).
- 현재 상태: GitHub 로그인 2FA 적용됨, 저장소에 운영자 본인 외 협업자 없음 →
  "타인이 내 계정으로 로그인해서 push한다"는 경로는 사실상 닫혀 있음.
- 계정 탈취 자체를 막는 근본 대책(하드웨어 보안키, Google Advanced Protection
  Program)은 이 프로젝트 코드가 아니라 계정 설정 영역 — 여기 기록만 하고 실행은
  운영자 판단.

### 2.3 프론트엔드 XSS 감사 — 렌더러 3개 전수 확인
`docs/SPEC.md` §3의 "innerHTML 금지, textContent/createElement만" 원칙이 실제로
지켜지는지 `src/frontend/js/{notices,tweets,render}.js` 를 직접 grep + 코드 리딩으로 감사.

- **innerHTML 사용처는 전부 정적 문자열**(SVG 아이콘, 빈 문자열, 고정 템플릿)뿐이고,
  외부 유래 텍스트(YouTube 영상 제목 `item.title` — `render.js:250`, 트윗 본문
  `m.text`/`m.text_ko` — `tweets.js:181`, 소식 제목 `titleText` — `notices.js:72`)는
  예외 없이 `textContent` 또는 `_esc()`/`_attr()`(`notices.js:79-82`)를 거친다.
- **URL 필드는 스킴 주입이 구조적으로 불가능**: URL을 만드는 유일한 지점인
  `xnotice.py:63` `_URL_RE = re.compile(r"https?://[^\s　]+")` 가 애초에 `https?://`로
  시작하는 문자열만 매치하므로 `javascript:` 같은 실행형 스킴이 `url` 필드에 들어올
  수 없다. 채널 링크 등 나머지 href는 `config/channels.json` 정적 값에서만 파생.

**결론**: 현재 코드에서 발견된 코드 실행형(XSS) 취약점은 없음. (2026-09-12 기준 스냅샷 —
새 렌더링 코드 추가 시 같은 기준으로 재점검 필요.)

### 2.4 남은 잔여 위험 (코드 실행형이 아닌, 시각적 기만형)
2.3에서 막힌 건 "스크립트 실행"이지, "유효하지만 사람을 속이는 URL"은 못 막는다.
이스케이프/정규식 어느 것도 이 두 가지는 방어하지 못함:
- **유니코드 방향 재정의 문자(RTLO, U+202E) 트릭**: 트윗 본문에 섞이면 URL 표시
  순서가 뒤집혀 실제 도메인을 위장할 수 있음.
- **Look-alike 도메인**: `https://x.com.evil-phish.example/...` 처럼 정규식·이스케이프를
  전부 통과하는 형태로 신뢰 도메인을 흉내낼 수 있음.

이 두 항목은 **2.5의 완화책 하나로 함께 닫힌다** — 소식 링크를 원본 URL이 아니라
트윗 URL로 고정하면, 본문에 어떤 위장 URL이 있어도 사이트가 사용자를 거기로 직접
보내지 않는다.

### 2.5 실제 공격이 성립하는 유일한 현실적 경로: 업스트림(멤버 X 계정) 탈취
소식/스케줄 콘텐츠의 원천은 5인 멤버·그룹 공식 계정의 실제 트윗이다. 이 계정이
탈취되면 그 내용이 Automate 릴레이 → `/ingest` → `notices.json`/`preview.json` 정상
파이프라인을 그대로 타고 사이트에 반영된다. **코드 버그가 아니라 각 계정 소유자의
계정 보안 문제이며, 이 저장소가 오픈소스인지와 무관하게 존재하는 리스크**. 2.3의
이스케이프/스킴 제한 덕에 스크립트 실행까지는 안 가지만, 콘텐츠 왜곡(가짜 일정·
피싱 링크 유포)은 막지 못한다.

**계획된 완화(미패치, 이 문서 작성 시점 기준 TODO)**: `notices.js:58`의
`const href = n.url || n.tweet_url || "#"` 를 `n.tweet_url` 우선(또는 고정)으로 바꿔서,
소식 클릭 시 항상 원본 트윗 페이지로만 연결하고 트윗 본문 속 임의 URL로 직행하지
않게 한다. 사용자가 명시적으로 "당장 패치하지 않음"을 선택 — 다음에 이 문서를
다시 열 때 이 항목부터 볼 것.

### 2.6 "clone → 프로덕션 프론트 하이재킹"의 유일한 실제 경로: PR 병합
직접 write 권한 탈취가 막혀 있는 상태에서, 외부인이 실제로 프로덕션 프론트 코드에
영향을 주려면 **악성 PR을 만들어 운영자가 리뷰 없이 merge하게 만드는 것** 외에는
경로가 없다(예: 리팩터링으로 위장해 `innerHTML` 재도입, 이스케이프 로직 제거,
외부 CDN `<script>` 삽입). 방어 수단은 추가 인증 계층이 아니라 **PR 리뷰 습관 +
GitHub 브랜치 보호 규칙**(강제 리뷰, 직접 push 금지). 브랜치 보호 규칙 활성화 여부는
2026-09-12 기준 미확인 — 확인 필요 시 GitHub 저장소 Settings → Branches 참고.

## 3. 별도로 논의된 아이디어 — "수동 배포/쓰기 시 2차 확인" (미구현)

계정(구글 로그인) 세션 하나가 뚫리는 단일 실패점을 줄이기 위해, **로컬 배포 스크립트
실행**과 **텔레그램 수동 관리 명령**(`/del`, `/ingest`, `/notice-edit`, `/undo`, `/pause`,
`/resume` 등 사람이 의도적으로 트리거하는 것)에 한해 2차 확인(step-up 인증)을 추가하는
아이디어가 논의됐다. **`/tick`/`/wake` 같은 스케줄 기반 자동 쓰기에는 적용하지 않는다**
— 무인 운영이 전제이므로 사람 개입을 요구하면 안 됨.

핵심 설계 함정 — **검증 비밀이 보호 대상과 같은 신뢰 경계 안에 있으면 안 된다.**
텔레그램 채팅방 안에서 OTP를 발급하고 같은 방에서 입력받는 방식은, `TELEGRAM_BOT_TOKEN`과
`TELEGRAM_CHAT_ID`가 결국 같은 GCP Secret Manager/Cloud Run 환경변수에 있기 때문에
"GCP 계정이 이미 탈취된" 공격자에게는 순환 참조가 되어 실질적 방어가 안 된다(공격자가
그 값들을 읽어 같은 채널을 재현할 수 있음). 진짜 2단계가 되려면 검증 비밀이 GCP 프로젝트
탈취로는 닿지 않는 곳(예: 완전히 별도 계정의 외부 서비스, 또는 어디에도 저장되지 않고
사람 머릿속에만 있는 패스프레이즈)에 있어야 한다.

**상태: 설계 방향만 합의, 미구현.** 다음에 이 작업을 재개할 때:
1. 검증 비밀을 어디에 둘지(GCP 외부 vs 로컬 전용 패스프레이즈) 먼저 결정
2. 적용 범위는 로컬 배포 스크립트 + 텔레그램 수동 admin 명령으로 한정
3. 자동 스케줄 경로(`/tick`, `/wake`, `/ingest`의 정상 자동 흐름)는 대상에서 제외

## 4. 요약 — 지금 당장 조치가 필요한 것 / 필요 없는 것

- **조치 불필요 (이미 안전)**: clone을 통한 직접 배포/데이터 조작, 현재 렌더러의
  코드 실행형 XSS.
- **낮은 우선순위, 계획만 세움**: 소식 링크를 트윗 URL로 고정(§2.5), 수동
  배포/쓰기 2차 확인(§3).
- **코드 밖의 일, 이 문서는 기록만**: 구글 계정 자체 탈취 방지(하드웨어 보안키 등),
  멤버 X 계정 보안.
- **확인 완료 (2026-09-13, 아래 §6 참고)**: GitHub 브랜치 보호 규칙 — `main`/`data`
  둘 다 미설정 확인. `main`은 걸어둘 가치 있음(§2.6/§6), `data`는 자동화 구조상
  걸어도 실효 없어 보류. Vercel fork PR 프리뷰 빌드 설정은 여전히 미확인
  (`vercel` CLI 로컬 미설치).
- **사용자 결정 (2026-09-13)**: 지금 단계에서 브랜치 보호·2차 인증 등 추가 조치는
  보류. "보안을 너무 무겁게 걸고 싶지 않다"는 것이 명시적 선택 — 다음에 이 문서를
  열 때 이 결정을 다시 뒤집을 근거(예: 사고 정황)가 없다면 그대로 유지.

## 5. 계정별 탈취 리스크 요약 (2026-09-13)

이 프로젝트의 제어권에 관여하는 계정 5개와, 각각이 뚫렸을 때의 실제 블라스트 반경.
"탈취 시 가능한 것"은 그 계정만 단독으로 뚫렸을 때 기준 — 다른 계정과 결합 시
반경이 늘어나는 경우는 "캐스케이드" 열에 별도 기재.

| 계정 | 탈취 시 가능한 것 | 못 하는 것(한계) | 캐스케이드 위험 |
|---|---|---|---|
| **구글 (GCP)** | 백엔드(Cloud Run) 재배포·조작, Secret Manager 전체 열람(`GITHUB_TOKEN`/`INGEST_SECRET`/`TELEGRAM_BOT_TOKEN`/`GROQ_API_KEY` 등), `data` 브랜치 콘텐츠 조작, 텔레그램 봇으로 위장한 알림 발송, Groq 쿼터 남용 | 프론트(Vercel 프로덕션 코드) 직접 수정 — 백엔드는 유저 브라우저와 직접 상호작용 안 함 | **`GITHUB_TOKEN`이 레포 전체에 Contents:Write 스코프면 그 토큰으로 `main`에도 push 가능 → 깃헙 계정 탈취와 동급으로 번짐.** PAT 스코프 미확인(§1) — 확인 시 `main` 브랜치 보호가 이 캐스케이드를 직접 차단 |
| **깃헙** | `main` 직접 push/PR 병합 → 프론트 코드 완전 장악(이스케이프 로직 제거, XSS 재도입, 임의 스크립트 삽입) | GCP 인프라 접근 불가 (레포에 시크릿 없음, git 히스토리 확인됨) | 없음 — 닫힌 경로 |
| **베셀** | GitHub 연동 소스를 임의로 교체해 프로덕션 도메인에 임의 코드 배포, 프로젝트 폐쇄, 커스텀 도메인 설정 변경 | GCP/GitHub 자격증명 자체엔 접근 불가 | 깃헙과 **동급의 "최종 방아쇠"** — 깃헙이 멀쩡해도 베셀 하나만으로 프론트 완전 장악 가능 |
| **텔레그램** | `data` 브랜치 콘텐츠 조작(`/del` `/notice-edit` `/undo` 수동 `/ingest`), 파이프라인 일시정지(`/pause`)로 자해적 DoS | 코드/배포 계층 접근 불가 — 임의 명령 실행 코드 자체가 없음(`os.system`/`subprocess`/`eval` grep 확인 0건), GCP/GitHub 시크릿 노출 경로 없음 | 없음 — `telegram_app.py:2453-2469`의 webhook secret + `chat_id` 이중 검증으로 다른 계정에 안 번짐 |
| **Groq** | API 키 재발급/삭제로 우리 쪽 키 무력화 → 번역·소식 제목추출 기능 강제 중단 | 코드 실행·데이터 조작 불가 — `llm.py`의 모든 실패 경로가 `None` 반환으로 graceful degradation(코드 확인, 크래시 없음) | 없음 — 기능 저하로 국한, 서비스 전체엔 영향 없음 |

**서열 요약**: 구글·깃헙·베셀 3개는 "코드/배포 계층"까지 닿는 동급 리스크(그리고 구글은
조건부로 깃헙까지 캐스케이드 가능), 텔레그램은 "데이터 계층"으로 국한, Groq는
"기능 저하"로 가장 낮은 반경.

## 6. 계정 보호 우선순위 결론 (2026-09-13)

**구글·깃헙·베셀 3개는 동등한 최상위 등급으로 취급한다.** 텔레그램·Groq는 그 아래
간접 등급.

순위를 매기는 축이 두 가지 있고 서로 다른 답이 나오지만, 결론(최상위 3개 묶음)은
같다:

- **캐스케이드/도달 범위 축**: 구글이 제일 넓다 — 백엔드 장악 + 전체 시크릿 열람 +
  (§5 표의 `GITHUB_TOKEN` 스코프 확인 여부에 따라) 깃헙까지 번질 수 있음 + 텔레그램
  위장 발송까지 가능. 이 축만 보면 `구글 > 깃헙=베셀`.
- **유저(팬) 직접 피해 축**: 깃헙·베셀은 뚫리는 즉시 **유저 브라우저에서 실행되는
  코드**를 장악(§2.6 — PR 병합이든 배포 소스 교체든 결과는 동일)하므로 가장 직접적인
  피해 경로. 구글은 §5에서 확인했듯 백엔드가 유저 브라우저와 직접 상호작용하지
  않아 프론트 장악까지 가려면 캐스케이드 조건이 하나 더 필요 — 이 축만 보면
  `깃헙=베셀 > 구글`.

**어느 축으로 봐도 텔레그램·Groq보다는 압도적으로 위 등급**이라는 점은 동일하다.
그래서 정밀한 서열보다 **"구글·깃헙·베셀 = 동일 최상위 등급, 텔레그램·Groq = 그
아래 간접 등급"** 이라는 2단 구획이 실무적으로 더 유효한 결론이다.

**의미**: 이 3개 계정(구글/깃헙/베셀)엔 동일한 강도의 보호(2FA, 가능하면 하드웨어
보안키, 로그인 알림)를 걸어야 하고, 어느 하나만 상대적으로 느슨하게 둬도 전체
방어선이 그 계정 수준으로 낮아진다. 반대로 텔레그램·Groq는 뚫려도 §5에서 확인한
대로 반경이 데이터 계층/기능 저하로 국한되므로, 상대적으로 낮은 우선순위로 둬도
무방하다.
