## 관련 용어 (위 항목에 딸린 것)

- **`POST /ingest`** — 업스트림 시스템이 중계한 푸시알림 텍스트를 백엔드가 받는 공개 엔드포인트. transport 추상화 경계 — 입력 소스가 바뀌어도 이 이후 스키마는 불변.
- **`data` 브랜치** — 백엔드가 상태를 커밋하는 GitHub 브랜치. 코드 없음, JSON 만.
- **`monitoring` 브랜치** (v3.9) — 데이터 저장소의 **로그 전용** 브랜치. 이벤트 로그
  (`monitoring/events-*.jsonl`)·모니터 스냅샷(`latest.html`)·유실 원문 큐(`lost_queue.json`)가
  여기 쌓인다. `data` 에서 분기해 만들어 과거 로그를 히스토리째 승계했다. **분리한 이유**는
  GitHub Contents API 의 PUT 이 파일이 아니라 **브랜치 HEAD 단위로 충돌**하기 때문 — 이 로그들은
  `/write` 직렬화 창구를 거치지 않고 제어 채널이 직접 커밋하는데, 제어 채널은 인스턴스가 최대
  20개라 버스트 때 `data` 브랜치 쓰기를 409 로 밀어냈다(2026-09-24 트윗 유실 사고).
  env `MONITOR_BRANCH` 로 지정(기본 `monitoring`). "로그 브랜치"라고 불러도 되지만 문서·코드
  표기는 `monitoring` 브랜치로 통일.
- **`devpapers` 브랜치** — 개발 중 상시 참조하지 않는 문서(배경자료·구버전 기록·운영자용
  설명자료 등)를 모아두는 GitHub 브랜치. `docs/`에서 개발 시 계속 쓰는 4개
  (`SPEC.md`·`TERMINOLOGY.md`·`VERSION.md`·`INGEST_FLOW.md`)만 `main`에 남기고 나머지가
  여기 있다. `PUSH_MONITOR.html`처럼 자동으로 시간마다 갱신·커밋되는 문서도 여기 둔다 —
  `data` 브랜치와 같은 이유로 Vercel 배포 트리거에서 제외돼 있다(`vercel.json`). **"docs
  브랜치"라고 부르지 말 것** — `docs/` 폴더명과 헷갈린다.
- **메인 콘텐츠** — preview(방송예고) · tweet(개인 트윗) · notice(공식 소식) 3종.
- **소식 제목 · 본문 필드** — 소식 항목의 일본어 제목 = `title`, 한글 제목 = `title_ko`(LLM 이 따로 뽑은 제목),
  트윗 원문 = `body_raw`, **본문 한글 번역 = `body_ko`**(v4.0.5, 2026-10-04 운영자 결정 — `<원문 필드>_ko` 모양.
  `body_raw_ko` · `text_ko` 로 부르지 않는다. 개인 트윗의 본문 번역은 `text_ko` 로 따로 있다).
- **모니터링 스냅샷** — (v3.8.9) 매일 KST 06:10 백엔드 `/monitor` 가 방금 끝난 하루(06:00~익일
  06:00 KST)의 모니터 리포트 데이터를 계산해 굳혀 둔 것. `monitoring/days/YYYY-MM-DD.json`
  (하루치 상세) + `monitoring/summary.json`(전 기간 잔디용 요약), `monitor_snapshot.py`.
  웹 monitor 는 오늘치만 실시간으로 계산하고 지난 날짜는 이것을 읽는다. 외부 조회값
  (healthchecks.io·Vercel)은 찍은 시각(`snapshotAt`) 기준. **"스냅샷"만 단독으로 쓰지 말 것** —
  undo 스냅샷(`/undo` 되돌리기용), reconcile 의 "이전 스냅샷 대비 diff" 와 헷갈린다.

## v4a 용어 (브랜치 `v4a` — 2026-09-29 구현, 미배포)

`ref/v4a/v4a_design.md` §3 에서 2026-09-28 확정한 용어를 v4a 구현과 함께 옮긴다. 현행 운영(v3.8.10)을 가리킬 때는 위 표의
이름(백엔드 · 제어 채널 · `/tick` 등)을 그대로 쓰고, v4a 구성 요소를 가리킬 때만 아래 이름을 쓴다.

| 정식 명칭 | 가리키는 것 | 현행 대응 · 쓰지 말 것 |
|---|---|---|
| **접수 서비스** (`mewtype-intake`) | 바깥에서 오는 모든 것을 받는 공개 서비스 — `/ingest` · 관리 페이지 · 텔레그램 비상 명령 · 외부 호출로 가공. data 브랜치에 쓰지 않는다 | 현행 제어 채널 `mewtype-telegram` |
| **쓰기 서비스** (`mewtype-writer`) | data 브랜치를 쓰는 **유일한** 주체. reconcile · 작업 적용 · 다음 확인 예약 · 알림 DM | 현행 백엔드 `mewtype-backend` |
| **적용 큐** (`mewtype-apply`) | 쓰기 서비스로 작업을 하나씩 전달하는 큐. 모든 쓰기 요청 · reconcile 요청이 여기로 | 현행 wake · tick 예약 큐 · `/write` |
| **가공 큐** (`mewtype-enrich`) | 번역 재시도를 쓰기 경로 밖(접수 쪽)에서 하게 전달하는 큐 | 현행 tick 안 `_translate_sweep` |
| **reconcile(범위)** | "지금 상태가 어때야 하나"를 다시 계산해 data 에 맞추는 동작. 범위 = 전체 또는 영상 하나. 즉시 wake · 자기 호출 · 재개 tick 을 전부 대체 | 현행 `/tick` · `/wake` |
| **작업 · 작업 id** | 적용 큐로 전달되는 요청 하나와 그 식별자(태스크 이름 = 중복 적재 방지) | job(단독) |
| **`ops` 브랜치** | 운영 상태 — `control.json` · `admin_state.json`(재등록 차단 · 잔재 슬롯) · 작업 이력(`history.json`) · 로그인 nonce | 현행 data 브랜치의 control · admin_state |
| **관리 페이지** | 운영자 웹 화면(`/admin`). 로그인 = 텔레그램 `/admin` 일회용 링크 | 관리 콘솔, 어드민 |
| **텔레그램 비상 명령** | v4a 에서 텔레그램에 남는 명령 — `/status` `/pause` `/resume` `/list` `/admin` | — |
| **`out`** | (v4a D7) preview 아이템이 `preview.json` 에서 빠져 `preview_archive.json` 으로 가는 신호. 저장되는 상태가 아니다(FSM 파생 값). 구 이름 `none` — 옛 모니터 로그의 `none` 은 같은 뜻으로 읽는다 | `none`(preview 상태를 가리킬 때). YouTube `liveBroadcastContent="none"` · 소식 `mode:"none"` 은 다른 뜻이라 그대로 |
| **`yt_notif` 작업** | (v4a D1~D3) 업스트림 YouTube 알림을 상태 신호로 쓰는 적용 큐 작업 — reconcile(영상) 후 30분 전 알림 → watching, 시작 알림 → live, URL 없는 예고는 ±45분 자리표시에 URL 부여 | — |
| **로컬 시험판** *(제안 — 사용자 확인 전)* | v4a 를 배포하지 않고 운영자 로컬 PC(24시간)에서 돌리는 형태. 저장은 `_local/<브랜치>/`, 폰 알림은 Tailscale 로 수신 | — |
| **로컬 러너** *(제안 — 사용자 확인 전)* | 로컬 시험판을 한 프로세스로 띄우는 `python -m src.backend.local_runner` — 접수 앱 + 쓰기 스레드 `q-apply` + 가공 스레드 `q-enrich` + 정기 잡 스레드 + 텔레그램 폴링 | — |
| **프리미어** | YouTube 「プレミア公開」 — 미리 올린 녹화본을 정해진 시각에 다 같이 처음 보는 공개 방식(대기실 · 실시간 채팅 · 끝나면 일반 영상). API 는 라이브 예정(`upcoming`)과 똑같이 보고하므로 `VideoInfo.is_premiere`(업로드 상태 `processed` / duration ≠ `P0D`)로 가른다. v4a 는 **그룹 공식 채널** 프리미어만 방송 카드에서 뺀다(D26, `preview_build.is_group_release`) — 멤버 개인 채널 프리미어는 카드로 올린다. OBS 로 녹화본을 틀어 켜는 방송은 API 상 생방송이라 프리미어가 아니다 | 노래 영상(프리미어가 아닌 일반 업로드 노래 영상 · 歌枠 생방송까지 섞여 들린다), 녹화 방송 |

## 행사 배너 용어 (브랜치 `v4a` — 2026-10-02 설계, 미배포)

「이벤트」는 모니터링 이벤트 로그(`flow=…` 줄)와 헷갈려 쓰지 않는다 — 게임 안 기간 한정 콘텐츠는 **행사**라고 부른다.
설계: `ref/v4a/v4a_event_banner_design.md`, 계약: `docs/SPEC.md` 계약 J.

| 정식 명칭 | 가리키는 것 | 쓰지 말 것 |
|---|---|---|
| **행사** | 게임 안 기간 한정 콘텐츠(예: 챌린지 라이브 「アイの奔流 AtoZ」). 개최일 **과 종료일이 둘 다 있어야** 배너로 오른다. 상시화(종료 없는 상시 운영)된 것은 올리지 않는다 | 이벤트(단독 — 모니터 이벤트 로그와 혼동), 소식(소식판 항목과 혼동) |
| **행사 배너** | 소식 란을 펼쳤을 때 맨 위에 보이는 카드. 데이터 `banners.json` / `banners_archive.json`, 모듈 `banners.py` | 이벤트 배너, 게임 소식 |
| **행사 카드** | 행사 배너 안의 행사 한 건 — 흐린 이미지 배경 + 절취선으로 나뉜 [행사 이미지 | 정보]. 정보 = 한글 제목 + 작은 원제 + 날짜 → 딸린 가챠 → 종료 일정 박스 두 칸 → 진행 막대(점선 · 말풍선). 여러 장이면 이미지가 5초마다 한 방향 슬라이드. 표시 상태 sched · live · warn(노랑) · urgent(빨강) · done(회색, 자정까지) | — |
| **딸린 가챠** | 행사 카드 **안에** 하위 블록으로 들어가는 가챠(별도 카드 아님, 가챠 이미지는 안 씀). 한글 제목 + 작은 원제 + 행사와 **다른 부분의 기간만**(같은 날이면 「종료 11:59」, 날짜가 다르면 날짜까지) | 가챠 카드, 가챠 이벤트 |
| **게임 계정** | 행사를 알리는 게임 공식 X 계정(현재 `bang_dream_on`, 표시명 バンドリ！アワーノーツ). `config/channels.json` `game_accounts`. 이 계정 글은 소식 · 스케줄 경로를 타지 않고 **행사 판정**으로만 간다 | 공식 계정(= 그룹 공식 `@BDP_yumemita` 만 가리킨다), 크로스오버 계정 |
| **행사 판정** | 게임 계정 글 1건마다 외부 LLM(`llm.banner_judge`)이 내리는 판단 — 무관 · 새 행사 · 갱신 · 보류 · 취소 + 근거 한 문장. 작업 탭 「LLM 판단」(`kind=banner_judge`)에 기록 · 되돌리기 | — |
| **보류 표시** | 개최가 보류된 행사 — 배너에 기존 개최일을 `mm.dd(보류)` 로 쓰고 그 날짜 + 15일까지만 둔다. 새 기간 공지가 오면 그 날짜로 갱신해 다시 올린다 | 연기(날짜가 정해진 변경은 보류가 아니라 날짜 갱신) |

| 용어 | 뜻 |
|---|---|
| **LLM 판단** | 자동 인입에서 LLM 이 내린 판정(행사 · 방송 취소/변경 · 합동 게스트 · 소식 중복 · 이미지 OCR 참여 멤버 · 본인 예고 확인 · 외부 채널 참여). ops `llm_actions.json` 에 기록. |
| **반려** | (구 「되돌리기」) 그 판단이 데이터에 한 변경만 원래대로 돌리는 롤백. 같은 글을 자동으로 다시 판정하지 않는다. 롤백할 변경이 없는 검토용 판단도 반려할 수 있다(표시만 「반려됨」). |
| **LLM 재판단** | 반려된 판단을 기록해 둔 입력(`input`)으로 같은 판정을 LLM 이 다시 하는 것. 프롬프트 앞에 「이전 판정이 반려됐다」 힌트가 붙는다. 입력이 없는 옛 기록은 불가. |
| **사용자 판단** | 반려된 판단의 결과를 운영자가 직접 정해(종류별 선택지) 같은 반영 경로로 처리하는 것. LLM 호출 없음. |
| **후속 판단** | 재판단 · 사용자 판단이 남기는 새 기록(`parent_id` 로 이어짐, `by` = `llm_rejudge`/`user`). 다시 반려할 수 있다. 한 기록의 후속은 한 번. |

## 에러 버스 용어 (브랜치 `v4.3-fullauto` 전용 — 2026-10-12 운영자 승인, 미배포)

규약 본문: `docs/BUS_PROTOCOL.md`. 이 브랜치에 한해 등록한 용어이며 `main` 용어집에는 아직 없다.

- **버스** — 발신기와 수신기가 메시지를 주고받는 공용 통로. 지금은 공유 폴더(`MEW_BUS_DIR`, 폴더 스풀), 나중에 Pub/Sub. "큐"라고 부르지 말 것
  (`jobqueue`의 적용 큐·가공 큐와 헷갈린다).
- **발신기** — 서비스(러너)의 에러 로그 · 이벤트를 **봉투**로 만들어 버스에 내보내고 제어 봉투를 받아 반영하는 쪽. `src/bus/`.
- **수신기** — 버스에서 에러 봉투를 가져와 분석 · 대응(`claude -p`)하는 쪽. 발신기와 **별도 세션** — 서로의 코드를 모른다.
- **봉투** — 버스를 오가는 메시지 한 건(JSON). 종류: 에러 봉투 `mew.err/1` · 제어 봉투 `mew.ctl/1` · 보고 봉투 `mew.report/1` · 생존 신호 `mew.hb/1`.
- **심각도** — 봉투의 `severity` 5단계(2026-10-13 개정, `TRACE` 폐기): `CRITICAL`(에러로 러너(서버)가 뻗어 기능 불능) · `ERROR`(정의된 폴백이 아닌 의도되지 않은 동작으로 수행, 또는
  폴백이 있어도 의도한 출력이 끝까지 나오지 못해 유저에게 서비스 제공 실패) · `WARN`(정상 수행은 못 했으나 정의된 폴백으로 수행되어 서비스는 제공됨) · `INFO`(정의된 기능이 의도대로 정상 수행 — 409 재시도
  성공 포함) · `DEBUG`(사용자 정의 등 필요에 따라 남기는 로그). 파이썬 `WARNING` 은 `WARN` 으로 표기. 한 사건에는 한 등급만 붙인다. 판정 규칙 · 변환은 `BUS_PROTOCOL.md` §1.
- **이벤트 `result`** — 모니터 이벤트 로그의 결과 라벨 3값 `ok`(INFO 와 같은 뜻) · `warn`(WARN 과 같은 뜻 — 구 이름 `degraded`) · `err`(ERROR 와 같은 뜻). 심각도 정의를 그대로 따른다.
- **제어 봉투** — 수신기 → 발신기 명령(`set_level` `pause` `resume` `ping`). **기존 용어 「제어 채널」(텔레그램 운영 명령 경로)과 무관하다** — 섞어 쓰지 말 것.
- **수정 브랜치** (`auto/<시그니처>-<n>`) — 수신기 2단계가 만든 자동 수정 커밋이 놓이는 **로컬 전용** 브랜치. 원격에 푸시하지 않는다(운영자가 요청할 때만).
- **가드** — 자동 수정이 운영 자원(원격 main · data, Vercel 주소, GCP URL, 텔레그램 번호 등)을 건드리지 않는지 **기계적으로** 확인하는 사후 검사(`src/busrx/guard.py`).
  프롬프트 규약과 구분해서 부른다. 상세 `docs/AUTOFIX.md` §3.
- **이중 검토** — 수정안을 만든 쪽(Haiku 5.5)과 별개로, 검증자와 독립 검토자(새 맥락) 둘이 Sonnet 5.5 로 따로 검토하는 것.
- **자동 대응 관리 페이지** — 수신기 프로세스가 별도 포트(8789)로 띄우는 관리 UI(`docs/BUS_DASHBOARD.md`). 러너 **어드민 페이지(`/admin`)와 별개**이며 코드도 공유하지 않는다. "어드민"이라고만 부르지 말 것.
- **수신기 전용 봇** — 수신기가 알림 · 보고서 · DM 명령(`/ctl` `/auto` …)에 쓰는 텔레그램 봇(`RX_TELEGRAM_BOT_TOKEN`). 러너 봇(`TELEGRAM_BOT_TOKEN`)과 **별개** — 한 봇을 두 프로세스가 폴링할 수 없어 분리했다.
- **정책** (에러 레벨별 자동 대응 정책) — 심각도마다 기록 · 동작(끔/분석만/수정까지) · 프리셋 · 쿨다운을 정하는 설정(`rx/policy.json`). 용어 「프리셋」과 함께 쓴다.
- **프리셋** (파이프라인 프리셋) — 자동 수정 파이프라인의 구성: **표준**(충분한 검증) / **긴급**(최소 검증). 가드는 모든 프리셋에서 고정. 로컬 브랜치 「프리셋」과 무관.
- **블록** (파이프라인 블록) — 자동 수정 파이프라인을 이루는 한 단계(명세서 · 구현 · 가드 · 테스트 · 검증 · 독립 검토 · 커밋 · 보호 확인 · 적용 · 재시작). **잠금 블록**은 빼거나 끄거나 순서를 바꿀 수 없다. 카탈로그 `src/busrx/pipelines.py`, 설명 `docs/AUTOFIX.md` §9.
- **파이프라인** — 블록의 순서 있는 목록. 내장(표준 · 긴급)과 사용자 정의(`rx/pipelines.json`). 용어 「프리셋」은 내장 파이프라인을 가리킨다.
- **자동 대응** (정식 풀네임: 에러 자동 대응) — 수신기가 발신기의 에러를 받아 **분석 → (정책에 따라) 수정 · 승인 · 적용**까지 하는 기능 전체의 이름(2026-10-13 운영자 확정, 구 표현 「자동제어」 폐기).
  서비스 전체를 운영하는 것이 아니라 **에러에 반응하는 범위**만 가리킨다 — 「자동운영」 · 「자동제어」처럼 넓은 말을 쓰지 말 것. 화면의 「로그 레벨별 대응 정책」 · 「동작 모드」(자동/반자동/끔) · 「동작 주기」가 모두 자동 대응의 설정이다.
  짝이 되는 말은 「사람 조치 필요」. 코드 · 내부 이름(`busrx` 등)은 그대로 두고 사용자에게 보이는 문구와 문서에만 쓴다.
- **테스트판 버전 (`vT`)** — 브랜치 `v4.3-fullauto`(테스트판) 전용 버전 번호. `vT1.0.0` 에서 시작해 프로젝트의 기존 규칙(핫픽스 = 패치 번호, 기능 = 마이너)대로 올린다(2026-10-13 운영자 확정). 배포판 번호(`v4.x`)와 별개이며 서로 대응하지 않는다(`vT1.0.0` = 옛 표기 `v4.3.x` · 배포판 v4.2.3 위의 에러 버스 · 자동 대응 실험 일체). 기록은 `docs/VERSION_vT.md`.
- **동작 모드** — 자동 대응 전체 스위치: **자동**(기본, 전부 자동 패치) / **반자동**(패치 계획안을 사람이 승인 · 반려 · 거절) / **끔**(동작 안 함, 기록만). 에러 레벨별 「정책」과 별개. `rx/PAUSE`(긴급 임시 정지)와도 구분한다.
- **패치 계획안** (계획안) — 반자동 모드에서 분석 뒤 만들어지는 승인 대기 항목: 에러 요약 + 패치 계획(여러 판 rev) + 계획 파일 + 결정 이력. 「승인 / 반려(재계획) / 거절」 세 결정을 쓴다.
- **사람 조치 필요** — 외부 서비스(LLM · YouTube · GitHub · 텔레그램 등 모든 외부 API)의 인증 · 결제/요금제 · 쿼터 · 계정 · 정책 변경이 원인이라 **코드가 아니라 사람이 결정해야 하는** 에러에 자동 대응이 붙이는 상태(분석 결과 `needs_human`).
  수정 · 계획안을 만들지 않고 텔레그램에 1회 알리며, 같은 에러는 표시가 풀리거나 만료(기본 24시간)될 때까지 다시 분석하지 않는다. Control 탭 「조치 완료 — 다시 감시」로 푼다. 상세 `docs/AUTOFIX.md` §11.
- **fault_lab** — 결함 주입 시험용 격리 모듈(`src/backend/fault_lab.py`, `fault_lab_run.py`). 일부러 버그가 들어 있고 러너는 import 하지 않는다. 고치지 말 것(자동 수정이 고쳐야 한다).
