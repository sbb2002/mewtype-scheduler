# 이 앱의 생명주기
![image](lifespan_clean.png)

* idle : 방송 예고가 알려지지 않은 상태 + 현재 라이브 중이 아님.
* upcoming : 현재 라이브 중이 아니지만 다음 방송 예고(24시간 이내)가 있는 상태.
* live : 현재 예고된 방송을 라이브로 진행하는 상태.

# upcoming 감지
1) RSS 수집 : videoId, title, thumbnailURL 등을 수집하여 다음 방송에고를 감지함.
2) 새로운 방송 예고 또는 기존 예고 중 변경된 예고는 youtube data api를 호출하여 현재 상태를 none->upcoming으로 업데이트 및 프론트 업데이트.
3) 시작시간 3분 전에 'upcoming 시작 직전' 로직을 이행하도록 예약 후 이 로직은 종료.

# upcoming 시작 직전
* api 호출 : videos.list 호출로 라이브 상태인지 아닌지 파악. (미리 켜는 경우를 감지하기 위함.) 만약 켰으면 live로 프론트 업데이트하고 이 로직은 종료.
1) 시작 시간 3분 전 : api 호출. 만약 시작하지 않았으면 2)번으로.
2) 시작 시간 당시 : api 호출. 만약 시작하지 않았으면 3)번으로.
3) 시작 시간 3*n분 마다 : api 호출. 만약 시작하였으면 이 로직은 종료. 또는 시작 시간에서 60분 경과했는데 라이브 상태가 아니라면 아래 fallback 발동.

* fallback
1) scheduleStartTime 엔드포인트 호출. 시작 시간이 변동되었는지 확인.
2) 만약 시작 시간이 변동되었다면 시작 시간 변경 업데이트 후 바뀐 시작 시간 3분 전에 'upcoming 시작 직전' 로직을 이행하도록 예약 후 이 로직은 종료.
3) 만약 변동이 없다면, 시작 시간 1시간씩 경과할 때마다 1)번부터 시작. 이는 라이브 여부 상태가 none or live으로 나올 때까지 진행. 

# live 이후
1) 실제 live 시작 후 60분 이후 3*n분마다 vidoes.list의 liveBroadcastContent 요소를 확인.
2) 이 요소가 live인 경우 다음 3분째에 다시 1)으로 돌아감.
3) 만약 none으로 나타나는 경우 방송이 종료되었다(idle)고 판정하고 프론트 업데이트 후 이 로직을 종료.

# 백엔드 유의사항
- 현재 github actions -> render + cron으로 이주 계획.
- render 무료티어 플랜 특성 상 15분이 지나면 자동 sleep처리가 됨.
- upcoming 상태는 현재 기준 일정한 로직을 가지고 유튜브 예고 스트림이 감지될 경우 idle -> upcoming으로 업데이트함.
- 5명 전원을 모니터링하면서 1명이라도 upcoming, live 신호가 있다면 놓치지말고 업데이트해야함.
- 5명이 거의 비슷한 시간대에 upcoming 예고, live 시작/종료하므로 이를 업데이트하거나 api 호출 시 race condition과 ratelimit violation이 예상됨. 
- 따라서 이를 고려하여 큐잉 시스템 등을 활용하여 api 호출 또는 프론트 업데이트해야함. 큐잉 시스템은 bandori-playlist-maker의 AI모드 큐잉 시스템이나 veiga-translator의 전사/번역 파이프라인 큐잉 시스템의 구조를 참고하여 제작하면 될 것 같다.
