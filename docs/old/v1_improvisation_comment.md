# v1_improvisation 검토 코멘트 (2026-08-31)

`v1_improvisation.md`의 보완 로직에 대한 리뷰. 현재 구현(`src/collector/`)과 대조함.

## 총평

방향(upcoming→live 확인 버스트)은 맞다. 다만 **실행 기반과 상태 저장이 안 풀렸고, 큐잉 시스템은 이 규모(N=5)에 과설계**다.

## 현재 구현 vs 계획

- **현재**: 완전 무상태 배치. 매시간 cron 1회 → `schedule.json` 로드 → RSS 발견 → `videos.list` enrich → reconcile → 변경 시 커밋. 타이머·콜백 예약 없음.
- **계획**: 상태 full 이벤트 드리븐(T-3분 콜백 예약, 버스트 폴링, 단계별 상태머신). 작은 리팩터가 아니라 아키텍처 전환.

---

## 반드시 보완해야 할 점

### 1. 실행 기반을 먼저 정해야 함 — "3분 전 예약"과 현재 후보가 서로 모순

- **GitHub Actions cron**: 정각 ±3~15분(드물게 1시간) 지터, 최소 간격 5분 → 3분 정밀도 불가.
- **Render 무료 티어**: 15분 유휴 시 sleep + 콜드스타트. 타이머를 들고 있을 프로세스가 안 살아있음. Render cron job은 일회성 호출이라 실행 간 타이머 유지 안 됨 → 정밀도가 오히려 악화.
- 항상 떠 있는 타이머 프로세스가 필요하면 유료 Background Worker.

**→ "이벤트 드리븐 + 타이머"를 "적응형 간격 폴링"으로 재정의.** 일회성 cron(5분 간격) + 상태 파일. 매 실행: 임박/라이브 구간에 든 방송이 있으면 배치 `videos.list` 1회, 없으면 평소 RSS+reconcile. 달성 가능한 지연은 3분이 아니라 현실적으로 **5~10분**이라고 못박을 것.

### 2. 진행 중 폴링 상태를 저장할 스키마가 없음

"예약 후 이 로직은 종료" — 그 예약을 어디 저장? 무상태 일회성 실행이면 매 런마다 다시 읽어야 함. `schedule.json`에 방송별 `poll_phase`, `next_check_at`, `check_count` 필드를 추가하거나 별도 `pending.json` 필요. 문서에 없음.

**→ in-flight 폴링 상태 스키마 정의. 이거 없이는 계획이 성립 안 됨.**

### 3. 큐잉 시스템(본문 34~35번 줄)은 이 워크로드에 불필요 — 빼는 걸 권함

- YouTube API에 여기서 걸릴 초당 레이트리밋 없음. 한도는 일 10,000유닛 + 분당 1,800요청. 사이클당 요청 1~5개면 근처도 못 감.
- race condition: 단일 cron 프로세스가 순차 1패스면 동시성 자체가 없음. 방송인별 워커를 동시에 띄울 때만 레이스 발생 — 5개짜리에 그럴 이유 없음. `for` 루프면 끝.
- `videos.list`는 id 50개까지 배치 → 5명을 한 요청에 처리. 큐가 아니라 그 반대(단일 벡터 호출).
- 유일한 실제 조율 대상인 data 브랜치 커밋 충돌은 이미 `concurrency: {group: collect, cancel-in-progress: false}`가 직렬화 중.

**→ v1.x에서 큐잉 제외.** 없는 스케일 문제를 푸는 것. "N=5는 배치 1회로 처리됨, 큐잉은 검토 후 보류(50채널+ 되면 재검토)"로 기록.

### 4. "live+60분 이후에야 종료 확인 시작" → 60분 사각지대

60분 미만 방송(게릴라, 테스트, 크래시 후 재시작)이 60분 마크까지 종료로 안 잡힘. 이 방송인들 짧은 방송 잦음. 종료 확인도 어차피 공짜 배치 호출.

**→ 라이브 방송은 시작 직후부터 매 사이클 배치에 포함.** 비용 0. 종료 판정은 현재 `reconcile.py`처럼 `actual_end` 존재 기준 유지(단순 `live_state=="none"` 말고).

### 5. Render 이주의 실제 이유가 문서에 없음

정밀도가 목적이면 Render 무료는 오히려 악화. 항상 떠있는 타이머 프로세스가 목적이면 유료 — 가격을 적을 것. cron 신뢰성이 목적이면 현재 얼마나 자주 런이 실제로 누락되는지 먼저 측정. `GITHUB_TOKEN` 커밋 플로우가 공짜인 걸 버리는 대가가 큼.

### 6. 사소함: "scheduleStartTime 엔드포인트"는 별도 엔드포인트 아님

`videos.list?part=liveStreamingDetails`의 필드일 뿐. 같은 호출 1유닛. 본문 20번 줄 표현만 정정.

## 계획에서 좋은 부분

- upcoming→live 확인 버스트: v1의 최대 약점(라이브 시작 반영 최대 1시간 지연)을 정확히 겨냥.
- fallback에서 `scheduledStartTime` 변동 체크: 맞고 저렴.
- "미리 켜는 경우 감지": 좋은 캐치. T-3분 조기 `videos.list`로 커버.
- detect / imminent / live / ended 단계 분리: 깔끔한 상태머신.

## 권장 순서

1. **가장 싼 즉효, 먼저 하고 측정**: RSS 전용 워크플로를 `*/15`(또는 `7,22,37,52 * * * *`)로 추가. RSS는 쿼터 0. 예고 발견 바닥을 60분→15분으로. 이것만으로 라이브 시작 지연이 여전히 체감 문제인지 먼저 확인 — 아니면 버스트 머신 전체가 불필요.
2. 실행 기반 확정(§1). 3분 목표는 버리고 5~10분으로.
3. in-flight 폴링 상태 스키마 정의(§2).
4. 큐잉 삭제, "보류" 메모(§3).
5. 라이브를 매 사이클 배치에 포함(§4).
6. Render 이주는 구체적 사유 적거나 드롭(§5).

## 부록 A. 실행 기반 옵션 비교 (2026-08-31 논의)

§1의 "실행 기반을 먼저 정하라"에 대한 후속. 요구: 무료 유지, 정시성 예측 가능, `data` 브랜치 커밋 유지.

### A-1. GitHub Actions `schedule:` cron (현행)

- GitHub 배치 스케줄러가 처리 → 공식 문서상 고부하 시(특히 매시 정각) 지연. 실측 3~15분, 부하 크면 **런 통째 누락**.
- 최소 간격 5분이지만 그 간격에서 신뢰도 낮음. 60일 레포 비활성 시 스케줄 비활성화됨.
- → 3분 정밀도 불가. 현행 유지 시 실효 지연을 5~10분+ 로 인정해야 함.

### A-2. Google Cloud Scheduler → GitHub Actions (트리거만 교체) — **권장**

- Cloud Scheduler(관리형 cron, SLA 99.9%, 목표시각 수 초 내 발화, 재시도, at-least-once)가
  HTTP로 GitHub REST API `workflow_dispatch` 호출 → 명시적 API 디스패치라 배치 스케줄러 우회.
- 체인: `정시(수초) → API 수락(수초) → 러너 픽업(<1분)` = **목표시각 + 약 1~3분**, 예측 가능.
- **비용 $0**: Cloud Scheduler는 billing account당 월 3잡 무료(초과 $0.10/잡/월). GitHub Actions는 public 레포면 무제한 무료(레포가 public 전제). GCP 카드 등록은 타 프로젝트로 이미 완료.
- **인증**: 외부 트리거는 PAT 또는 GitHub App 필요(`GITHUB_TOKEN`은 런 내부에만 존재).
  - 권장: **fine-grained PAT**, `sbb2002/mewtype-scheduler` 한 레포만, 권한 `Actions: write` + `Contents: read`.
    유출 시 blast radius가 "public 레포 하나의 워크플로 트리거"뿐 → **무기한 또는 1년 만료 + 캘린더 리마인더**로 충분.
  - 만료 관리가 싫으면 GitHub App(private key 무기한, 1시간짜리 installation token 발급) — 최초 세팅 ~20분, 개인 레포엔 다소 과함.
  - PAT 유효기간 선택지: classic = 7/30/60/90/커스텀/무기한, fine-grained = 최대 366일.
- **러너 준비 오버헤드 ~2~3분은 이 설계에서 문제 없음.** Cloud Scheduler의 목적은 초 단축이 아니라 예측 가능성(누락 없음). 적응형 폴링(5분 cron, 실효 5~10분)의 노이즈 범위 안.
- **캐시로 러너 단축?** 의존성이 `requests` 하나라 `cache: pip` 로 아껴봐야 5~15초. 지배적 비용인 VM 할당(~10~30초)은 캐시 불가. 설정 복잡도 대비 이득 없음 → 안 함.

### A-3. Google Cloud Scheduler → Cloud Run/Functions (로직 자체 이전)

- 러너 오버헤드 제거. 콜드스타트 1~2초, 지연 **<30초** 가능. Cloud Run 무료 티어 넉넉(월 200만 요청, scale-to-zero).
- 대가: 컨테이너화 + `data` 브랜치 커밋용 git 인증을 잡 안에서 처리(PAT/App). Actions보다 이주 폭 큼.
- **판단**: v1.x에선 불필요. A-2의 ~2~3분이 "너무 느리다"고 체감될 때가 A-3로 갈 신호. 그 전엔 오버킬.

### 결론

- **A-2 채택**: 최소 이주로 ~2분급 예측 가능한 정시성. §권장순서의 "적응형 간격 폴링"(5분 cron)과 궁합 좋음.
- Render(A안 원문)는 무료 티어 sleep+콜드스타트로 정시성이 오히려 악화 → 드롭.
- 조건: 레포 public 유지, fine-grained PAT(단일 레포·최소 권한).
