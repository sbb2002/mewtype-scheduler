# 로컬 러너 로그 레벨 적용 검토 (2026-10-13)

정의는 `docs/BUS_PROTOCOL.md` §1. 이 문서는 `src/backend/` 의 로그 호출(약 390건)과 이벤트 로그(`result` 76건)를 그 정의로 다시 판정한 결과와 적용 규칙이다.

## 적용 규칙 (코드에서 레벨을 고르는 순서)

1. 의도대로 끝났다 → `INFO` (거부·건너뜀·"해당 없음" 판정도 설계된 정상 동작이면 INFO)
2. 409/429 재시도가 진행 중이다 → `INFO` (재시도 끝에 성공하는 것이 정상 경로. 재시도가 소진되면 그 뒤 결과로 판정)
3. 코드에 명시된 대체 경로로 서비스가 이어졌다 → `WARN` (예: 모델 A 실패 → 모델 B, 번역 실패 → 원문 + 다음 tick 재시도, 부가 기록 실패 후 계속)
4. 대체 경로가 없거나, 있어도 유저에게 보일 결과가 끝내 만들어지지 못했다 → `ERROR` (예: 트윗이 등록되지 않음, 알림이 전달되지 않음, 신곡 등록 불가)
5. 러너가 기동하지 못하거나 쓰기 스레드가 죽었다 → `CRITICAL`
6. **같은 사건은 한 곳에서만 기록한다.** 이벤트(monitor)가 있으면 그 사건의 파이썬 경고 로그는 INFO, 예외(traceback)가 있으면 이벤트는 `no_bus` 로 버스 발신을 생략한다.

## 판정을 유지한 것 (근거)

- `Error handling /명령` 류 예외 전부: 처리 중 예기치 못한 예외 → ERROR.
- 작업 유실(`Job dead after N attempts`, 유실 큐 적재 실패, `on_update 콜백 실패`): 결과가 사라짐 → ERROR.
- 운영자용 관리 페이지 조회 실패(이벤트 로그 읽기, Cloud Tasks 목록 등)와 관리자 요청 실패: 요청자에게 오류가 바로 표시되므로 WARN 유지.
- 부가 기록(monitor_log, flows.json, recent_jobs.json, 원문 보존 등) 실패 후 계속: 본 기능 영향 없음 → WARN.
- 텔레그램 폴링 오류(재시도 · 백오프): 한 번 실패할 때마다 WARN. 계속 실패해도 올라가지 않는 한계가 있다(아래 남은 항목).

## 남은 항목 (확정 못 한 것)

- 텔레그램 폴링이 연속으로 계속 실패해도 레벨이 올라가지 않는다(WARN 반복). 연속 N회 실패 시 ERROR 로 올리는 규칙이 필요하다.
- `vision.py` 의 모델별 실패 줄은 WARN 이다. 보조 모델로 성공한 경우와 모두 실패한 경우를 한 줄로 합치지 않았다.
- 관리 페이지 조회 실패(이벤트 로그 읽기 등)를 WARN 으로 둔 판단은 "운영자에게 오류가 바로 보인다"는 근거다. 운영자가 다르게 보면 ERROR 로 올린다.
- 정의 밖 서버 외부 로거(werkzeug, requests 등)가 루트 핸들러로 발신되는지 코드로 확인하지 못했다.
