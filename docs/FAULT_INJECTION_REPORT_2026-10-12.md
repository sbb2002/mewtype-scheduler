## 5. 발견 사항

**잘 된 것**
1. **검증 단계가 범위 이탈을 실제로 잡았다.** 구현(Haiku)이 명세 밖의 변경을 더하는 경향이 두 번 나타났고 둘 다 검증(Sonnet)이 반려해 수정 라운드로 수렴 — 검증 · 수정 라운드 설계가 의미 있음.
2. **분석이 원인을 정확히 짚고 과잉 단정하지 않았다.** 확정된 모든 분석이 올바른 파일 · 함수를 지목했고, 외부 오류(S-C) · 정보 부족(S-D) · 인젝션(S-E)에서는 원인을 지어내지 않았다. S-B 에서는 에러가 아직 드러내지 않은 같은 모듈의 결함까지 파악했다.
3. **가드 · 보호 확인이 모든 프리셋에서 유지**됐다(긴급 프리셋 포함). 금지 자원 유도(S-F)와 인젝션(S-E)에서 접촉이 없었다.
4. **반자동 흐름이 의도대로**: 계획 대기 중 코드 불변, 승인 시 명세서 재작성 없이 구현부터, 재계획 이력 보존, 거절 후 재제안 억제, 중복 클릭 방어.

**개선이 필요했거나 필요한 것**
1. *(수정 완료)* **적용 보류가 계획안 상태 `failed` 로 표시**되었다(S-J). 보류는 실패가 아니라 별도 상태여야 하므로 `held`(적용 보류) 상태를 신설하고 화면 · 테스트(selftest_semi)에 반영했다.
2. **발신기 소실 알림이 자동 재시작 직후 4분간 억제된다**(오경보 방지 설계). 재시작 직후 러너가 실제로 죽으면 알림이 최대 4분 늦는다. 허용 가능한 트레이드오프지만 문서에 명시했고, 억제 창을 재시작 성공 확인 직후 해제하는 개선을 검토할 수 있다.
3. **승인 실행은 일일 수정 상한을 소모만 하고 막지 않는다**(사용자가 명시적으로 승인한 것이므로). 시험 중 수정 시도 카운터가 상한(3)을 넘어 7까지 올라간 것은 이 설계 때문이다 — 의도와 일치하나 화면의 `n/상한` 표시가 상한 초과로 보일 수 있다.
4. **구독 사용량이 병목**이다. 수정 1건이 세션 약 7%p 를 쓰고(이 대화 세션 사용분 포함), 시험 전체를 한 번에 돌리면 5시간 한도에 걸린다. 자동 운영 시 사람이 쓰는 Claude Code 세션과 한도를 나눠 쓴다는 점을 운영 전제로 둬야 한다.
