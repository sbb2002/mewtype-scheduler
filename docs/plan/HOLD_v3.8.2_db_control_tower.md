**상태: 보류 (2026-09-21 사용자 결정). 배포·`main` 머지 금지 — 재검토 전까지 이 브랜치는 보존만 한다.**
사용자 결정문: "당장 배치하긴 어려울 것 같고, 하더라도 **속도와 안정성을 모두 잡아야만** 의미가 있다."

## 왜 보류했나 (2026-09-21 로컬 실험 + 운영 로그 조사)

관제소는 GitHub 쪽 실패(속도 제한·409)를 막지만, 우리가 겪는 주된 병목·유실은 다루지 않는다.

### 1) 60건 버스트 비교 (로컬, 가짜 GitHub, 관제소 있음 vs 없음)
조건: 1.5초 안에 `/ingest` 60건 — 소식 5 · 예고 5(합동 1) · 개인 트윗 50(유닛당 10). 외부 LLM 은 1초 지연 가짜. 프로세스가 끝난 뒤 최종 상태 기준.

| | 관제소 있음 | 관제소 없음(=현재 main) |
|---|---|---|
| 개인 트윗 저장 | 50/50 | 17/50 |
| 예고 저장 | 5/5 | 2/5 (합동 유실) |
| **소식 저장** | **0/5** | **0/5** |
| GitHub 속도 제한 / 409 | 0 / 0 | 125 / 43 |
| 응답 시간 중앙값 | 82.9초 | 62.8초 |
| 60초 초과 요청 | 44/60 | 43/60 |

- **관제소가 나아진 것**: GitHub 쪽 실패(속도 제한·409)를 0 으로 → 트윗·예고 저장률.
- **나아지지 않은 것**: 지연(오히려 홉만큼 늘어남), 60초 초과 요청 수(업스트림 60초 타임아웃 문제 그대로), **소식 유실(관제소와 무관)**.
- **진짜 병목**: 백엔드 `/write`(`concurrency=1`) 직렬화 — 처리량 ≈ 3.3초/건(60건 이상적 완주 ≈ 200초, 추정). 제어 채널→백엔드 `/write` 호출의 **내부 60초 대기**(`WriteError … Read timed out (read timeout=60)`)를 넘긴 요청이 실패로 끝난다.
- **소식 유실 원인**: 소식은 `notice_sweep` → `apply_notice` 2단계. 1단계가 60초 대기를 넘기면 제어 채널이 2단계를 보내지 않고 포기(`auto notice 실패`) → 관제소 유무와 무관하게 5/5 유실.
- 직접 모드에서 응답이 63초에 몰린 것(43건, 62.8~64.1초)은 처리가 빨라서가 아니라 내부 60초 대기 + 준비 3초에 **포기한** 시간이다.
- 관제소 모드에서 트윗 35건은 응답이 `mode: error` 였는데도 나중에 저장됐다(시뮬레이터 백엔드는 클라이언트가 끊어도 잡을 끝까지 실행). **실제 Cloud Run 이 끊긴 요청의 잡을 계속 실행하는지는 미확인** — 실제로는 유실일 수 있다.

### 2) 운영 로그 (data 저장소 `monitoring/events-*.jsonl`, 09-09~09-21 13일)
- 이벤트 1,795건 중 `err` 2 · `degraded` 2. `err` 2건은 09-15·09-16(09-16 = 409 유실 사고, v3.7 `/write` 직렬화 **이전**) — v3.7 배포(09-17) 이후 0.
- **403/429 속도 제한 기록 없음.**
- 실제 최대 버스트: ingest 계열 이벤트가 30~60초 창에 **8건**(5초 창 6건). 실험은 1.5초에 60건 = 관측 최대의 7배 이상.
- 8건 버스트 시뮬레이션(`scripts/sim_burst.py --burst 8`): 관제소 유무 차이 거의 없음(둘 다 8/8, 지연 차이 ≈2%).

### 3) 추가 비용·위험
서비스 1개 증가(3개), 모든 GitHub 접근에 홉 추가, 관제소 장애 시 `/tick`·`/wake`·`/status`·`/list` 동반 정지(SPOF).

## 결과를 그대로 믿으면 안 되는 이유
- 가짜 GitHub **모형**: 분당 900점 등 임계값은 가정값(실제 GitHub 가 그 지점에서 막는지 미확인). 동시 PUT 409 는 `scripts/probe_github.py` 로 실제 확인됨.
- 지연은 실측 중앙값(GET 0.23·PUT 0.80초), 가짜 LLM 1초는 임의값. Cloud Run 요청 취소·큐 동작은 모형과 다를 수 있음.
- 운영 13일은 짧은 표본이고, 모니터 로그는 **로그 기록 자체가 실패한 경우**를 못 남긴다. "안 일어난다"가 아니라 "13일간 관측된 적 없다".

## 재검토 조건 / 다음에 볼 것
1. **관제소 단독으로는 배포하지 않는다.** 속도(`/write` 잡 비용, ≈3.3초/건)와 안정성(소식 2단계 유실·내부 60초 대기)을 **함께** 개선해야 의미가 있다.
2. 가설(미검증): 소식 `notice_sweep`+`apply_notice` 를 한 잡으로 통합 / `/write` 잡 하나가 쓰는 GitHub 호출 수·시간 측정 / 트윗 커밋 배치화.
3. 재평가 시점: 정식 출시일 같은 **대형 이벤트 전**(5인 개인 트윗 + 공식 계정 동시 폭주 가능성).
4. 업스트림 Automate HTTP 타임아웃은 60초(2026-09-21 운영자 상향) — 60초 초과 요청은 폰에서 실패 처리되고 재시도 없음.
