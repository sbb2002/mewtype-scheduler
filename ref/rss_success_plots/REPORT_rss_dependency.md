# RSS 피드 의존성 점검 보고서 — RSS 가 무력화되면 이 앱은 어떻게 되는가

작성: 2026-10-13 (v4.3 테스트 중 조사). 대상: 배포판 `mewtype-backend`(Cloud Run) 로그 30일(2026-09-13~10-13) + 코드 점검 + 이 PC 직접 조회.
관련 파일: 같은 폴더의 `rss_success_by_hour.png` · `rss_success_heatmap.png` · `hourly.csv`(집계) · `plot.py`(그림 생성), `../pubsub_probe/`(PubSub 시험 기록).

## 1. 결론 (요약)

1. **지금도 RSS 는 한국 시간 낮(08~16시)에 대부분 실패한다.** 17~07시에는 거의 100% 성공. 같은 시간대에 배포판(Cloud Run)과 이 PC 모두 실패하고, 채널·코드 경로(개인 채널 / 곡 토픽 채널)와 무관하게 같은 곡선이다 → 앱 코드 문제가 아니라 YouTube 쪽의 시간대성 제한으로 보인다(원인 확정 불가).
2. **RSS 가 완전히 없어져도 평소 방송 추적은 유지된다.** RSS 는 "새 영상 ID 발견"만 맡고 상태 판정은 `videos.list` API 가 하며, 방송 예고는 X 트윗 중계·관리 페이지·공식 스케줄 등 다른 경로로도 들어오기 때문이다.
3. **확실히 못 하게 되는 것은 둘이다.** ① **신곡 자동 감지 전체**(곡 토픽 채널 RSS 가 유일한 경로), ② **트윗·알림 없이 YouTube 에서만 새로 만든 예약·프리미어 방송의 발견**.
4. **대체 경로가 있다.** YouTube Data API `playlistItems.list`(채널 업로드 재생목록, 요청당 쿼터 1)가 예약 영상과 곡 토픽 채널 모두를 돌려주는 것을 직접 확인했다(§5). 운영자 결정(2026-10-13)은 **보류하고 관찰** — 아직 도입하지 않았다.

## 2. RSS 가 이 앱에서 하는 일

| 역할 | 위치 | 설명 |
|---|---|---|
| 개인 채널 새 영상 ID 발견 | 틱(10분)마다 `fetch_all_rss_video_ids` → 후보 집합 | 그룹 공식 채널은 제외(노래 영상이 합동 방송으로 팬아웃되는 문제). 발견한 ID 를 `videos.list`(쿼터 1)에 넘겨 상태 판정 |
| 곡 토픽 채널 신곡 감지 | `handlers._detect_new_songs` → `songs.fetch_feed_entries` | 목록에 없는 곡을 `songs.json` 에 등록(독음은 LLM). 방송 판정과 무관 |

RSS 는 **폴링**(10분마다 HTTP GET)이다. 푸시(WebSub)가 아니다. 피드는 시간과 무관하게 그 채널의 **최근 영상 15개**를 담는다(실측: 미야코 15건, 약 한 달 치).

## 4. RSS 가 완전히 없어질 때의 영향 (시나리오 점검)

### ① 예고 상태 감지 (개인 채널)

| 경로 | RSS 없이 가능? |
|---|---|
| 이미 추적 중인 예고의 상태 전환 | **가능** — `videos.list` 로 계속 갱신 |
| 트윗에 영상 URL 이 있는 예고 | **가능** — URL 로 바로 확정 |
| 트윗에 URL 이 없는 예고 | **대체로 가능** — 시작 +2분에 `search.list` 로 찾음(쿼터 100) |
| 공식 일일 스케줄, 관리 페이지 입력, 회원 전용 알림 | **가능** |
| **트윗·알림 없이 YouTube 에서만 새로 만든 예약/프리미어** | **불가능** — 발견 경로가 사라짐 |
| 예고 없이 갑자기 시작한 라이브 | **불가능** (지금도 RSS 가 늦으면 못 잡음) |

### ② 새 음반(신곡) 감지

| 경로 | RSS 없이 가능? |
|---|---|
| 곡 토픽 채널 신곡 자동 감지 | **불가능** — 유일한 경로. 완전히 멈춤 |
| 관리 페이지 「곡 직접 추가」 | **가능** — 영상 URL 만 넣으면 `videos.list` 로 제목·날짜 채움(RSS 로 채우는 부분만 빠짐) |
| 관리 페이지 「지금 RSS 조회」 점검 | 불가능(조회 자체가 RSS) |

(참고: v1 수집기 `src/collector/main.py` 도 RSS 를 쓰지만 break-glass 전용이라 현행 사이트와 무관.)

## 5. 대체 경로 검증 — YouTube Data API 업로드 재생목록

방법: 채널 ID `UCxxxx` 의 업로드 재생목록 `UUxxxx` 를 `playlistItems.list`(쿼터 1/요청)로 조회. 2026-10-13 직접 실행.

| 확인 | 결과 |
|---|---|
| 현재 예정(upcoming) 상태인 리츠 예약 영상 `Pmo1Um8aCfg` | 업로드 재생목록(50건)에 **포함** |
| 현재 예정 상태인 미야코 예약 영상 `65Lq4jg4JmM` | 업로드 재생목록(50건)에 **포함** |
| 곡 토픽 채널 `UUeXzC…` | 200 OK, 59건 최신순 반환(최신 2026-09-29) |

- 쿼터: 틱당 6채널 = 6 units, 하루 약 864 units(일일 한도 10,000, 현재 틱당 사용 1).
- **한계**: 예약 영상 표본이 2건뿐. 한국 시간 낮(RSS 실패 구간)에 이 API 가 안정적인지는 **아직 시험하지 못했다**(API 키 요청이라 RSS 와 다른 경로라 기대는 되지만 미검증).
- `search.list`(eventType=upcoming)는 100 units 이라 10분 주기로는 한도를 넘는다 → 대체 수단이 아니라 최후의 수단.
- PubSub(WebSub)도 Google 의 같은 계열 레거시 프로토콜이라 RSS 보다 안전하다고 보장할 수 없다. PubSub 시험기(`../pubsub_probe/`)는 2026-10-14 약 16:40 까지 알림 수신을 기록 중.

### 5-1. `playlistItems.list` 가 라이브 예정·라이브 중 영상을 감지하는가 (공식 문서 + 실측, 2026-10-13)

**공식 문서가 말하는 것** ([playlistItems.list](https://developers.google.com/youtube/v3/docs/playlistItems/list) · [PlaylistItems 리소스](https://developers.google.com/youtube/v3/docs/playlistItems) · [channels 리소스](https://developers.google.com/youtube/v3/docs/channels) · [변경 이력](https://developers.google.com/youtube/v3/revision_history))
- 쿼터 1 unit/호출, `maxResults` 0~50(기본 5), `playlistId` 로 조회. 업로드 재생목록 ID 는 `channels.list` 의 `contentDetails.relatedPlaylists.uploads` ("채널의 업로드 영상 재생목록").
- `snippet.publishedAt` = **재생목록에 추가된 시각**, `contentDetails.videoPublishedAt` = 영상 게시 시각(2017-03 추가).
- **문서는 다음을 말하지 않는다**: 정렬 기준, 예정/라이브 영상 포함 여부, 비공개·삭제 영상 처리, 반영 지연/캐시. → 라이브 예정·라이브 중 감지는 **문서로 보장되지 않으며 실측으로만 확인된 동작**이다(향후 변경 위험).
- 변경 이력에 RSS 폐지 공지는 없음(조회한 앞 10만 자 기준). 2026-06-01 부터 `search.list` 는 별도 쿼터 버킷(기본 한도·호출당 비용은 문서에 미기재 → 현재 쓰는 `search_live` 쿼터 계산 재확인 필요).

**실측 결과** (우리 5채널 + 그룹 + 외부 24시간 라이브 채널 Lofi Girl, 각 최근 50건을 `videos.list` 로 상태 대조)
| 상태 | 재생목록에 나타나는가 | 근거 |
|---|---|---|
| 라이브 예정(`upcoming`) | **나타남** | 아라레(예정 시작 12-24, 재생목록 위치 20번째), 리츠(위치 0), 미야코(위치 1), Lofi Girl 1건 — 모두 `privacyStatus: public` |
| 라이브 중(`live`) | **나타남** | Lofi Girl 5건이 `live` 로 재생목록에 포함(상시 라이브 채널이라 우리 채널 사례는 아님) |
| 종료(`none`) | 나타남 | 그 외 전부 |
- `videos.list` 로 상태(`liveBroadcastContent`)·예정/실제 시작 시각(`liveStreamingDetails`)을 읽는 후속 단계는 RSS 때와 같다. 재생목록은 **발견(ID)** 만 한다.
- **주의 1 — 위치**: 예정 영상은 **생성 시각** 기준 위치에 있다(아라레 12-24 예정은 08-29 생성 → 20번째). 라이브가 시작되면 `snippet.publishedAt` 이 **실제 시작 시각**으로 바뀐 것으로 보인다(Lofi 예: 영상 게시 12:39 / 재생목록 publishedAt 17:00:26 = actualStart). 즉 오래전에 만든 먼 미래 예약은 새 업로드가 쌓이면 첫 50건 밖으로 밀릴 수 있다 → 신규 발견은 첫 페이지로 충분하지만, 추적 중인 예약은 지금처럼 `videos.list` 로 ID 직접 조회해야 한다(현 구조와 동일).
- **주의 2 — 비공개·회원 전용·삭제**: 이번 표본은 모두 공개. 비공개·회원 전용 예약의 노출은 미확인.
- **주의 3 — 지연**: 새 예약이 만들어진 뒤 재생목록에 나타나기까지의 시간은 문서에도 없고 이번에도 측정하지 못했다(2013년 서드파티 포럼의 "가끔 느리다"는 일화뿐). RSS 대체를 판단하려면 **새 예약 생성 시각 vs 재생목록 첫 등장 시각**을 직접 측정해야 한다.

### 5-2. 틱에서 RSS 를 `playlistItems.list` 로 대체할 수 있는가 (운영자 판단 + 점검, 2026-10-13)

- **구조상 가능**: 틱(10분 주기)은 RSS 를 "후보 영상 ID 목록을 만드는 한 단계"로만 쓴다(`handlers._run` → `fetch_all_rss_video_ids`, 곡 감지 → `songs.fetch_feed_entries`). 상태 판정은 `videos.list` 가 하므로, 이 한 단계를 재생목록 조회로 바꿔도 앞뒤 로직은 그대로다.
  - 예고 감지: 영상 ID 목록만 필요 → 재생목록이 같은 형식으로 제공.
  - 음반 감지: 영상 ID·제목·게시 시각·설명이 필요 → 곡 토픽 채널에서 RSS 와 값이 일치함을 확인(2026-10-13 16:03, 최신 3건 비교).
  - 업로드 재생목록 ID 는 채널 ID 의 `UC` → `UU` 치환(6채널 모두 조회 성공). 쿼터는 틱당 6 units(하루 약 864).
- **장점**: RSS 와 달리 공식 API 라 폐지 위험이 작고 오류 응답이 명확하다(지금 RSS 는 404 원인 불명).
- **도입 전 확인 항목 (미확인)**: ① 새 예약이 생긴 뒤 재생목록에 나타나기까지의 지연(10분 주기에 충분한가), ② 한국 시간 낮(08~16시)에도 정상인가, ③ 회원 전용·비공개 예약의 노출 여부.
- **도입 방식 제안**: 재생목록을 먼저, RSS 를 보조로 두고 후보 ID 를 합집합으로 쓰면서 양쪽 결과 차이를 로그로 남겨 누락 여부를 검증한 뒤 RSS 를 걷어낸다.
- **현재 결정**: 도입은 **보류**(코드 변경 없음). 위 확인 항목은 새 예약 생성 시각과 한국 시간 낮 시간대의 직접 측정이 필요하다.

## 6. 권고와 현재 결정

- **현재 결정(2026-10-13, 운영자)**: PubSub 전환·폴링 방식 추가 개선은 **보류하고 관찰**한다. 이미 반영된 것: 재시도(1·3초) + 지속 실패 채널 휴지(10/30/60분) + WARN 시간당 1회 + 채널별 1분 시차 폴러(v4.3-fullauto).
