## 0. 용어 주의
- **WebSub(PubSubHubbub)** = 허브(`pubsubhubbub.appspot.com`)가 우리가 준 HTTPS 주소로 **POST** 하는 웹훅. 웹소켓 아님(연결 유지 없음).
- GCP 의 **Cloud Pub/Sub 과는 다른 서비스**다. 이름만 비슷하다.
- 비교 대상 "폴링" = 배포판(Cloud Run `mewtype-backend`)의 10분 틱 RSS + `videos.list`, 그리고 상태별 Cloud Tasks `wake`. 로컬 러너(`v4.3-fullauto`, 이 PC)는 어제 17:20 경 절전으로 멈췄다가 오늘 09:08 재시작해서 **비교 대상이 아니다**.

## 1. 다시 돌리는 법 (결과 재현)
```
cd mewtype-scheduler/ref/pubsub_probe        # 메인 폴더 ref (v43 worktree 에는 없음, 미커밋)
python -X utf8 compare.py                    # 기본 2026-10-13 ~ 10-16 이벤트 파일
python -X utf8 compare.py 2026-10-14 2026-10-15
```
- 입력: `pubsub_probe.log`(PubSub `notify`) + `gh api` 로 `sbb2002/mewtype-scheduler-data` 의 **`monitoring` 브랜치** `monitoring/events-<날짜>.jsonl`(배포판 이벤트, `flow=preview` 전이). `gh` 로그인(읽기)만 필요.
- 이벤트 파일 날짜는 **KST 06:00 경계**(06:00~익일 06:00)라 10-15 09:00 까지 보려면 `2026-10-14`, `2026-10-15` 두 파일이 모두 필요하다.
- Cloud Logging 의 `Failed to fetch RSS` 경고(낮 시간대 RSS 실패)는 별도: `gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="mewtype-backend" AND textPayload:"Failed to fetch RSS" AND timestamp>=… AND timestamp<…'` 후 KST 시 단위로 센다(어제 14시 28건 · 15시 30건 · 16시 5건 · 17시 이후 0건).
- 시험기 상태 확인: `Get-CimInstance Win32_Process | ? CommandLine -match pubsub_probe` (현재 PID 3500, 기한 1408분). 끝나면 로그에 `kind:"end"` 줄. **끝난 뒤 `ngrok.exe` 를 직접 종료**(`Stop-Process -Id <PID>`, 구독기가 끝나도 안 꺼짐).
- 시험 기간 중 **PC 절전 금지**(절전이면 구독기 · 터널 멈춤). 중간에 멈췄는지는 `pubsub_probe.log` 의 `start`/`end` 줄과 `notify` 공백으로 본다.

## 5. GCP(Cloud Run 배포판)에서 받는 설계안 — 미구현
**가능 여부**: 가능. 필요한 것은 인터넷에서 닿는 공개 HTTPS 주소뿐이고 Cloud Run 이 이미 제공한다. 이 PC 용 ngrok 은 불필요해진다.
- **위치**: `mewtype-telegram`(이미 인증 없이 열린 공개 서비스)에 콜백 라우트를 얹는 것이 가장 가깝다. 메인 `mewtype-backend` 는 OIDC 인증이라 허브가 직접 호출할 수 없다. (대안: 콜백 전용 소형 서비스. v3.9 교훈상 `max-instances=1` 로 429 가 나는 서비스와 분리하는 편이 안전.)
- **GET 검증**: `hub.challenge` 를 그대로 돌려줘야 한다(시험기 `do_GET` 참고). `hub.topic` 이 우리 채널인지 확인.
- **POST 알림**: 본문(Atom)을 **신뢰하지 않고** `yt:videoId` 만 뽑아 기존 판정 경로(`videos.list` → reconcile 또는 `/wake` 계열 enqueue)에 태우고 즉시 2xx(204) 응답. 중복 알림은 영상 ID 로 흡수.
- **인증**: 구독 시 `hub.secret` 을 주고 알림의 `X-Hub-Signature` 를 HMAC 으로 검증(시험기의 경로 비밀보다 낫다). 비밀은 Secret Manager. 서명 헤더가 실제로 오는지는 **시험기에서 확인한 적 없음** — 시험기 로그는 헤더를 기록하지 않았다(도입 전에 헤더 포함 기록으로 한 번 확인 필요).
- **재구독**: 임대(시험 요청값 432000초=5일, 수락됨) 만료 전에 Cloud Scheduler 잡으로 재구독. 허브가 허용하는 최대 임대는 이 시험에서 확인하지 않음.
- **구독 대상**: 5명 + 곡 토픽 채널(`topic:topic`). 그룹 공식 채널은 RSS 에서 이미 제외(노래 영상이 합동 방송으로 올라오는 문제)라 같은 규칙을 따라야 한다 — 구독은 되지만 처리 단계에서 개인 채널과 동일 규칙을 적용할 것(근거 규칙 · 프리미어 규칙 유지).
- **로컬 러너(v4a/v4.3 시험판)**: 인바운드 불가(Tailscale 폰 알림만) 라서 이 설계는 **배포판 전용**. 로컬 러너에 쓰려면 ngrok 같은 터널이 계속 필요.
- 이 설계에서 **검증되지 않은 가정**: 허브의 재시도 정책(전달 실패 시 재시도한다고 알고 있으나 시험하지 않음), 서명 헤더 형식, 최대 임대, Cloud Run 콜드스타트 시 허브 타임아웃 여부.
