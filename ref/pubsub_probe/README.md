# PubSubHubbub(WebSub) 구독 시험 — YouTube 채널 피드가 푸시로 내려오는지 확인

앱과 별개의 시험기다. 앱의 RSS 폴링이 이 PC 에서 404·500 으로 거의 막혀(2026-10-13 직접 조회: 36회 중 2회 성공) 푸시 방식이 대안이 될 수 있는지 본다.

> **결과 비교 · 판단 · 도입 설계안은 `PUBSUB_VS_POLLING.md`**, 비교표 재생성은 `python -X utf8 compare.py`. 시험 종료 후 다른 세션은 그 문서 §3 체크리스트부터.

## 파일
| 파일 | 내용 |
|---|---|
| `pubsub_probe.py` | 시험기. 허브(`pubsubhubbub.appspot.com`)에 7개 채널을 구독하고, 허브의 검증(GET)·알림(POST)을 받아 기록 |
| `pubsub_probe.log` | 기록. 한 줄 = JSON 하나. `kind` = `start` · `subscribe` · `verify` · `notify` · `end` |
| `probe.out` | 화면 출력 사본(같은 내용) |

## 지금까지 확인된 것
- 7개 채널 구독 요청 전부 HTTP 202, 허브 검증(GET)도 7개 모두 통과. 구독 경로 자체는 정상.
- 푸시 알림(`notify`)은 **아직 미확인** — 채널에 이벤트가 있어야 온다.

## 확인할 것 (로그가 찬 뒤)
1. `notify` 가 채널별로 몇 건 찍혔는가. 0건이면 그동안 해당 채널에 이벤트(아래)가 없었는지 먼저 확인.
2. 알림이 온 시각 vs 실제 이벤트 시각(영상 게시·예약 생성) 차이 = **지연**. RSS 폴링(최대 10분)보다 빠른가.
3. 어떤 이벤트에 알림이 오는가:
   - 새 영상 공개 / 프리미어 예약 / **라이브 예약 생성**(방송 예고의 핵심 — 앱이 RSS 에서 `upcoming` 을 발견하는 경로)
   - 제목·설명 수정 (예약 시각 변경은 알림이 오는지)
   - 영상 삭제 (삭제 항목 형태)
   - **라이브 시작·종료**는 항목 변화가 없어 안 올 것으로 예상 — 실제로 안 오는지 확인
4. 같은 시간대 RSS(`/feeds/videos.xml`)가 404 였을 때도 푸시는 왔는가 (= 푸시가 RSS 제한과 무관한지).
5. 알림 본문(`body`)에서 영상 ID(`yt:videoId`)·게시 시각·제목이 오는가 → 앱의 `videos.list` 후보로 바로 쓸 수 있는지.
6. 중복·누락: 같은 영상 알림이 여러 번 오는가, 방송 예약이 있었는데 알림이 없었던 적이 있는가.

## 앱에 도입하려면 (결과가 좋을 때)
- 영구적인 공개 콜백 URL 이 필요(이 PC 는 인바운드 불가 → ngrok 고정 주소/터널 상시 구동, 또는 별도 수신 지점).
- 구독 임대(최대 5일)마다 재구독, 콜백 비밀 경로 유지(재시작해도 같은 구독을 쓰려면 비밀을 저장).
- 알림 본문은 신뢰할 수 없는 입력 — 영상 ID 만 뽑아 기존 `videos.list` 판정에 태울 것(본문 내용 그대로 믿지 않기).
- 허브 검증은 `hub.challenge` 를 그대로 돌려줘야 하고, 알림은 빠르게 2xx 로 응답해야 한다.
