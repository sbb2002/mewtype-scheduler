## 3. 구현 후 — 한 번의 「소식 이해」 호출 + 한 번의 결정

### 3-1. 순서

```
[코드] ① 사전 계산 — 가상 병합(URL · 원문 제목 일치 + 날짜 규칙 F5 일부) · 같은 날짜 기존 소식 목록(중복 후보, 최대 8건)
[LLM ] ② 소식 이해(llm.notice_understand) 1회 — 주제 · 분류(분류마다 예/아니오 + 근거) · 공연 이름 · 공연일(+근거) ·
         시점(알림/보고 · 그 일 날짜 · 다음 일정 줄 + 그 줄의 분류 · 제목) · 제목(원문 · 한글) · 같은 소식(후보가 있을 때만, 후보 id + 근거)
[코드] ③ 결정 1회 — 근거 검사(항목마다: 근거가 원문에 없으면 그 항목만 버림) → 분류 확정 → 라이브공연이면 그대로 올림 /
         아니면 시점 규칙(F4) → 병합 대상 확정(F5: 가상 병합 결과 · LLM 중복 후보 중 공연 이름이 다르면 별개) →
         지난 날짜 새 글 버림 · 보관함 흡수는 라이브공연이면 건너뜀(F3) → 만료(라이브공연 소감 = 표시 기간, 결정 대기)
[LLM ] ④ 본문 번역 — 올라가거나 본문이 바뀌는 줄만(지금 그대로, 번역 전용 처리 유지)
[코드] ⑤ 저장
```
- **Groq 호출: 새 소식 1건 = 2회**(이해 1 + 본문 번역 1). 이미 본 트윗 = 0회. 판정 기록 · 다시 판정은 아래 3-4.
- **로직 단계: 5 ~ 13 의 9단계 → 4단계**(사전 계산 · 이해 · 결정 · 본문 번역).
- 본문 번역을 이해 호출에 넣지 않는 이유(기능 > 호출 수): 지금 번역에는 용어 가림(`_mask_glossary`) · 멤버 이름 표 · 「일본어 글자 남기지 않기」 검사와 다시 묻기(v4.2.4 · v4.5.7)가 붙어 있고,
  이해 호출의 출력이 길어지면 판정 품질 · 토큰이 같이 흔들린다. 번역이 필요 없는 줄(이미 본 글 · 안 올림)에서는 지금처럼 안 부른다.

### 3-2. `llm.notice_understand` — 프롬프트 · 응답

- **프롬프트** = 세 덩어리를 한 글에 대해:
  1. 분류 — 5차 프롬프트(ROUND5_PLAN §1-1, 운영자 답 반영: 소감도 live · 「방송·영상」)의 정의 · 「일부러 더 고르지 말 것」 · 분류마다 예/아니오 + 근거.
  2. 공연 — 라이브공연이 예일 때만: 공연 이름(「」 안 타이틀, 멤버 솔로 공연 포함 — v4.7.1 문구) · 공연일(티켓 · 통판 날짜 아님) + 근거 줄.
  3. 시점 — 지금 `llm.notice_timing` 의 규칙 문장 그대로(알림/보고 · 그 일 날짜 · 다음 일정 줄). 라이브공연이 예이면 「시점은 비워도 된다」(출력 줄임).
     다음 일정 줄이 있으면 그 줄의 분류(예/아니오) · 제목도 — 「다음 일정만」 으로 잘릴 때 다시 부르지 않으려고.
  4. 제목 — 지금 `llm.notice_title` 규칙(짧은 제목 1줄 · 고유명사 보존 · 용어 토큰 그대로).
  5. 같은 소식 — 후보 목록이 있을 때만 붙인다: 「후보 중 이 글과 **같은 행사 · 같은 공연**인 것의 id, 없으면 ""」 + 근거.
- **응답 스키마**(json_schema strict) = `{subject, cats:{live,event,goods,broadcast:{yes,evidence}}, live:{name,name_evidence,date,date_evidence},
  timing:{kind,subject_date,evidence[],next_lines[],next_cats:[],next_title_ja,next_title_ko}, title_ja, title_ko, dup:{id,reason}, reason}`.
- **검사 · 다시 묻기**: JSON · 스키마가 깨졌을 때만 다시 묻는다(최대 2회). 근거가 원문에 없는 항목은 **그 항목만 버린다**(분류 하나 · 공연 이름 · 공연일 · 같은 소식) — 응답 전체를 버리지 않으므로 다시 묻기가 거의 없다.
  시점은 지금처럼 근거 필수 — 근거가 없으면 시점만 「판정 실패」 로 보고 F4 의 「올리고 기록」.
- 재판단 힌트(`_with_hint`)는 지금처럼 앞에 붙인다.

### 3-3. 결정 규칙(코드) — `_decide_notice`(새 함수, `_prepare_notice` 안)

1. 분류 = 운영자 지정 > 게임 계정 = Our Notes > 리포스트 = 기타 > 이해 결과(근거 있는 예) > 하나도 없으면 기타 > 호출 실패면 없음(옛 분류 바꿔 읽기 + `needs_cat`).
2. **라이브공연이면** → 올림(시점 무시, 다음 일정 줄 포함 글 전체) · 공연 이름 · 공연일 붙임.
3. **아니면** 시점(운영자 지정 `_review_forced("notice_timing")` 이 있으면 그것) → `notices.timing_decision` 그대로. 「다음 일정만」 이면 내용 · 분류 · 제목을 next 것으로(이해 결과에 이미 있음 — 다시 안 부름).
   기록 · 되돌리기(`_llm_record(kind="notice_timing")`)는 지금 그대로.
4. 병합 대상: 가상 병합(F5 날짜 규칙 포함)이 고른 기존 소식 → 공연 이름이 둘 다 있고 다르면 별개. 가상 병합이 새 소식이면 이해 결과의 `dup.id`(운영자 지정 `dup_id` 우선) → 그 소식과 공연 이름이 다르면 별개.
   기록(`kind="duplicate_notice"`, 병합 전 스냅샷 되돌리기)은 지금 그대로.
5. 지난 날짜의 새 글 · 보관함 같은 소식: 라이브공연이면 버리지 않고 새 소식으로(F3). 만료 = 라이브공연 소감은 **표시 기간(결정 대기)**, 그 밖은 지금 그대로.

### 3-4. 다른 경로 · 기능에 주는 영향(같은 `_prepare_notice` 를 쓰는 곳)

| 경로 | 바뀜 |
|---|---|
| 게임 계정 글(게임 밖 행사 → 소식) | 분류는 지금처럼 Our Notes(코드). 이해 호출은 시점 · 제목 · 같은 소식을 위해 부른다(분류 칸은 무시). 출연진 OCR 은 그대로 따로 |
| 멤버 글(유튜브가 아닌 URL → 소식) | 공식 글과 같은 새 흐름 |
| 관리 페이지 원문 투입 미리보기(`timing="show"`) | 이해 1회 — 미리보기에 분류 · 시점 · 공연 이름 표시. 확정(`timing="off"`)은 미리보기 결과를 그대로 올림(지금 v4.7.0 처럼) |
| 텔레그램 수동 투입(`timing="off"`) | 시점은 쓰지 않음(지금 그대로), 분류 · 제목 · 같은 소식은 이해 결과 |
| LLM 판단 반려 · 재판단(`_run_notice_timing` · `_run_notice`) | 같은 글로 `_maybe_auto_notice` 를 다시 돌리는 방식 그대로 — 강제 값만 3-3 의 3 · 4 에서 읽는다 |
| 정기 수집의 다시 판정(A5, 새) | `needs_cat` 인 줄만 이해 호출 1회 — 분류 · 공연 이름만 반영(시점 · 병합은 다시 안 함) |
| `llm.notice_timing` · `notice_categories` · `live_info` · `notice_title` · `duplicate_notice` | **지우지 않는다** — 다른 곳(번역 sweep 의 제목 · 행사 배너 · 시험 스크립트)이 쓰거나 비교 기준으로 남긴다. 소식 준비에서만 안 부른다 |
| 예고 · 행사 배너 · 개인 트윗 · 프론트 · 저장 형식 | 바뀌지 않음(프론트는 A6 「방송·영상」 이름만) |

### 3-5. 병합 규칙 코드(F5)

- `notices._same_group(a, b)`: URL 같음 → 같은 소식(지금 그대로). 원문 제목 같음 → **두 줄의 날짜가 다르면 별개**. 그 뒤 공연 이름 검사는 결정 단계(이해 결과가 있어야 함)에서.
- `notices.merge_into` 호출부(`_commit_notice`): LLM 이 고른 기존 소식과 공연 이름이 다르면 합치지 않고 새 소식으로.
- 확인: 보관함 `nd9f0821858f4ac9`(RESONEXT + 근트레이닝부)가 새 규칙에서 별개로 남는지 self-test 로.

## 4. 시험(내일 5차와 묶음)

- 5차 = **이 이해 프롬프트 자체**로 돌린다(분류 부분을 두 데이터셋 · 2 · 3 · 4차와 같은 채점으로 비교 — ROUND5_PLAN §2). 분류만 따로 시험한 프롬프트를 나중에 이해 호출로 옮기면 결과가 달라질 수 있어서.
- 시점 부분은 정답표가 없다 → 같은 글에 대해 지금 `llm.notice_timing` 결과와 얼마나 같은지(일치율) + 다른 것만 운영자가 확인. 공연 이름은 라이브공연 글에서 근거 검사 통과율 · 같은 공연끼리 같은 이름이 나오는지.
- 비용 어림: 65건(36 + 29)을 9건 묶음으로 → 8요청, 출력이 4차보다 길어 **약 4만 토큰(추정)**. 남길 4만 규칙으로 하루에 가능.
- 운영 코드는 글 하나씩 부르므로, 채택 뒤 시험 브랜치에서 실제 글 몇 건으로 한 건씩 호출 확인(약 3천 토큰 × 5건).

## 5. 구현 순서(시험 브랜치 `test/notice-r5`)

1. `notices._same_group` 날짜 규칙 · 결정 단계 공연 이름 검사 · 지난 날짜 / 보관함 라이브공연 예외(코드, self-test)
2. `llm.notice_understand` + 스키마 + 근거 항목별 검사(가짜 응답 self-test)
3. `_prepare_notice` 5 ~ 13단계를 사전 계산 → 이해 → 결정 → 본문 번역으로 교체, 강제 값 · 기록 유지(가짜 LLM 으로 준비 → 저장 경로)
4. `needs_cat` 다시 판정(정기 수집) · 「방송·영상」 이름
5. 5차 결과로 프롬프트 확정 → 실제 Groq 로 한 건씩 확인 → PR(병합 · 배포는 운영자 결정)

## 6. 운영자 결정(10-23 2차) — 시점 판정은 Groq 없이 코드로 · 라이브공연 유지 기간

**결정**
- **라이브공연 관련 소식은 그 공연의 공연일 다음 날 자정(공연일 + 1일 24:00 KST = 공연일 + 2일 00:00)까지 유지**한다 — 티켓 · 굿즈 안내처럼 공연 전에 올라온 소식도 공연이 끝날 때까지 묶음에 남는다.
  (해석 — 「당일날 + 1일 자정」 을 공연 다음 날이 끝나는 시각으로 읽었다. 공연 당일 24:00 이면 알려 주실 것.)
- **그 기간 안에 온 소감 · 보고는 라이브공연에, 기간이 지난 뒤 온 소감은 기타로** 올린다.
- **시점 판정은 Groq 를 쓰지 않고 코드로** — 판정 시각(KST)과 글에 적힌 날짜 · 시각(KST)을 비교한다. → 소식 이해 호출에서 시점 칸을 뺀다(출력이 줄어든다).

**코드 시점 판정 — 규칙(초안)**: 글에 적힌 날짜 · 시각을 모두 뽑는다(월/일 · 연도 · 「本日 · 今日 · 今夜 · 明日」 · 시각만 있으면 오늘 · 24시 넘는 표기는 다음 날 · 「A〜B」 기간은 B · 「〜まで」 는 그 날).
하나라도 판정 날짜 이후 → 「앞으로」(올림), 오늘이 있으면 → 「오늘」(오늘 자정까지), 모두 지났으면 → 「지난 일」(라이브공연이 아니면 안 올림). 라이브공연은 위 유지 기간 규칙이 먼저.

**점검 — 실제 소식 129건(정답표 데이터, 판정 시각 = 트윗 게시 시각)**: 앞으로 74 · 오늘 23 · 날짜 없음 29(시각만 · 本日 등 — 소식 파서가 오늘로 둔다) · **지난 일 0** — 올라간 소식을 잘못 버리는 일은 없었다(`timing_sim.py`).
다만 이 129건은 이미 올라간 글뿐이라 「버려야 할 소감을 코드가 통과시키는」 쪽은 이 데이터로 잴 수 없다(LLM 시점 판정 기록 = 운영 ops `llm_actions.json` 에 0건).

**문제 될 수 있는 경우(코드 판정)**

| # | 경우 | 코드 판정 결과 | 대응(제안) |
|---|---|---|---|
| T1 | **감사 + 다음 일정**(「ご参加ありがとう … 次回は10/4」) | 미래 날짜가 있어 「앞으로」 → **글 전체**가 올라간다(v4.6.3 은 다음 일정 줄만) | 받아들임(감사 문구가 같이 보임) 또는 「미래 날짜가 든 줄부터」 만 남기는 코드 잘라내기 — 결정 필요 |

**바뀌는 계획**: §3 의 「소식 이해」 에서 시점 칸(kind · subject_date · next_lines · next_cats · next_title) 제거 → `notices.timing_by_code`(새, 순수 함수) · 라이브공연 유지 기간 · 기간 뒤 소감 = 기타.
Groq 호출 수는 그대로(이해 1 + 본문 번역 1)이고 출력이 줄어든다. LLM 판단 기록 `notice_timing` 은 코드 판정이 「안 올림」 일 때 「코드 판정」 으로 남겨 반려 · 사용자 판단(「소식으로 올림」)은 지금처럼 쓸 수 있게 한다.

**운영자 답(10-23 3차)**
- **T1** = 감사 + 다음 일정 글은 **내용 전체를 올린다**(잘라내지 않음 — v4.6.3 의 「다음 일정 줄만」 은 쓰지 않는다).
- **T6** = 판정 기준 시각 = **트윗 게시 시각**(tweet id 로 계산, 없으면 처리 시각).
- **T9** = 라이브공연 유지 기간을 **공연일 + 7일(그날 24:00 KST)** 까지로 늘린다 — 최대한 라이브공연으로 담기 위해. 그 안에 온 소감 · 보고 = 라이브공연, 그 뒤 = 기타.
  기간 뒤 기타로 간 소감의 표시 기간은 따로 정하지 않아 **게시일 24:00 까지**로 둔다(제안 — 바꾸려면 알려 줄 것).
- T2 · T3 · T4 · T8 은 표의 대응대로 구현한다.

**확정된 시점 · 유지 규칙(구현 기준)**
1. 기준 시각 = 트윗 게시 시각(KST).
2. 라이브공연(공연일을 앎): 기준 날짜 ≤ 공연일 + 7일 → 라이브공연으로 올림(글 전체), 만료 = 공연일 + 7일 24:00. 그 뒤 → 분류를 기타로 바꿔 올림, 만료 = 게시일 24:00.
3. 그 밖(라이브공연인데 공연일을 모름 포함): 글의 날짜 · 시각(本日 · 明日 · 시각만 = 오늘, 昨日 · 昨夜 · 先日 = 지난 날, 「N年前」 = 지난 일, A〜B = B, 〜まで = 그 날,
   開催中 · 発売中 · 販売中 · 放送中 · 公開中 = 오늘 이상)이 하나라도 기준 날짜 이후 → 올림(글 전체), 오늘만 → 게시일 24:00 까지, 모두 지남 → 안 올림(코드 판정 기록 · 반려 가능).
