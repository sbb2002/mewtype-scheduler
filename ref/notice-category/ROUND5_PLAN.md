## 1. 5차 프롬프트 — 설계 원칙

1. **주제를 먼저 한 줄로 쓰게 한다(subject).** 분류는 그 주제에서 나온다. 본문에 곁들여 나온 단어(「当日グッズ情報も」 · 생중계 언급 · 영상 언급)로는 붙이지 않는다 —
   검증 세트의 잘못 붙임(#78 동시 시청 → live, #83 라이브 정보 → goods, #100 공연장 CD → live, #70 · #77 영상 → goods)이 이 유형.
2. **분류마다 따로 예/아니오 + 근거 한 줄.** 「여럿 골라라」 고 유도하지 않는다. 근거 줄이 원문에 없으면 그 분류만 버린다(코드).
3. **예시는 특정 글이 아니라 규칙 문장, 「포함」 과 「아님」 을 짝지어.** 한쪽으로 밀지 않게.
4. **시험 글을 프롬프트에 넣지 않는다.** 정의 줄 일부는 운영자 정답(검증 세트)의 판단 기준을 옮긴 것이다(아래 표) — 그만큼 검증 세트 점수가 유리해질 수 있다는 점을 결과 해석 때 감안한다.

### 1-1. 시험용 프롬프트(9건 묶음 — 2 · 3 · 4차와 같은 조건)

스크립트 `notice_cat_exp.py` 의 `HEAD_C`. 응답 스키마 = 글마다 `{n, subject, live:{yes, evidence}, event:{…}, goods:{…}, broadcast:{…}, reason}`(json_schema strict).

```
아래는 X(트위터) 글 여러 개다. 각 글은 성우 밴드 「夢限大みゅーたいぷ」(유메미타 — 仲町あられ · 宮永ののか · 峰月律 · 藤都子 · 千石ユノ) 관련 글이다.
글마다 아래 두 단계를 따라라.
1단계 — subject: 이 글이 팬에게 알리는 것을 한국어 한 줄로 적어라(무엇을 · 언제). 글에 곁들여 언급된 것은 넣지 않는다.
2단계 — 아래 네 분류마다 「이 글이 그것 자체를 알리는가」를 따로 판단해 yes(true/false)와 근거 한 줄(evidence — 원문 그대로 복사, no 면 "")을 적어라.
여러 개가 yes 일 수 있지만, 일부러 더 고르지 말 것. 곁들인 언급(「当日グッズ情報も」 같은 한 줄)만으로는 yes 가 아니다 — 그 내용 자체를 안내하면 yes.
- live (라이브공연): 유메미타 전체 · 일부 · 멤버 솔로가 무대에 서는 공연. 그 공연의 티켓 · 추첨 · 아카이브 시청권 판매 · 개장 · 변경 안내, 공연 회장 안의 부대 안내, 공연이 끝난 뒤의 감사 · 소감 · 현장 보고 · 세트리스트 포함. 아님: 공연 영상을 다 같이 보는 동시 시청 방송(→ broadcast).
- event (오프라인행사): 공연이 아닌, 멤버가 나오는 오프라인 행사 — 사인회 · お渡し会 · 릴리즈 이벤트 · 토크쇼 · 팬 이벤트 · 전시 · 콜라보 매장. 아님: 「ライブ」 공연, 온라인 사인회의 생중계 자체(→ broadcast).
- goods (음원·굿즈): 판매 · 발매 · 예약 · 특전이 이 글의 안내 대상인 물건 — CD · 음원 · 커버곡 · 굿즈 · Blu-ray · 잡지 · 코믹스. 아님: 영상 · MV 공개 자체(판매가 아님), 행사 · 공연 안내 속 한 줄 언급.
- broadcast (방송·영상): 멤버가 출연하거나 직접 하는 방송 · 영상 — 유튜브 생방송 · 프리미어 · 동시 시청, 「バンドリ！TV LIVE」, 라디오 · TV 출연, 행사 · 공연의 생중계. 아님: 애니메이션 「ゆめ∞みた」 방영 · 재방송 안내(멤버 출연이 아님).
reason = 판단 이유 한국어 한 문장. 결과는 글 번호(n)마다 하나씩. JSON 으로만 답하라.
```

**응답 → 분류 목록(코드, `_cats_c`)**: `yes` 이고 근거 줄이 원문(제목 + 본문)에 있는(공백 무시 · NFKC · 2자 이상) 분류만. 하나도 없으면 기타.
운영 코드에 넣을 때도 같은 규칙(아래 §3 P3).

### 1-2. 운영 코드에 넣을 때(글 하나용)

첫 줄을 「아래는 X(트위터) 글이다. 이 글은 … 관련 글이다.」, 「글마다」 → 「이 글에 대해」, 마지막 줄의 「결과는 글 번호(n)마다 하나씩」 을 뺀다(4차를 옮길 때와 같은 방식, v4.7.0 `NOTICE_CAT_PROMPT`).
응답 스키마는 `n` 만 빠진 같은 모양. `llm.notice_categories` 의 반환(분류 목록)은 그대로라 호출부 · 저장 형식은 안 바뀐다.

## 4. 운영자 답(10-23)과 남은 질문

- **소감 소식도 라이브공연** — 분류뿐 아니라 「지난 일의 소감이면 소식으로 안 올림」(v4.6.2 시점 판정)도 라이브공연은 예외로 바꿔야 한다(§5 A3).
- **「방송」 → 「방송·영상」** — 화면 · 관리 페이지 · 문서의 이름만(값 `broadcast` 그대로).
- **P5(병합 때 분류 합치기)는 보류.** 대신 **공연 이름이 다른 소식은 합치지 않는다**(운영자 요구, §5 A4). 원인 조사(10-23, 데이터): 아카이브 `nd9f0821858f4ac9` 에 RESONEXT 글과
  근트레이닝부(筋トレ部) 글이 한 줄로 합쳐져 있다(한글 제목은 RESONEXT · 본문은 筋トレ部). 두 글의 원문 제목이 똑같이 「チケット一般発売開始」 —
  `notices.merge_notice` 의 「URL 일치 **또는 제목 일치**면 같은 소식」 규칙에 걸린 것으로 보인다(**추정** — 제목 외 다른 일치 근거는 못 찾음).
- **채택 기준**은 §2 그대로(운영자 확정).

남은 질문: ① #100 공연장 CD 판매 = goods 만? ② #120 애니메 이벤트 토크쇼 출연 = broadcast? ③ #64 · #70 발매 기념 생방송 = broadcast 만? ④ P5.

## 5. 새 요구에 맞춘 구현 범위(시험 브랜치 — 제안)

5차 프롬프트는 「분류」 만 바꾼다. 10-23 에 생긴 요구(공연별 묶음 · 소감도 라이브공연 · 다른 공연은 합치지 않음)는 분류 밖의 순서 · 병합 규칙에 걸려 있어 함께 고쳐야 한다.

| | 할 것 | 걸린 요구 |
|---|---|---|
| A1 | 분류 프롬프트 = 5차(채택될 때) + 근거 없는 yes 는 그 분류만 버림(P2 · P3) | 분류 정확도 |
| A2 | 공연 이름 = 멤버 솔로 공연 수정(v4.7.1 후보 `3e384d8`) | 공연별 묶음 |
| A3 | **시점 판정의 「지난 일 소감 → 안 올림」 을 라이브공연이면 예외로** — 분류를 시점 결정 **앞**으로 옮겨(LLM 시점 판정은 그대로 부르고, 올릴지 정하는 코드만 분류를 본다) | 소감도 라이브공연 |
| A4 | **병합 막기: 두 소식 모두 공연 이름이 있고 다르면 합치지 않는다**(제목 · URL 이 같아도). 같은 원문 제목만으로 합치는 규칙도 공연 이름 · 날짜가 다르면 막을지 함께 본다 | 다른 공연은 합치지 않음 |
| A5 | 판정 실패 → 다음 정기 수집에서 1회 다시(P4) · 올라가지 않을 글엔 분류 안 부름(P1) | 비용 · 누락 |
| A6 | 「방송」 → 「방송·영상」 이름(프론트 · 관리 페이지 · 문서) | 운영자 결정 |

**한 번의 호출로 합치기(나중 단계)**: 시점 판정 · 분류 · 공연 이름은 모두 「이 글이 무엇을 알리나」 를 묻는다. 한 호출로 합치면 소식 1건 Groq 호출이 3번 → 1번으로 준다.
다만 시점 판정의 품질까지 함께 바뀌어 원인 구분이 어려우므로, A1 ~ A6 을 먼저 시험하고 그 다음 단계로 둔다.
