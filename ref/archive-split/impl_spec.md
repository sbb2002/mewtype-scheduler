## 0. 용어 (구현하면 `docs/TERMINOLOGY.md` 에 올린다)

- **캐시 보관함*** — * 캐시 보관함 = 운영 경로가 늘 읽는 최근분 보관 파일. **파일 이름은 지금 그대로**(`tweet_archive.json` · `notice_archive.json` · `llm_actions.json`) —
  운영 코드의 읽기 · 쓰기 경로를 바꾸지 않으려고(운영자 확정 2026-10-26).
- **일자 보관함*** — * 일자 보관함 = 캐시 보관함에서 기간이 지난 항목을 날짜(KST)별로 옮겨 두는 보존용 파일. `tweet_archive/YYYY-MM-DD.json` ·
  `notice_archive/YYYY-MM-DD.json` · `llm_actions/YYYY-MM-DD.json`. 운영 경로는 읽지 않고, 웹 모니터 지난 날짜 조회 · 분석 · 디버깅만 읽는다.
- **보관함 정리*** — * 보관함 정리 = 하루 한 번(KST 06:10) 캐시 보관함의 오래된 항목을 일자 보관함으로 옮기는 작업.
- 이름 예: 「트윗 캐시 보관함」 · 「트윗 일자 보관함」 · 「소식 캐시 보관함」 … 「LLM 판단 기록 캐시」 · 「LLM 판단 기록 일자 파일」.

## 1. 왜 (2026-10-26 확인한 사실)

- GitHub Contents API 는 **1MB 넘는 파일을 기본 형식으로 읽으면 `content` 를 비워 준다** → `gh_store.read_json`(83줄)이 126줄에서 「No content」 예외.
  `write_json` 도 먼저 읽으므로(157줄 설명) 쓰기도 같이 실패한다.
- 크기 · 증가(2026-10-26):

| 파일 | 크기 | 증가 | 1MB 도달 | 지금 상한 |
|---|---|---|---|---|
| `tweet_archive.json`(data) | 888,969 B · 792건 | 하루 약 19KB | **약 11-03 전후** | 없음 |
| `notice_archive.json`(data) | 250,173 B · 115건 | 하루 약 7.7KB | 2027-01 무렵 | 없음 |
| `llm_actions.json`(ops) | 247,522 B · 209건 | 하루 약 9.5KB(10-26 은 42.7KB) | 300건 상한이라 최악 약 1MB(항목 최대 2.9KB × 300 · 들여쓰기) | 300건(넘는 건 **버림**) |

- 트윗 보관함이 터지면: 개인 트윗 커밋 `_commit_personal_tweet`(2160줄 보관함 읽기)이 전부 실패 → 멤버 트윗 유실(유실 원문 DM · 큐로는 남음).
- 참고(범위 밖): `preview_archive.json` 151KB(data) — 같은 문제가 언젠가 온다. 다음 후보. `monitoring` 브랜치에 남은 옛 `tweet_archive.json`(271KB) ·
  `notice_archive.json`(66KB)은 브랜치를 data 에서 갈라 만들 때 딸려 온 것으로 코드가 읽지 않는다 — 건드리지 않는다.

## 2. 공통 설계

### 2-1. 보관함 정리 (하루 한 번)
- **어디서**: `apply.run_snapshot`(422줄 — 백엔드 `/monitor`, Cloud Scheduler KST 06:10 · 로컬 러너 스냅샷 작업과 같은 코드). 스냅샷 **앞에** 따로 try 로 감싸 실패해도 스냅샷 · DM 은 계속.
  - 일시정지(`control.json` paused)와 **상관없이** 돈다(`run_snapshot` 은 paused 를 안 본다 — 트윗 인입도 paused 와 무관하므로 보관함은 계속 자란다).
  - 백엔드는 `concurrency=1` 이라 이 작업 동안 `/write`(트윗 · 소식 저장)가 기다린다 → **한 번에 쓰는 파일 수를 작게**(아래 상한).
- **새 모듈** `src/backend/archive_rotate.py`(순수 로직 + 저장 호출 얇게):
  - `plan(items, *, key_date, keep)` → (남길 것, {날짜: 옮길 것}) — 순수.
  - `rotate(gh, spec, now_iso)` — 한 대상(트윗 · 소식 · LLM) 정리. 반환 = {moved, files, skipped_days}.
  - self-test: `python -m src.backend.archive_rotate`.
- **순서(잃지 않게)**: ① 캐시를 읽는다(sha) → ② 옮길 항목을 날짜별로 묶는다 → ③ 날짜마다 일자 파일을 읽어(없으면 빈 것) **id 로 합쳐** 쓴다(이미 있는 id 는 그대로 둠) →
  ④ (소식만) 색인 갱신 → ⑤ 캐시에서 옮긴 항목을 빼고 `prev_sha` 로 쓴다. ⑤가 충돌하면 캐시를 다시 읽어 ②부터(③은 id 합치기라 두 번 써도 같음).
  중간에 실패하면 같은 항목이 양쪽에 남을 뿐 잃지 않는다 — 다음 정리 때 캐시에서 빠진다.
- **한 번에 쓰는 일자 파일 상한 = 대상마다 3개**(평소엔 하루치 1~2개). 넘는 날짜는 다음 날로 미룬다(오래된 날짜부터 처리).
  밀린 것(첫 이전)은 정리 작업이 아니라 **1회 이전 스크립트**로(§6) — 정리 작업이 수십 개를 쓰면 그동안 `/write` 가 막혀 트윗 저장이 429 재시도 끝에 실패할 수 있다.
- **크기 안전장치**: 정리 뒤 캐시 직렬화 크기가 **600KB** 를 넘으면, 기간 안이라도 오래된 날짜부터 더 옮긴다(위 3개 상한 안에서). 그래도 넘으면 모니터 `warn` + 운영자 DM.
- **모니터**: `flow="archive"`(새 흐름) 이벤트 1건/대상 — 옮긴 건수 · 쓴 파일 · 캐시 크기. 옮길 것이 없으면 기록하지 않는다. 실패 = `err`.
- **일자 파일 형식**: 캐시와 같은 모양(`{"tweets": [...]}` · `{"notices": [...]}` · `{"items": [...]}`), 직렬화 규칙도 같음(`gh_store._serialize`).
  하루 최대 크기 추정: 트윗 약 80KB(최다일 69건) · 소식 약 23KB · LLM 약 43KB — 1MB 와 거리가 멀다.

### 2-2. 저장 경로 라우팅
- `storage.RoutedStore._pick`(로컬 · 배포 공용): 지금은 `OPS_PATHS` 에 **정확히 같은 이름**만 ops 로 보낸다. `llm_actions/` 로 시작하는 경로도 ops 로 —
  `OPS_PREFIXES = ("llm_actions/",)` 추가. 트윗 · 소식 일자 파일은 data 그대로.
- 로컬 시험판 `LocalStore` 가 하위 폴더(`_local/data/tweet_archive/…`)를 만드는지 구현 때 확인(필요하면 `os.makedirs`).

### 2-3. 날짜(KST) 계산
- 트윗: **게시 시각** — tweet id(Snowflake)에서 계산(`xtweet._TW_EPOCH_MS`). 숫자 id 가 아닌 옛 항목(v2 시절 `p…`)은 `received_at`.
- 소식: **`first_seen`**(처음 받은 시각). 없으면 `archived_at`.
- LLM 판단: **`ts`**.
- 모두 KST 달력 날짜(00:00 경계). 웹 모니터의 하루(06:00 경계)와 다르므로, 지난 날짜 조회는 그날과 다음 날 파일을 함께 읽는다(§3-3 · §4-3).

## 4. 소식 보관함 `notice_archive.json`

### 4-1. 캐시에 남기는 기준
- **보관된 지(`archived_at`) 30일 이내**. 크기 약 230KB 안팎(지금과 거의 같음 — 동작 변화를 최소로).
- 근거 — 운영 경로가 캐시에서 찾는 것:
  - `notices.merge_notice`(137줄): ① 같은 트윗 id 를 본 적 있으면 `dup`(148줄) ② **보관된 소식과 같은 묶음(URL 또는 제목 일치, `_same_group` 70줄)이면
    후속 글로 흡수 `recap`**(162줄) — 지난 행사의 후속 글이 새 소식으로 다시 올라오지 않게.
  - 사용처: `_notice_already_seen`(1887줄) · `_prepare_notice` 중복 사전 계산(1953줄) · `_commit_notice`(2087줄) · 관리 페이지 수동 소식(`admin_api` 1214줄) ·
    소식 시점 판단 반려(5126줄) · 만료 정리(2237줄).
  - `enrich` 지난 소식 본문 번역 백필(92 · 187줄) — 캐시만 백필한다(일자 보관함으로 간 것은 백필 안 함).
- **바뀌는 동작(운영자 확인 필요 §7-1)**: 보관된 지 30일이 지난 소식은 위 ①②에서 안 보인다.
  - 같은 URL · 제목의 새 글이 오면: 날짜가 지난 글이면 지금처럼 `skip`(173줄 — 안 올림), **날짜가 앞으로인 글이면 새 소식으로 올라간다**
    (지금은 몇 달이 지나도 옛 소식에 흡수돼 안 올라간다 — 예: 같은 공연 페이지 URL 로 한참 뒤 새 공지를 내면 지금은 묻힘).
  - 30일 넘은 옛 트윗이 다시 들어오는 일은 관리 페이지 재투입 · 유실 원문 재투입뿐이다.

### 4-2. 색인 `notice_archive/index.json`
- 소식은 웹 모니터 이벤트가 **소식 id · 그 소식이 흡수한 트윗 id(`seen_ids`) · 시각(`first_seen` · `last_updated`)** 으로 찾는다(`monitor_report` 383줄).
  `seen_ids` 의 뒤 트윗이나 `last_updated` 는 `first_seen` 과 날짜가 달라 파일을 계산으로 고를 수 없다 → 색인을 둔다.
- 모양: `{"keys": {"<소식 id | seen id | first_seen | last_updated>": "YYYY-MM-DD", …}}` — 옮길 때 그 소식의 키를 모두 적는다.
- 크기: 소식 1건 키 약 4개 × 약 50B → 1년 약 900건 ≈ 180KB. 5년쯤 뒤 1MB — 그때 연도별로 나눈다(지금은 범위 밖, 문서에 남김).

### 4-3. 웹 모니터
- 지난 날짜 조회에서 소식을 표에서 못 찾으면 색인을 읽어(1회) 해당 일자 파일만 읽는다.

## 5. LLM 판단 기록 `llm_actions.json` (ops)

### 5-1. 캐시에 남기는 기준
- **판단 시각(`ts`) 14일 이내, 그리고 최신 300건까지**(둘 중 더 적은 쪽). 300건을 넘는 오래된 것도 **버리지 않고 일자 파일로**.
- 근거 — 운영 경로가 캐시에서 찾는 것:
  - 관리 페이지 작업 탭 「LLM 판단」 목록(`admin_api.list_llm_actions` 546줄 — 최근 300건) · 흐름 목록(1850줄).
  - 반려 · 재판단 · 사용자 판단 · 되돌리기(`_llm_actions_read` 5027줄을 거쳐 id 로 찾음 — 5657 · 5700줄 등, 갱신 5043 · 5073 · 5292 · 3537줄).
- **바뀌는 동작(운영자 확인 필요 §7-2)**: 14일 지난 판단은 관리 페이지에 안 보이고 반려 · 재판단을 할 수 없다.
  - 지금은 300건 상한이 약 22일치(10-05~10-26)를 덮는다. 14일로 줄이는 이유 = 10-26 하루 42.7KB 처럼 늘면 21일치가 약 900KB 로 1MB 에 붙는다.
    크기 안전장치(600KB)가 있으니 21일로 둘 수도 있다 — 운영자 선택.
  - 지금 300건을 넘으면 오래된 판단이 **사라지는데**, 바뀐 뒤엔 일자 파일에 남는다(되돌리기 데이터 포함 — 읽기 전용).

### 5-2. 바뀌는 코드
- 덧붙이기에서 300건 자르기를 **없앤다** — `telegram_app._llm_record` 쪽 쓰기(5062줄 `items[-_LLM_ACTIONS_MAX:]`) · `handlers` 신곡 판단 기록(319줄).
  자르면 정리 작업 전에 버려지므로. 하루 최대 약 40건이라 다음 정리까지 캐시가 300건을 잠깐 넘는 것은 문제없다.
- `admin_api.list_llm_actions(limit=300)` 은 그대로(최근 300건 표시).
- 보관함 정리에 LLM 대상 추가. 일자 파일은 ops 브랜치(`llm_actions/YYYY-MM-DD.json`, §2-2 라우팅).
