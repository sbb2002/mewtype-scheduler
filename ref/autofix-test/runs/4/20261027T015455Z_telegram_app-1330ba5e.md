### 원인

gh_store.read_json 은 GitHub Contents API 의 content(base64) 필드만 읽는다. 이 API 는 1MB 를 넘는 파일에는 content 를 비우고 encoding='none' 으로 응답한다. 로그의 tweet_archive.json 은 size=1052918(약 1.05MB)로 한도를 넘었고, read_json 이 'No content in response' RuntimeError 를 던졌다. _commit_personal_tweet 의 광범위 except 가 이를 잡아 ERROR 로 기록하고 mode='error' 를 반환했다. 대용량 파일용 폴백(raw media type · blob API · download_url)은 코드에 없다(grep 으로 확인). 아카이브는 계속 커지기만 하므로 일시 오류가 아닌 구조적 결함이다.

### 근거

- src/backend/gh_store.py:122 — resp.json() 에서 content 만 읽고 대용량 대체 경로가 없다

### 서비스 영향 · 빈도

tweet_archive.json 이 1MB 를 넘은 상태라면, 개인 트윗 인입마다 tweets.json 에도 쓰지 못해 팬 화면에 새 트윗 말풍선이 누락된다. 지금까지 1건만 확인됐고 env=local 이라 운영 영향은 확인하지 못했다. 다만 파일이 줄어들지 않으므로 같은 조건의 운영 환경에서는 매 트윗 지속적으로 재발할 것이다. 폴백 없이 기능 출력이 끝까지 나오지 못하므로 ERROR 등급이 맞다.

### 제안 (미적용)

gh_store.read_json 에서 content 가 비고 encoding=='none' 이면 같은 URL 을 Accept: application/vnd.github.raw+json 으로 다시 요청해 본문을 직접 받거나, git blob API(sha 사용)로 읽는다. sha 는 기존 응답 값을 그대로 쓴다. write_json 도 내부에서 read_json 을 쓰므로 같은 수정으로 해결된다. 근본적으로는 tweet_archive.json 이 1MB 를 넘지 않도록 보관 기간 제한이나 월별 분할을 검토한다. 같은 이유로 notice_archive 등 다른 아카이브 파일도 1MB 에 가까워지면 실패하므로 함께 점검한다. 이 단계에서는 변경하지 않는다.
