## 2. 분석 — claude-sonnet-5-5

**판정**: 원인 확정 — tweet_archive.json이 1MB를 넘어 Contents API가 content를 비워 개인 트윗 반영 실패

### 원인

gh_store.read_json은 Contents API 응답의 `content`만 base64 디코딩한다. 로그의 응답은 encoding='none', size=1138183(약 1.1MB)이라 content가 비어 있고, read_json이 "No content in response"로 RuntimeError를 낸다. 이 응답 형태는 GitHub Contents API가 큰 파일에 주는 것으로 알려진 동작이다(이 부분은 로그 값과 외부 지식에 근거하며, 소스로 직접 증명한 것은 아니다). tweet_archive.json이 커져 그 한도를 넘었다. read_json에는 큰 파일용 대체 경로(raw 미디어 타입 또는 Git Blob API)가 없다. _commit_personal_tweet은 같은 try 안에서 아카이브를 읽으므로(2160행) 예외가 바깥 except로 가서 ERROR를 남기고 mode "error"를 반환한다. tweets.json은 이미 읽었어도 write_json 호출 전에 실패하므로 쓰이지 않는다.

### 근거

- src/backend/gh_store.py:122-128 — content가 비면 encoding·size를 담아 RuntimeError를 낸다. 큰 파일(encoding='none')에 대한 대체 읽기 경로가 없다.
- src/backend/telegram_app.py:2160 — _commit_personal_tweet에서 gh.read_json(_TWEET_ARCHIVE_PATH) 호출이 예외를 던진 지점이다.
- src/backend/telegram_app.py:2207-2213 — 예외를 log.exception('personal tweet 반영 실패')으로 기록하고 mode 'error'를 반환한다. 재시도나 폴백 없이 해당 트윗 반영을 포기한다.
- src/backend/telegram_app.py:2025, 2936, 4614, 6185, 6309 — 같은 아카이브를 read_json으로 읽는 다른 호출부가 있어 같은 실패가 퍼질 수 있다.
- logs.json — 트레이스백 메시지에 encoding='none', size=1138183이 찍혀 있다.

### 서비스 영향 · 빈도

로그에는 1건(2026-10-27 02:54Z)만 잡혔다. 그러나 아카이브가 이미 1MB를 넘었으므로 이후 개인 트윗이 들어올 때마다 같은 실패가 되풀이될 가능성이 높다. 실패하면 tweets.json이 갱신되지 않아 해당 멤버의 트윗 말풍선이 팬 화면에서 누락되고, 폴백도 없다. 아카이브를 읽는 다른 기능(삭제, 조회 등)도 영향을 받을 수 있다.

### 제안 (미적용)

1) gh_store.read_json에서 content가 비고 encoding이 'none'이면 `Accept: application/vnd.github.raw+json`으로 다시 GET해 본문을 받거나, 응답의 sha로 Git Blob API(최대 100MB)를 읽는다. 이 경로의 sha는 write_json의 prev_sha 낙관적 동시성에도 그대로 쓴다. 2) 근본적으로는 tweet_archive.json에 보존 기간이나 건수 상한을 둬서 오래된 항목을 잘라내거나 분할한다. 3) 같은 파일을 읽는 다른 호출부(2025, 2936, 4614, 6185, 6309행)도 read_json을 고치면 함께 해결되는지 확인한다.
