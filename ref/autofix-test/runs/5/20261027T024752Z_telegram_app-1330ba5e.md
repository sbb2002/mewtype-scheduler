## 2. 분석 — claude-sonnet-5-5

**판정**: 원인 확정 — tweet_archive.json 이 1MB 초과해 Contents API가 content를 비워 개인 트윗 반영 실패

### 원인

gh_store.read_json 은 GitHub Contents API JSON 응답의 base64 `content` 만 읽는다. Contents API는 1MB를 넘는 파일에 대해 content를 비우고 encoding='none' 으로 응답한다. tweet_archive.json 은 size=1138183(약 1.1MB)으로 한도를 넘었다. 그래서 read_json 이 "No content in response" RuntimeError를 던졌다. _commit_personal_tweet 은 이 예외를 잡아 log.exception(ERROR)을 남기고 mode="error" 를 반환한다. 아카이브가 계속 1MB를 넘는 한 같은 조건에서 반복해 실패하는 구조적 문제다. 일시적 장애가 아니다.

### 근거

- src/backend/gh_store.py:122-128 — content 가 비면 encoding/size 를 담아 RuntimeError 를 던지고, raw 미디어 타입이나 blob API 폴백은 없음
- src/backend/telegram_app.py:2160 — _commit_personal_tweet 이 tweets.json 읽기 직후 gh.read_json(_TWEET_ARCHIVE_PATH) 호출
- src/backend/telegram_app.py:2207-2213 — 예외를 잡아 log.exception("personal tweet 반영 실패") 후 mode=error 반환, tweets.json 쓰기(2188행)에 도달하지 못함
- src/backend/telegram_app.py:2025,2936,4614,6185,6309 — 같은 아카이브를 읽는 다른 호출부도 같은 read_json 을 쓰므로 같은 영향을 받음
- logs.json — RuntimeError: No content in response for tweet_archive.json (encoding='none', size=1138183)

### 서비스 영향 · 빈도

아카이브가 1MB를 넘은 뒤로 개인 트윗(+예고 판정) 인입이 tweets.json 에 반영되지 못해, 해당 트윗이 팬 화면에서 누락될 수 있다. 같은 아카이브를 읽는 다른 경로도 영향을 받을 수 있다. 수신기에는 1건만 잡혔고 24시간 시간대별 집계는 비어 있다. 다만 원인이 파일 크기라서 개인 트윗이 들어올 때마다 재현될 가능성이 높다. 이 호출의 폴백은 mode=error 반환뿐이라 사용자에게 서비스가 제공되지 않는다.

### 제안 (미적용)

1) gh_store.read_json 에서 content 가 비고 encoding=='none' 이면 `Accept: application/vnd.github.raw+json` 으로 같은 URL을 다시 GET해 본문을 받고(sha는 1차 응답 값 사용), 또는 git blob API(`/git/blobs/{sha}`)로 읽는 폴백을 추가한다. 이 방식은 100MB까지 가능하다. write_json 의 PUT 은 1MB 초과여도 가능한지 함께 확인한다. 2) 근본적으로 xtweet 아카이브에 보존 기간이나 건수 상한을 두어 1MB 아래로 유지한다(보수적인 값으로 정한다). 3) 아카이브가 이미 비대하므로, 폴백을 넣은 뒤 트윗 수명 정책에 맞춰 정리하는 데이터 작업을 한다.
