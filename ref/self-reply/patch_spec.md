## 3. 데이터 (계약 I `tweets.json` / `tweet_archive.json`)

- 항목에 **`reply_to_id`**: 같은 멤버 자기 글에 단 답글이면 바로 위 글의 tweet id(문자열), 아니면 `null`. 옛 항목엔 키가 없다(= `null`).
  - 폰 경로: vxtwitter 단건 `replyingTo`(핸들) · `replyingToID` / fxtwitter 폴백 단건 `replying_to` · `replying_to_status` — 핸들이 그 멤버일 때만.
  - 상시 조사: fxtwitter 목록 `replying_to.status` → `vxtwitter.fetch_profile_statuses`(158줄) 반환에 `reply_to_id` 추가.
- **수명**: 지금 `expires_at = 게시 + 48h`(`xtweet.TTL_HOURS` 35줄 · 139줄). 자기 답글을 커밋할 때 같은 커밋에서 **원글(사슬이면 위로 뿌리까지 전부)** 의
  `expires_at = max(지금 값, 원글 게시 + 48h, 답글 게시 + 24h)`. 답글 자신은 게시 + 48h 그대로.
  - 예: 원글 10:00 · 답글 10:05 → 원글 그대로(10:05+24h < 10:00+48h). 원글 10-01 · 답글 10-04 → 원글 10-05 까지.
- 원글이 보관함(`archived_reason` = `expired` · `rolled` · `replaced`)에 있으면 **스레드로 되살린다**(번역 재사용, 보관함 항목은 지움).
  `deleted`(관리 페이지에서 지움)면 되살리지 않고 **답글도 올리지 않는다** — 확인 필요(§7).
- 스레드 상한 `MAX_THREAD = 50`(199줄)은 그대로 — 되살린 원글이 바로 밀려나면(rolled) 이어 붙이기는 원글 없이 단독 표시로 떨어진다(실제로는 한 멤버 50건이 차는 일이 없다).

## 4. 동작

### 4-1. 상시 조사 — 접수 서비스 `POST /gap-check` (1분)
1. 멤버 5명 동시에 `GET /2/profile/<핸들>/statuses?since=<지금 − 30분>`.
   - **5명 모두 204면 바로 끝** — GitHub 읽기 · 쓰기 · LLM · 모니터 기록 없음(대부분의 실행).
   - 매시 정각 실행만 `since` 없이(최근 20건) — 서비스 장애 · 지연 뒤 30분 창을 놓친 것 회복용.
2. 응답이 있으면 `tweets.json` + `tweet_archive.json` 을 읽어 이미 아는 id 를 빼고 후보를 고른다(`xtweet.gap_candidates` 286줄 규칙 — 본인 · 리트윗 아님 ·
   남에게 단 답글 아님 · 48h 안). 바꾸는 점:
   - 개수 상한 3건 → 없앤다(실행 간격이 짧아 한 번에 몰리지 않는다 — 실측 한 멤버 10분 최대 9건).
   - **본인 일반 글은 게시 2분 뒤부터 후보**(폰 알림의 64% 가 2분 안에 온다 — 같은 글을 폰과 동시에 처리하는 일을 줄임). 자기 답글은 바로 후보(폰으로 안 온다).
   - 자기 답글의 원글이 48h 를 넘었어도(목록에 없어도) 답글은 후보 — 원글은 §4-2 가 찾는다.
3. 후보마다 **보충 작업**을 Cloud Tasks 에 적재 — 이름 `gapfill-<트윗 id>`(분 버킷 없이). 이미 같은 이름이 있으면 ALREADY_EXISTS → 건너뜀
   (Cloud Tasks 는 실행 · 삭제된 이름을 약 1시간 다시 못 쓴다 — 문서마다 1h/4h/24h 로 달라 확인 필요. 그 뒤엔 「이미 등록」 검사가 막는다).
4. 조사 자체는 외부 호출 5회 + (가끔) GitHub 읽기 2회뿐이라 1분 안에 끝난다. **번역 · 판정 LLM 은 보충 작업에서만** 돈다.

### 4-2. 보충 작업 — 접수 서비스 `POST /gap-fill` (트윗 1건)
- 새 큐 **`mewtype-gapfill`** — `max-concurrent-dispatches=1`(보충 작업끼리 동시에 안 돎 → 같은 글 두 번 처리 · 쓰기 몰림 방지), 재시도 3회.
1. `tweets.json` 을 다시 읽어 이미 등록이면 끝(폰이 먼저 넣은 경우).
2. 자기 답글이면 원글부터:
   - 원글이 스레드에 있음 → 다음 단계.
   - 보관함에 있음(`deleted` 제외) → 되살림(§3).
   - 어디에도 없음 → `/2/thread/<원글 id>` 로 원글 본문을 받아 **같은 개인 트윗 경로로 먼저 넣는다**(원글이 또 자기 답글이면 뿌리까지 위로).
     원글이 48h 를 넘었어도 넣는다(수명은 §3 규칙으로 답글 게시 + 24h).
3. 그 글을 `_maybe_personal_tweet(..., reply_to_id=...)` 로 — 번역 · 예고 판정 · 변경 판정까지 지금 경로 그대로.
4. 실패하면 200 으로 끝내고 다음 상시 조사가 다시 찾는다(태스크 이름이 막혀 있는 동안은 「이미 적재」로 건너뛰고, 풀리면 다시 적재).

### 4-3. 폰 알림과 겹칠 때 — `_maybe_personal_tweet` 고침
- **커밋 결과가 `dup`(같은 id 가 이미 등록)이고 `via="ingest"` 면 예고 판정 · 변경 판정 · 새 트윗 DM 을 건너뛴다.**
  지금은 `dup` 이어도 판정이 다시 돈다 — 상시 조사가 폰보다 먼저 넣는 일이 잦아지면(폰 알림 36% 가 2분 넘게 걸림) 같은 글을 두 번 판정한다(Groq 두 배 · 중복 DM 위험).
  관리 페이지 수동 경로(`via="ops"`)는 그대로 돈다.
- 준비 단계는 이미 「바뀐 게 없으면 번역 안 함」(`_prepare_personal_tweet` 2044줄) — 둘이 거의 동시에 준비하면 번역만 두 번 될 수 있다(드묾, 허용).
- 폰 알림 뒤의 즉시 보충(`/ingest` 7329줄 `_fill_member_gaps`)은 **없앤다** — 상시 조사가 같은 일을 1분 안에 한다(같은 글을 두 경로가 처리하는 일을 줄임).

### 4-4. 이어 붙이기 — 프론트 (`tweets.js` · `css/tweets.css`)
- `_groupMsgs`(324줄 부근): `reply_to_id` 가 목록 안 다른 메시지의 `id` 면 시각 간격과 상관없이 **원글이 든 묶음의 원글(또는 이미 붙은 답글) 바로 뒤**에 넣는다.
  원글이 목록에 없으면 지금처럼 시각 순서대로 단독.
- `.lane__thread__unit.is-reply` — 원글 쪽으로 이어지는 연결선 + 번역 말풍선 머리표 「이어서」. 모양은 구현 때 시안으로 확인.
- X 카드 `hideThread=true` 유지(원글이 바로 위에 따로 있으므로). 데이터는 `textContent` 로만. 모바일 토스트 · PC 말풍선 공용.

### 4-5. 모니터
- 보충 1건마다: 자기 답글 = `ok` 「gap-fill(자기 답글) · <id> · +N분 · mode: …」, 본인 일반 글 = `warn` 「gap-fill · <id> · +N분 · mode: …」
  (+N분 = 게시에서 들어오기까지). 원글을 같이 넣었으면 「원글 함께」.
- 상시 조사가 아무것도 못 찾은 실행 · 204 실행은 기록하지 않는다.

## 5. 배선

### 배포판
- **예약**: Cloud Scheduler 새 잡 `mewtype-gapcheck`(`* * * * *`, 대상 = 접수 서비스 `/gap-check`, OIDC = `INVOKER_SA`). `deploy/scheduler.sh` 에 추가.
  - 비용: Scheduler 는 결제 계정당 잡 3개 무료, 그 뒤 잡당 월 $0.10(실행 횟수 무관). 지금 4개라 **이미 1개는 유료일 수 있고 이 잡으로 1개 더** — 확인 필요(§7).
  - 대안(잡 추가 없음): 10분 light 틱이 `+0~+9분` 10건을 Cloud Tasks 로 예약. 단 백엔드 `/tick` 이 일시정지(paused)면 조사도 멈춘다
    (개인 트윗 인입은 paused 와 무관하게 도는 것과 어긋남) · 틱이 실패하면 10분이 비어 정각 회복 실행에 기댄다.
- **보충 작업 큐**: `deploy/setup.sh` 에 `mewtype-gapfill`(`--max-concurrent-dispatches=1 --max-attempts=3`) 추가. 대상 = 접수 서비스 자기 URL(env `ADMIN_BASE_URL`).
  `tasks.from_env` 는 대상이 쓰기 서비스로 고정이라, 대상 URL · 큐를 받는 생성 함수를 더한다. 이름은 `_build_task`(34줄)의 분 버킷 없이 `gapfill-<id>`.
- **인증**: 접수 서비스는 `ALLOW_UNAUTH=1` 이라 `oidc.verify_request`(20줄)가 검증을 건너뛴다. `/gap-check` · `/gap-fill` 은 공개 주소이므로
  **이 두 경로만 OIDC 를 강제 검증**(audience = 접수 서비스 URL, 발급자 = `INVOKER_SA`) — `verify_request` 에 강제 인자 추가. Scheduler · Tasks 둘 다 OIDC 토큰을 붙인다.
- 일시정지(`control.json` paused): 개인 트윗 인입처럼 **상관없이 돈다**.
- 쓰기: 보충은 지금처럼 `writeclient.call_write` → 백엔드 `/write`(직렬화). 보충 작업이 동시 1건이라 `/write` 에 더해지는 부담은 최대 1건씩.

### 로컬 시험판
- Scheduler 대신 로컬 러너 타이머 1분 → 조사. 보충 작업은 **가공 큐(`q-enrich`)** 에 적재(적용 큐 `q-apply` 에 넣으면 `call_write` 가 같은 큐를 기다려 교착).

### 부담 (1분 주기)
- fxtwitter: 분당 5회(한도 0.5%) + 보충 시 원글 조회 가끔. Cloud Run 이 나가는 IP 를 다른 사용자와 공유할 수 있으나 이 양이면 영향 없다고 본다.
- 접수 서비스 실행 하루 1,440회 — 대부분 204 로 1초 안팎. Cloud Run 무료 사용량 안인지는 **배포 전 지금 사용량 확인**(§7).
- GitHub 읽기: 최근 30분 안에 글이 있는 실행만(대략 하루 수백 회) — PAT 한도(시간당 5,000)와 거리가 멀다.
- Groq: 지금과 같다(새 글이 있을 때만, §4-3 으로 중복 판정은 오히려 줄어듦).

## 8. 범위 밖이지만 급한 것 — `tweet_archive.json` 1MB

- 데이터 저장소 `data` 브랜치 `tweet_archive.json` = **888,969 바이트**(2026-10-26), 하루 약 19KB 씩 늘고 상한이 없다 → **약 11-03 전후 1MB(1,048,576) 를 넘는다**.
- GitHub Contents API 는 1MB 넘는 파일을 기본 형식으로 읽으면 `content` 를 비워 준다 → `gh_store.read_json`(83줄, 126줄 「No content」)이 예외 →
  **개인 트윗 커밋(`_commit_personal_tweet` 이 보관함을 같이 읽음)이 전부 실패**한다. 이 패치와 별개로 먼저 막아야 한다(보관함 상한 · 기간 정리 또는 큰 파일 읽기 방식).
