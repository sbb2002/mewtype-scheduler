v3b 목표 구조 — 관제탑 + 우편함

지금은 네모 박스끼리 직접 쓰고, 직접 부르고, 직접 예약한다. 목표 구조에서는 역할을 셋으로 나눈다. 게이트는 받아서 가공하고, 감시자는 보고, 관제탑만 쓴다. 게이트와 감시자는 "본 사실"을 우편함에 넣고 바로 돌아가며, 관제탑이 우편함을 묶음으로 비워 한 번에 커밋한다.

현재 배선 지도(ref/v3b_wiring_flow.html)의 기능을 모두 유지한다. 아래 "기능 커버리지" 표가 그 대조표다.

설계안 · 실측 전 — 60건 버스트 재측정으로 채택 여부 결정

설계 원칙

v3b의 모든 변경은 이 다섯 줄에 비춰 판단한다.

01쓰기는 관제탑만

data · monitoring 브랜치에 커밋하는 주체는 관제탑 하나. 머지 규칙(같은 방송 판정, 합동, 상태 역행 방지)도 관제탑 한 곳에만 있다.

02보낸 쪽은 기다리지 않는다

게이트 · 감시자는 우편함에 넣으면 끝. 운영자 명령은 "접수" 응답 후 결과 DM이 따로 온다. 지난 관제탑의 60초 동기 대기를 없앤다.

03묶음 커밋

관제탑은 깨어날 때 쌓인 이벤트를 전부 꺼내 브랜치당 커밋 1번. 60건이 몰려도 커밋은 몇 번이면 끝난다.

04느린 일은 가장자리에서

LLM · vxtwitter · videos.list · yt-dlp · OCR은 게이트 · 감시자에서 끝내고, 관제탑은 순수 머지와 커밋만 한다.

05읽기는 자유, 예약은 관제탑

읽기는 충돌하지 않으니 누구나 직접 읽는다. Cloud Tasks 예약은 관제탑만 한다 — 오늘 "즉시 wake 불발"(환경변수가 없는 쪽이 예약하던 문제)이 구조적으로 사라진다.

목표 흐름도

"시나리오" 탭은 기능 하나가 끝에서 끝까지 흐르는 경로, 분류 탭은 배선 가닥. 굵은 테두리 = 우리 코드(Cloud Run 서비스 3개: 게이트 · 감시자 · 관제탑). 점선 테두리 = 서드파티.

기능 커버리지 — 현재 기능이 목표 구조에서 어디로 흐르나

왼쪽 = 지금 있는 기능(배선 지도 + CLAUDE.md 기준). 오른쪽 = 목표 구조의 경로. 빠진 기능 없음.

트레이드오프 · 검증 필요

얻는 것만 있는 구조는 없다. 빨간 칸은 실측·확인 전이라 채택 전에 반드시 풀어야 하는 것.

운영자 응답이 두 번으로 나뉜다

"접수" DM이 먼저 오고, 반영 결과 DM은 관제탑이 커밋한 뒤 온다(수 초). 마법사형 명령은 단계마다 이 지연이 붙는다 — 어차피 재정리 대상이라 v3b에서 명령 체계를 같이 손보는 게 맞다.

화면 반영은 사실상 그대로

묶음 대기(수 초)가 더해지지만 raw CDN 캐시가 최대 약 5분이라 팬 화면 기준 체감 차이는 없다.

서비스가 2개 → 3개

관제탑은 concurrency=1로 따로 떼야 한다. 감시자가 같은 서비스에 있으면 관측 요청이 관제탑을 막는다(지금 백엔드가 /write 중에 /wake를 받으면 429가 나는 것과 같은 문제).

우편함 = Pub/Sub 신규 도입 (확인 필요)

pull 구독 + "비우기" 알림 태스크(5초 단위 이름 중복 제거) 조합. 무료 한도(월 10GiB) 안이라고 보지만 계정 설정·IAM · 보존 기간 · 데드레터 동작은 미확인.

여러 파일을 커밋 1개로 (구현 필요)

Contents API는 파일 1개씩이라 GitHub Git Data API(tree · commit · ref 갱신)로 바꿔야 한다. ref 갱신 충돌 시 재시도 규칙 설계 필요.
