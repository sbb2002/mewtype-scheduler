# 실제 각크기를 유지하면서 해·달의 존재감을 높이는 방법론

추천은 **원반의 각크기는 실제값으로 고정하고, 대기 효과와 촬영 효과를 분리해 조절하는 방식**이다. 해는 하얀 핵·부드러운 번짐·약한 방사광·시선에 따라 움직이는 고스트로 존재감을 높이고, 달은 저고도 소광과 주변 지평선 단서를 중심으로 표현하는 것이 좋다.

단, **같은 각크기의 달을 화면에서도 반드시 더 크게 느끼게 하는 방법은 확립되어 있지 않다.** 광륜을 넓히는 것은 가능한 디자인이지만 달 착시 자체를 재현했다고 설명하면 부정확하다.

아래는 두 소스 파일을 읽은 결과이며, 코드·파일은 수정하지 않았다. 수치표는 관측값과 구별한 **구현 시작용 디자인 제안값**이다.

## 1. 현재 코드에서 확인한 사항

| 항목 | 현재 구현 | 제안에 주는 의미 |
|---|---|---|
| 크기 | 기본 각반지름 해 1.2°, 달 1.6°. `real`은 각각 0.2665°, 0.2590° | 실제 크기 원칙을 적용하려면 기본 선택부터 결정해야 함 |
| 해 번짐 | `sky()`에서 `discGlow()`의 거듭제곱 3개를 합성 | 이미 다중 폭 번짐이 있으므로 추가보다 재조정 우선 |
| 해 합성 | `(c + light) / (1 + max(light))` | 강한 빛을 흰색으로 수렴시키지만 물리적 노출 모델은 아님 |
| 달 번짐 | `pow(discGlow(...), uLunar.z)` | 이미 저고도에서 폭·세기가 함께 증가 |
| 달 색 | `updateAstro()`의 `moonCol` 보간 | 낮에는 저고도 주황색을 다시 푸른 흰색 쪽으로 보정 |
| 원반 눌림 | `discTangent()`, 0～5°에서 경험적 변형 | 굴절을 표현하지만 정확한 대기 계산은 아님 |
| 천체 표시 | 실외·위치정보가 있을 때만 `uOut=1` | 실내도 같은 AR 방향을 쓰지만 천체는 현재 표시되지 않음 |
| 출력 | 바닥·빔 합성 후 디더 추가 | 렌즈 효과를 넣을 적절한 위치가 별도로 있음 |

특히 현재 번짐의 폭을 먼저 확인해야 한다. 변형 없는 경우 `cos(θ)^n`의 중심에서 반치점까지 각거리는 대략 다음과 같다.

\[
\theta_{1/2}\simeq\sqrt{2\ln2/n}
\]

- 해: 지수 360·80·24 → 약 **3.6°·7.5°·13.8°**
- 달: 지수 900 → 약 **2.25°**, 저고도 지수 240 → 약 **4.35°**

이 값은 **원반 반지름이나 눈에 보이는 최종 경계가 아니라 번짐 성분의 반치폭**이다. 그래도 실제 반지름 약 0.26°와 비교하면 이미 넓다. 현재 상태에서 광륜만 더 넓히면 “쨍함”보다 화면 전체가 뿌옇게 될 가능성이 높다.

## 2. Claude 초안의 과학적 검토

### 2.1 달 착시와 실제 크기

**대체로 맞지만, “사진에서 각크기가 같다”는 표현은 근사로 한정해야 한다.**

수평선의 달이 크게 느껴지는 것은 지각 현상이다. 대기가 달을 크게 확대하는 것은 아니며, 굴절은 보통 세로 방향을 압축한다. 다만 실제 각지름은 달까지의 거리와 관측자의 위치에 따라 조금 달라지므로 완전히 불변하지는 않다. 달 착시의 정확한 원인은 아직 합의되지 않았다. **확실도: 높음 / 원인 설명은 미확정.** [NASA의 달 착시 설명](https://science.nasa.gov/solar-system/moon/the-moon-illusion-why-does-the-moon-look-so-big-sometimes/), [촬영 비교 시 거리 변화에 대한 주의점](https://science.nasa.gov/resource/photographing-the-moon-illusion/)

지평선 실루엣과 원근 단서를 제공하는 것은 합리적인 실험이다. 그러나 다음은 구분해야 한다.

- 지평선·먼 지형: 거리 판단을 돕는 후보 단서.
- 돔 테두리·바닥: 가까운 구조물로 읽힐 수 있어 같은 효과를 보장하지 않음.
- 에빙하우스식 크기 비교: 주변 도형 크기에 따라 반대 효과도 가능.

따라서 “착시를 일으킨다”보다 **“원반을 유지하고, 크게 느낄 가능성이 있는 배경 단서를 제공한다”**가 정직하다. 폰 화면에서의 효과 크기와 개인차는 **확실하지 않음**.

### 2.2 저고도에서 광륜이 넓어진다는 주장

**초안의 인과관계는 수정해야 한다.**

긴 대기 경로는 직접광의 소광과 산란광 분포에 영향을 준다. 하지만 그것만으로 광륜의 각반경이 반드시 증가하지는 않는다. 입자 크기·분포·농도, 위상함수, 구름과 다중산란이 함께 작용한다. 특히 회절 코로나에서는 작은 입자가 더 큰 고리를 만든다. **입자와 각폭의 관계는 확실도 높음, 고도에 따른 단조 확대는 근거 부족.** [WMO 코로나 설명](https://cloudatlas.wmo.int/en/corona.html)

추천 표현은 다음과 같다.

> 저고도에서는 소광을 적용한다. 광륜의 폭과 강도는 별도 대기 상태값으로 조절하며, 필요하면 저고도에서 약하게 확대하는 미술적 보정을 추가한다.

또한 부드러운 번짐, 회절 코로나, 22° 얼음결정 헤일로를 하나의 현상으로 취급하지 않는 편이 좋다.

### 2.3 소광과 색 변화

**방향은 맞다. 단, 레일리 산란만으로 완성되는 모델은 아니다.**

분자 산란은 가시광에서 대략 파장 −4제곱에 비례한다. 에어로졸은 다른 파장 의존성을 가지며, 흡수 성분도 존재한다. 따라서 RGB 3채널 근사는 일관된 색 변화에는 유용하지만 분광적으로 정확한 하늘 모델은 아니다. [레일리 산란 광학두께 설명](https://atmos.nmsu.edu/education_and_outreach/encyclopedia/rayleigh_optical.htm)

낮은 달은 대체로 누렇게 보이지만, 항상 같은 노랑→주황→빨강 경로를 따르는 것은 아니다. 대기 상태에 따라 강하게 어두워져 사라질 수도 있다.

### 2.4 해의 광원 효과

| 주장 | 판정 |
|---|---|
| 여러 폭 가우스로 PSF 근사 | 타당한 렌더링 근사. 계수 선택만으로 실제 눈·렌즈를 재현한 것은 아님 |
| 짝수 날 N개 → N줄, 홀수 → 2N줄 | 이상화한 규칙적 조리개에서 성립. 곡률·개방 정도에 따라 모양과 선명도 변화 |
| 중심–해 직선 위 고스트 | 중심 정렬 렌즈를 흉내 내는 유용한 근사. 모든 고스트가 반대편에 생기는 것은 아님 |
| 중심에 가까울수록 눈부심 증가 | 중심 응시 느낌을 위한 디자인으로 가능. 모든 카메라 플레어의 보편 법칙은 아님 |
| 화면 밖 해의 번짐 | 타당. 단, 화면 밖 광원의 차폐·입사 조건도 고려해야 함 |

조리개 규칙은 [카메라 제조사 설명서](https://www.bhphotovideo.com/lit_files/42026.pdf), 렌즈 반사·플레어의 복잡성과 렌더링 접근은 [Hullin 등의 연구](https://resources.mpi-inf.mpg.de/lensflareRendering/)를 참고할 수 있다.

폰 방향은 **시야 방향**이며 실제 눈동자의 주시점을 측정하지 않는다. 제품 설명에서도 “시선 의존”은 이 제한을 전제로 해야 한다.

### 2.5 성능 +15%

**현재로서는 확실하지 않음.**

6～8개의 해석식 고스트도 모든 픽셀에서 계산하면 비용이 커질 수 있다. 패스·텍스처 수가 같다는 사실만으로 GPU 시간 증가율을 예측할 수 없다. +15%는 보장값이 아니라 실제 기기에서 확인할 목표다.

## 3. 실제 크기 원칙의 정의

추천 계약은 다음과 같다.

> 원반의 기하학적 각지름은 약 0.53°로 유지한다. 굴절에 의한 세로 압축은 허용한다. 산란과 렌즈 효과는 원반 밖에 별도 합성한다.

“화면에서 차지하는 시각적 범위도 0.53° 이내”를 요구하면 넓은 블룸과 충돌한다. 또한 노출로 원반 주변이 하얗게 포화되면 **기하 원반은 유지해도 흰 덩어리는 커 보인다.** 이 구분은 명시해야 한다.

현재 폰 초점은 `uF=390×1.25=487.5 CSS px`다. 화면 중심에서 지름 0.53°는 다음 정도다.

\[
2F\tan(0.53^\circ/2)\simeq4.51\text{ CSS px}
\]

DPR 1.5에서는 약 6.8 버퍼 픽셀이다. 달 표면과 가는 초승달을 상세히 표현하기 어려운 크기다.

또한 **가상 세계의 0.53°와 사용자의 눈에서 본 화면의 0.53°는 다르다.** 후자는 화면 실측 폭과 관찰 거리가 필요하다. `window` 모드는 이를 가정한 별도 투영이며, 원반만의 크기 변경으로 취급하면 안 된다.

| 선택지 | 원칙과의 관계 | 추천 |
|---|---|---|
| 원반 실제값, 번짐·지평선 단서 조절 | 충족 | 기본안 |
| 원반 실제값, FOV 축소 | 가상 각크기는 유지하지만 전체 시야 확대 | 별도 보기 모드 |
| 저고도 원반 1.03～1.08배 | 실제 크기 고정과 충돌 | 필요하면 명시적 스타일 옵션 |
| 거리 기반 실제 각지름 변화 | 과학적으로 더 정교함 | 후속 단계 |

## 4. 소광 색 모델의 실용 근사

`updateAstro()`에서 초당 한 번 계산해 uniform으로 보내면 충분하다.

겉보기 고도 \(h\)를 도 단위로 사용하면 Kasten–Young 식은 다음처럼 쓸 수 있다.

\[
m(h)=\frac{1}
{\sin(h\pi/180)+0.50572(h+6.07995)^{-1.6364}}
\]

양의 고도에서 사용하고, 지평선 아래로 무작정 외삽하지 않는다. 이 모델은 **겉보기 천정거리**를 요구한다. [pvlib 구현·입력 정의](https://pvlib-python.readthedocs.io/en/stable/_modules/pvlib/atmosphere.html)

대표 파장을 R/G/B 각각 650/550/450 nm로 놓은 시작용 근사는 다음과 같다.

\[
\tau_i=
0.10(P/P_0)(550/\lambda_i)^4+
\tau_{a,550}(550/\lambda_i)^\alpha
\]

\[
T_i(h)=\exp[-m(h)\tau_i]
\]

- `τa,550=0.05`, `α=1.3`: 시작용 대기 프리셋이며 관측값 아님.
- `0.10`: 550 nm 분자 광학두께를 단순화한 값.
- 해와 달에 같은 대기 투과 함수를 적용하되 원래 광원색·노출은 따로 둔다.
- 대기 관측값이 없으므로 이를 “현재 날씨 재현”이라고 부르지 않는다.

고도 60° 기준 외형을 유지하려면:

\[
L_i(h)=L_i(60^\circ)
\exp[-(m(h)-m(60^\circ))\tau_i]
\]

이때 `L(60°)`는 이미 그 고도에서의 값이므로 투과율을 중복 적용하지 않는다. 색만 정규화하면 소광에 의한 어두워짐이 사라지므로, **색비와 밝기를 함께 보존한 뒤 노출을 적용**한다.

위 예시의 대략적인 투과율은 다음과 같다.

| 겉보기 고도 | airmass | 직접광 투과율 R/G/B |
|---:|---:|---|
| 60° | 1.15 | 0.90 / 0.84 / 0.72 |
| 20° | 2.90 | 0.77 / 0.65 / 0.43 |
| 5° | 10.3 | 0.39 / 0.21 / 0.051 |
| 1° | 26.3 | 0.089 / 0.019 / 0.0005 |

이는 채널별 대표 파장 계산이며 **표시용 sRGB 색상표가 아니다.** 지평선 근처 수치는 실제 기상에 특히 민감하다.

현재 `bgastro.js`에서는 해 고도는 굴절 전, 달 고도는 굴절 후다. 달의 지심시차도 적용하지 않는다. 추후에는 `geometricAlt`와 `apparentAlt`를 구분하고, 원반 위치·소광·눌림이 어떤 고도를 사용하는지 통일해야 한다. 현재의 경험적 0.83배 눌림을 정밀 굴절이라고 설명해서는 안 된다.

## 5. 해의 구현 방법론

### 5.1 합성 위치

한 패스 안에서도 두 층으로 나눈다.

1. **`sky()` 내부:** 원반, 고도별 소광, 하늘에 고정된 대기 산란.
2. **`main()`의 바닥·빔 합성 이후, 디더 이전:** 화면 좌표 기반 번짐·방사광·고스트·베일.

렌즈 플레어는 센서 앞 광학계에서 생기므로 전경 위에도 겹칠 수 있다. 반면 광원이 전경에 가려지면 전체 플레어의 입력 강도는 낮아져야 한다. HUD는 광학 효과 이후에 합성하면 가독성을 유지하기 쉽다.

현재 소스는 sRGB 텍스처 값을 사실상 직접 혼합한다. 과학적인 소광식을 넣어도 이것만으로 선형광 렌더링이 되지는 않는다. 초기에는 새 광원 항의 처리 범위를 명확히 하고, 전체 색공간 변경은 별도 검증 대상으로 두는 것이 안전하다.

### 5.2 번짐과 방사광

기존 세 `pow()`를 먼저 정리하고, 각폭이 읽히는 형태로 바꾼다.

\[
B(\theta)=\sum_j A_j
\exp[-\theta^2/(2\sigma_j^2)]
\]

좁은 흰 번짐·중간 폭 번짐·약한 넓은 베일의 세 성분이면 충분하다. 기존 넓은 산란 위에 같은 성분을 중복 추가하지 않는다.

방사광은 해의 투영점 주변에 부드러운 방향성 로브를 만든다.

\[
S(\rho,\phi)=A_s
e^{-(\rho/\ell)^2}
\left[\max(0,\cos(M(\phi-\phi_0)))\right]^p
\]

이 식은 `2M`개 로브를 만든다. 예를 들어 `M=4`는 8방향이다. 중심에서는 각도가 정의되지 않으므로 방사광을 원반·내부 번짐 안에서 감쇠한다. 폭은 픽셀 풋프린트 이하로 좁히지 않는다.

참조 사진의 정확한 조리개·렌즈·노출은 **확실하지 않음**. 8～12개 부드러운 광선을 선택하는 것은 사진 분위기를 위한 디자인이다.

### 5.3 고도별 시작값

아래 강도는 광학 효과 프리셋의 상대값이다. **소광 후 광원 입력에 곱하며**, 최종 화면 밝기와 같지 않다. `σ`는 가우스 표준편차다.

| 해 고도 | 핵·주변색 | 내부/중간 σ | 넓은 베일 σ | 방사광 계수 / 길이 | 고스트 최대 불투명도 |
|---|---|---:|---:|---:|---:|
| ≥30° | 핵 흰색, 주변 약한 온백색 | 0.35° / 1.5° | 6° | 1.0 / 5° | 0.025 |
| 10～30° | 핵 흰색, 주변 금빛 증가 | 0.35° / 1.6° | 6° | 0.8 / 4° | 0.020 |
| 2～10° | 소광색 반영, 포화 시 중심만 흰색 | 0.40° / 1.8° | 6.5° | 0.35 / 3° | 0.010 |
| 0～2° | 감쇠된 노랑·주황·적색 | 0.40° / 1.8° | 6.5° | 0.10 / 2° | 0.003 |
| 완전 차폐·진 뒤 | 직접광 없음, 박명 별도 | — | — | 0 | 0 |

저고도 폭 증가는 **약한 미술 보정**이다. 대기 질량에서 도출한 결과가 아니다. 낮은 해를 항상 더 강하게 번지게 하면 소광과 모순되므로 강도는 줄이는 쪽을 추천한다.

## 6. 시야 방향에 따른 효과

현재 코드와 같은 CSS 좌표에서 다음을 계산한다.

\[
z_s=\mathbf{s}\cdot\mathbf{Fwd}
\]

\[
s_{screen}=uC+uF
\left(
\frac{\mathbf{s}\cdot\mathbf{Right}}{z_s},
-\frac{\mathbf{s}\cdot\mathbf{Up}}{z_s}
\right)
\]

고스트는 다음으로 시작할 수 있다.

\[
g_j=uC+k_j(s_{screen}-uC)
\]

`k={-0.25,-0.65,-1.1}` 정도의 3개부터 시작하고, 반경과 색을 고정한다. 매 프레임 무작위로 바꾸면 센서 흔들림과 함께 번쩍인다. 고스트는 픽셀 화면 좌표에서 계산해 종횡비 때문에 원이 타원이 되지 않게 한다.

중심 응시 느낌은 다음처럼 완만하게 줄 수 있다.

\[
\gamma=\arccos(\mathbf{s}\cdot\mathbf{Fwd})
\]

\[
G_{view}=0.75+0.25e^{-(\gamma/12^\circ)^2}
\]

이 값은 **중심에 가까우면 약간 더 눈부시게 하는 디자인**이다. 고스트까지 동일하게 최대화하면 중심에 모든 고스트가 겹치므로, 고스트는 별도 감쇠하거나 합산 상한을 둔다.

화면 밖 효과는 투영점에서 화면 사각형까지 최단거리 `δ`를 사용한다.

\[
G_{edge}=1-\operatorname{smoothstep}(0,\Delta,\delta)
\]

\[
A_{flare}=A_0\,
G_{view}G_{edge}V_{source}V_{front}
\]

- 화면 밖 5～10° 정도까지 부드럽게 감쇠하는 것으로 시작.
- `z_s≈0`에서 투영점이 발산하므로 투영 전에 측방·후방 광원을 감쇠.
- 구면 기반 대기 번짐은 해가 화면 밖이어도 자연스럽게 남길 수 있음.
- `Vsource`는 **해 방향의 구름·지평선·전경 차폐**다.

현재 `cloud`는 각 출력 픽셀 방향의 값이다. 고스트 위치의 구름값으로 고스트를 가리면 잘못된 동작이다. 해 방향 구름을 별도로 조회하거나 근사해야 하며, **텍스처 추가 없음과 텍스처 조회 추가 없음은 다른 조건**이다.

## 7. 달의 구현 방법론

달에는 해보다 훨씬 절제된 효과를 추천한다.

- `moon()`의 원반·위상·텍스처는 유지.
- `moonCol`의 저고도 고정 보간을 공유 소광 모델로 교체.
- 물리적인 투과색과 낮하늘의 대비 보정을 분리.
- 기존 저고도 광륜 확대는 줄이고, 대기 상태 프리셋으로 분리.
- 렌즈 고스트와 규칙적인 방사광은 기본값 0.

| 달 고도 | 색 | 직접광 밝기 | 광륜 σ | 광륜 상대 계수 | 방사광·고스트 |
|---|---|---|---:|---:|---:|
| ≥30° | 중성에 가까운 따뜻한 회백색 | 소광·위상으로 결정 | 0.25° | 0.015 | 0 |
| 10～30° | 약한 황백색 | 같은 모델 | 0.30° | 0.020 | 0 |
| 2～10° | 노랑～주황 | 같은 모델로 감소 | 0.40° | 0.025 | 0 |
| 0～2° | 주황～적색 또는 거의 소실 | 강한 감소 | 0.45° | 0.020 | 0 |

광륜 계수 역시 소광 후 달빛에 곱한다. 위상 의존은 현재의 `fraction^0.7`처럼 경험적 값으로 시작할 수 있지만 정확한 달 밝기 법칙으로 부르지는 않는다. 초승달에서 광륜이 원형 보름달처럼 읽히지 않는지 별도 검증한다.

큰 느낌을 원하면 광륜보다 먼저 **실제 지평선 근처에 고정된 먼 실루엣과 원근 단서**를 실험한다. 달을 따라다니는 비교 도형이나 자동으로 달 옆에 붙는 구조물은 피한다. 효과가 없으면 “착시 재현 성공”으로 평가하지 않는다.

## 8. 위험과 검증 방법

| 위험 | 검증·판정 방법 |
|---|---|
| 번짐이 흰 원반처럼 읽힘 | 효과 전부 끈 원반 마스크와 최종 화면을 따로 캡처. 기하 크기와 포화 범위를 별도 측정 |
| 작은 원반의 계단·반짝임 | 실제 크기에서 0.1 CSS px 상당의 미세 이동을 녹화. 적분 밝기·면적이 급변하는지 확인 |
| 화면 가장자리 크기 변화 | 중심과 네 모서리에서 비교. 원근 투영의 픽셀 확대를 원반 각크기 변경으로 오인하지 않기 |
| AA 폭 부정확 | 현재 상수 `1/(F×DPR)`와 방향 미분 기반 폭을 비교. 미분은 분기 전에 계산 |
| 밴딩 | 어두운 화면·밝은 화면에서 확인. 기존 디더는 최종 합성 뒤 유지 |
| 고스트가 차폐 뒤에도 남음 | 해가 구름·바닥·돔 경계에 가려지는 순간을 녹화 |
| 센서 흔들림이 광학 효과를 증폭 | 정지 10초와 느린 팬 비교. 광원 위치에 별도 지연을 크게 넣어 잔상이 생기지 않게 함 |
| 실내 표시 의도 변경 | 현재처럼 실내 천체 없음 유지 여부를 별도 결정. 표시한다면 돔의 투과·차폐 관계부터 정의 |
| 성능 목표 초과 | 같은 기기·해상도·장면에서 변경 전후 GPU 시간 비교. 타이머 지원 시 disjoint 샘플 제외 |

검증 장면은 다음 조합으로 고정한다.

1. **해 고도:** 60°, 20°, 5°, 1°, 원반 일부가 지평선 아래인 상태.
2. **달 고도:** 60°, 20°, 5°, 1° × 보름·반달·가는 초승달.
3. **시야:** 중심, 가장자리 안쪽, 화면 밖 2°·5°·10°, 후방.
4. **차폐:** 맑음, 얇은 구름, 짙은 구름, 전경 차폐.
5. **출력 조건:** 390×760, 가로 화면, DPR 1·1.5, 라이트·다크 테마.

현재 `bgmoon`은 달을 고도 35°로 고정하므로 저고도 시험에는 부족하다. 후속 구현에서는 고도·방위·대기 상태를 고정하는 디버그 입력이 유용하다. 실제 날짜 시험은 사이트 좌표·시간대·ISO 시각을 함께 기록한다.

달 착시는 원반 크기를 동일하게 둔 배경 단서 유무의 무작위 A/B로 평가한다. “어느 쪽이 더 커 보이는가”와 “원반 경계가 어디인가”를 따로 묻고, 배율 효과는 측정 전까지 **확실하지 않음**으로 남긴다.

성능은 정지 상태뿐 아니라 실제로 셰이더가 계속 그려지는 팬·배경 보기 상태에서 측정한다. 전체 프레임 시간에는 DOM 작업도 섞이므로 GPU 비용과 구분한다.

## 9. 추천 구현 순서

1. **크기 계약 확정:** `real`을 기준으로 정하고, 효과 없는 원반의 각크기·픽셀 풋프린트를 기록.
2. **기존 효과 정리:** 해 3중 번짐과 달 광륜을 각폭 기준으로 재조정. 추가 효과 없이 평가.
3. **고도 정의 정리:** 해·달의 기하/겉보기 고도를 구분하고 굴절 중복 방지.
4. **공유 소광 도입:** 색과 밝기를 함께 적용. 대기 프리셋과 노출 보정은 분리.
5. **해 방사광 추가:** 약한 고정 패턴부터 시작해 AA·미세 이동 검증.
6. **시야 의존 베일·고스트 추가:** 고스트 3개, 화면 밖 감쇠, 광원 차폐부터 구현.
7. **달 지각 단서 실험:** 원반 크기를 유지한 A/B로 판단.
8. **기기별 검증:** 품질과 GPU 비용을 확인한 뒤 필요할 때만 효과 수를 늘림.

가장 먼저 검토할 시안은 **“실제 원반 + 정리된 기존 번짐”**, **“여기에 해 방사광 추가”**, **“여기에 약한 시야 의존 고스트 추가”**의 세 단계다. 이 순서라면 어느 효과가 쨍함을 만들고 어느 효과가 단순히 화면을 흐리는지 분명하게 판단할 수 있다.
