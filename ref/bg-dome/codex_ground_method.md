# 수평선 아래 풍경 제안 — 구현 전 검토

**추천은 ‘가상 고도 2km, 지구 곡률을 반영한 지표, 절차적으로 만든 도시·산·바다’입니다.** 풍경은 바깥 보기에 먼저 넣고, 실내에는 같은 지형을 분홍 하늘에 맞춘 낮은 대비로 적용하는 순서가 좋겠습니다. 상공 느낌은 수평선 강하뿐 아니라 **아래로 펼쳐지는 지표와 거리별 흐려짐**에서 나옵니다.

[src/frontend/js/bgdomegl.js](src/frontend/js/bgdomegl.js)와 `bgastro.js`를 읽었습니다. 파일은 수정하지 않았습니다. `codex_luminary_consult.md`는 현재 작업 폴더와 상위 검색 범위에서 찾지 못했으므로, 그 문서의 구체적인 렌즈 효과 안과의 정합성은 **확실하지 않음**입니다. 아래 성능 수치는 측정 결과가 아닌 설계 예산입니다.

## 1. 초안 사실 확인과 추천 높이

### 현재 구조와 정정

| 항목 | 확인·정정 |
|---|---|
| 눈 위치 | 기본값 `EYE0 = [0, 0.24, 0]`, 줌 이동 한도 0.6으로 초안과 일치합니다. |
| 실제 수평 | 정규화된 시선 `d.y = 0`이 맞습니다. 유리 위도선과 별개입니다. |
| 18° 유리선 | 중심 눈에서 고도 `atan2(sin18°−0.24, cos18°) ≈ 4.15°`로 보입니다. 초안이 맞습니다. |
| 바닥 앞 가장자리 | 기본 눈에서 `−atan(0.24) ≈ −13.50°`입니다. |
| 수평 아래 하늘 | 하늘 영상이 이어지지만, 그대로 늘어나는 것만은 아닙니다. `skySet()`이 아래쪽을 흐린 수평 부근 색으로 섞습니다. |
| 해·달·별 | 이미 `above = smoothstep(−0.004, 0.006, d.y)`로 고도 0° 부근에서 감춥니다. 풍경 도입 시 함께 바꿔야 합니다. |
| 바닥 반사 | 현재는 `uSkyBase`를 이용한 간략 표현입니다. 풍경을 추가해도 바닥에 자동으로 반사되지 않습니다. |
| 한 패스 | WebGL 배경은 전체 화면 삼각형 한 패스입니다. 떠다니는 장식은 별도 DOM/SVG입니다. |

줌아웃에서 ‘앞쪽 띠가 넓어진다’는 설명도 맞습니다. 최대 이동 시 정면 바닥 경계는 약 **−8.53°**가 되어, 수평과 바닥 사이 띠가 넓어집니다.

다만 바닥 경계는 방위에 따라 달라집니다. 이동한 눈에서 가까운 가장자리는 약 **−30.96°**입니다. 따라서 **“−30° 아래는 무조건 바닥이 가린다”는 가정은 안전하지 않습니다.** 현재 줌 이동 방향이 시선 방위를 따라가므로 가까운 가장자리가 항상 화면 정면에 오는 것은 아닙니다.

### 추천: 가상 고도 2km

굴절을 무시한 구형 지구에서 수평선 강하는 다음과 같습니다.

\[
\delta=\arccos\left(\frac{R}{R+h}\right)\approx\sqrt{\frac{2h}{R}}
\]

`R = 6,371km`로 직접 계산하면 다음과 같습니다.

| 높이 | 수평선 고도 | 수평선까지 직선거리 |
|---|---:|---:|
| 1km | 약 −1.02° | 약 113km |
| **2km** | **약 −1.44°** | **약 160km** |
| 3km | 약 −1.76° | 약 196km |
| 10km | 약 −3.21° | 약 357km |

초안의 1km·10km 값은 맞습니다. 실제 관측에서는 대기 굴절로 달라지며, 고도만으로 정확한 값을 정할 수 없습니다. 이번에는 굴절 없는 기하를 일관되게 쓰는 편이 적절합니다. [SDSU의 수평선 강하 설명](https://aty.sdsu.edu/explain/atmos_refr/dip.html)

**2km를 추천하는 이유는 표현의 균형입니다.**

- 기본 바닥 경계까지 약 12°의 지표 띠를 확보합니다.
- 10km보다 도시와 산의 형태를 알아보기 쉽습니다.
- 1km보다 수평선 강하가 조금 분명하며, 높은 산을 과장하지 않고 구성할 여유가 있습니다.

이 값이 시각적으로 최적인지는 **확실하지 않음**입니다. 같은 장면으로 1·2·3km를 비교해야 합니다. 돔 반지름 1은 실내 좌표이므로, `EYE.y = 0.24`를 실제 고도 2km와 직접 환산해서는 안 됩니다.

또한 −1.44°는 **바다 또는 기준 지표의 수평선**입니다. 산 능선은 그보다 높게 솟을 수 있으며, 일부는 고도 0° 위로 올라오는 것이 자연스럽습니다.

## 2. 풍경 표현과 셰이더 구조

### 공통 구조: 방향과 지표 위치를 함께 사용

방위각만으로 실루엣을 만들면 ‘창밖 벽화’처럼 보이기 쉽습니다. 다음의 가벼운 2.5D 구조를 추천합니다.

1. `d`로 고도·방위를 구합니다.
2. 외부 세계의 눈을 지구 중심 기준 `(0, R+h, 0)`에 놓고 구와의 교차를 계산합니다.
3. 교차 위치에서 거리와 수평 지표 좌표를 얻습니다.
4. 지표 좌표로 도시·바다의 큰 무늬를, 방위각과 거리층으로 산·건물 윤곽을 만듭니다.
5. 지표색과 대기색을 합성한 뒤 기존 유리 표현으로 넘깁니다.

구 교차는 해석식 한 번이면 되며, 지형 전체를 레이마칭할 필요는 없습니다. 지구 반지름을 1로 정규화하고 `h/R`을 사용하면 큰 숫자를 직접 다루는 부담도 줄어듭니다. 수평선 접점의 수치 안정성은 별도로 검증해야 합니다.

돔 줌은 실내 눈 위치 `E`에만 적용하고, 외부 풍경은 우선 `d` 기준으로 고정합니다. 현재 줌을 실제 수백 m의 외부 이동으로 환산하면 풍경이 시선을 따라 움직이는 문제가 생깁니다.

### 대기 원근

기본식은 다음 정도로 충분합니다.

\[
C = T\,C_{\mathrm{surface}}+(1-T)\,C_{\mathrm{air}},\quad
T=e^{-\beta s}
\]

- `s`: 실제 교차거리 또는 거리층에 배정한 대표 거리
- `β`: 예술적으로 조절하는 안개 계수
- `C_air`: 해당 방위의 수평 부근 하늘색
- `C_surface`: 낮·노을·밤에 따른 지표색

**고도만으로 안개를 정하지 않는 것이 중요합니다.** 높은 산과 바다는 같은 화면 고도에서도 거리가 다를 수 있습니다.

`C_air`는 기존 A/B 하늘 텍스처의 흐린 수평색을 `uMix`와 동일하게 혼합하고, 바깥 보기의 야간 감광·태양 방향 온기를 맞추는 방식이 좋습니다. 완성된 `sky()` 전체를 다시 호출하면 해·달·별까지 중복 계산하므로, **천체를 제외한 하늘 바탕색 함수를 공유**하는 편이 낫습니다.

### 종류별 권장 표현

| 종류 | 구조·주요 파라미터 | 낮·노을·밤 |
|---|---|---|
| **산** | 원주 전체가 이어지는 능선 3층. 층별 대표 거리, 높이, 거칠기, 안개량. 저주파 형태에 작은 세부만 추가 | 낮에는 청회·녹회색, 노을에는 태양 방향의 약한 온기, 밤에는 낮은 대비의 어두운 능선. 먼 층일수록 하늘색에 가까움 |
| **도시** | 지표의 큰 구역 무늬 + 중·원거리 건물 윤곽 1~2층. 구역 크기, 밀도, 건물 높이 범위, 점등률 | 낮에는 낮은 채도의 건물·도로 덩어리, 노을부터 점등, 밤에는 적은 수의 안정된 빛과 넓고 약한 도시 광원 |
| **바다** | 구형 해수면 교차 + 큰 색 변화 + 저주파 파결. 거칠기, 반사 세기, 파결 크기 | 낮에는 하늘 반사와 시선각에 따른 변화, 노을에는 따뜻한 반사, 밤에는 어두운 수면과 조건부 달빛 |

**도시:** 2km 높이에서는 도시 전체가 가까운 스카이라인처럼 솟아 있지 않습니다. 기본 눈에서 −13.5° 방향의 지표는 평면 근사로 약 8km 앞입니다. 따라서 가까운 띠에는 지붕·구역·도로의 덩어리가, 먼 곳에는 작은 윤곽이 보이는 구성이 더 그럴듯합니다. 개별 창문을 촘촘히 그리는 것은 피합니다.

**산:** 정면 실루엣만 세 겹 놓기보다, 아래쪽 지표에도 완만한 색·음영 변화가 이어져야 합니다. 2km보다 높은 봉우리를 허용할 경우 능선이 기준 수평 위로 올라오는 것도 허용합니다. 각도 높이를 임의로 크게 주면 거대한 절벽처럼 보일 수 있으므로 대표 거리·실제 높이와 함께 조절합니다.

**바다:** 해·달과 같은 방위라는 이유만으로 세로 반사 띠를 그리지 않습니다. 수면 법선 `n`, 관측 방향 `v`, 천체 방향 `l`로 반사 정렬을 평가하고 거칠기로 폭을 넓힙니다. 구형 수면에서는 국소 법선을 쓰면 됩니다.

천체가 높으면 반사 중심이 바닥 뒤에 가려지는 것이 정상입니다. 해가 지표에서 조명할 수 없는 위치라면 반사도 줄여야 합니다. 달 반사는 위상·고도·`uMoonLight`와 연동합니다. 파도 반사의 정확한 물리 재현은 이 예산에서는 **확실하지 않음**이며, 넓고 절제된 근사 표현을 목표로 합니다.

### 랜덤 방식

**첫 방문에 시드를 만들고 기기에 저장해 유지하는 방식**을 추천합니다.

- 종류·지형·방위 배치는 새로고침과 보기 전환에도 유지합니다.
- 낮·밤은 같은 풍경의 조명만 바뀝니다.
- 종류와 지형 세부용 시드를 분리하면 조정과 재현이 쉽습니다.
- 향후 사용자가 풍경을 바꾸는 기능을 넣을 때만 재추첨합니다.

방문마다 재추첨하면 장소가 바뀌는 느낌이 강하고, 날짜 기반은 자정 전환이 어색합니다. 위치 기반은 실제 지리와 일치하지 않으면서 지리적으로 정확하다는 인상을 줄 수 있고, GPS 흔들림에 따른 변경도 관리해야 합니다.

세 종류는 화면 전체의 **주 풍경**으로 뽑는 것이 좋습니다. 방위 구간마다 도시·산·바다를 무작위로 붙이면 해안과 지형 연결부가 더 큰 작업이 됩니다.

## 3. 구현 방식·성능·용량

### 추천: CPU에서 정적인 형태 생성 + 한 패스 셰이더 합성

시드로 능선·구역 정보를 한 번 생성하고, 작은 데이터 텍스처로 전달하는 방식을 우선 추천합니다. 외부 라이브러리나 빌드는 필요 없습니다.

| 방식 | 장점 | 부담 |
|---|---|---|
| 매 픽셀 절차적 생성 | 추가 이미지 없음, 시간·방위 대응이 자유로움 | 여러 층의 해시·노이즈가 누적되고 미세 패턴이 흔들리기 쉬움 |
| 파노라마 이미지 | 사진 수준의 형태를 빠르게 확보 | 360° 이음매, 촬영 높이, 고정된 조명·반사, 시각별 변형·용량·권리 관리 |
| **정적 데이터 + 셰이더** | 반복 노이즈 계산을 줄이고, 조명·안개·반사는 동적으로 유지 | 데이터 형식과 필터링 설계가 필요함 |

사진 파노라마는 이번 1차 구현에는 추천하지 않습니다. 해·달이 실제 방위로 움직이는 구조에서 사진에 이미 구워진 노을과 반사는 충돌하기 쉽습니다.

예를 들어 `1024×4 RGBA8` 데이터 텍스처는 기본 레벨 **16KiB**, `256×256 RGBA8` 도시 패턴은 **256KiB**입니다. 밉맵을 모두 만들면 각각 대략 1/3이 더 필요합니다. 높이 데이터는 채널을 묶어 정밀도를 확보하고, 색 패턴과 같은 방식으로 무조건 필터링하지 않습니다.

런타임 생성이면 추가 이미지 다운로드는 0입니다. 추가 코드의 압축 용량은 **확실하지 않음**입니다. 참고로 이미지 방식의 `2048×512 RGBA8` 한 장은 압축 파일 크기와 별개로 밉맵 포함 약 **5.33MiB**입니다.

### +15% 이내 성능 목표

현재는 움직임에 따라 최대 30/60fps, 정지 시 약 160ms 간격으로 WebGL을 다시 그립니다. **바다 애니메이션 때문에 정지 상태도 60fps로 바꾸면 안 됩니다.** 프레임당 비용과 초당 총비용을 함께 관리해야 합니다.

초기 제한은 다음이 적절합니다.

- 추가 드로콜·후처리 패스 없음
- 산 3층, 도시 윤곽 최대 2층
- 풍경 데이터 조회는 해당 픽셀당 우선 2~4회 수준
- 바다 파결은 저주파 1~2개
- 지형 레이마칭·다중 반사 없음
- 하늘 픽셀과 완전히 가려진 바닥 픽셀에서는 풍경 계산 생략

현재 `main()`은 바닥 뒤의 `sky()`도 계산합니다. 불투명 지표 아래에서 비싼 천체 계산을 생략할 여지는 있지만, 분기 효율과 셰이더 복잡도 때문에 절감량은 **확실하지 않음**입니다.

+15%는 **동일 장면의 GPU 시간 중앙값과 p95를 기준 대비 1.15배 이하**로 정의하는 것이 좋습니다. 예를 들어 기존 GPU 시간이 4ms라면 목표는 4.6ms 이하입니다. FPS만으로는 여유 성능에 가려진 증가를 놓칠 수 있습니다. 지원 기기에서는 비동기 GPU 타이머를 사용하고 disjoint 결과는 버립니다. [Khronos 확장 명세](https://registry.khronos.org/webgl/extensions/EXT_disjoint_timer_query_webgl2/)

실기기 측정 전에는 **15% 달성을 보장할 수 없음**입니다.

## 4. 합성 순서와 위험·검증

### 권장 합성 순서

1. 하늘 바탕·구름·해·달·별
2. 먼 지표 → 가까운 지형·건물, 거리별 대기 원근
3. 유리 격자·유리 반사
4. 방위 글자
5. 기존 바닥 합성
6. 실내 조명 빔
7. 최종 디더링

이는 실제로 일곱 패스를 만들자는 뜻이 아니라, 현재 한 패스 안의 계산·합성 순서입니다.

핵심 수정점은 `above`입니다. **고도 0°에서 천체를 감추는 마스크를 유지한 채 풍경만 내리면 안 됩니다.** 지표·능선·건물의 가시성 마스크가 천체를 가려야 합니다. 원반과 별은 가리되, 넓은 대기광은 수평 부근에 남길 수 있습니다.

`uSolar.z`, `uLunar.x`도 고도 0° 부근을 기준으로 가시성을 줄이므로 함께 검토해야 합니다. 또한 `bgastro.js`는 현재 해에는 굴절을 적용하지 않고 달에는 적용합니다. 음의 고도에서도 달 보정이 들어가므로, 이번 기하와 정확한 출몰 시각의 일관성은 별도 정리가 필요합니다.

렌즈 고스트·화면 플레어는 **광원이 지형에 가려진 정도를 먼저 반영**해야 합니다. 반면 넓은 하늘 산란광까지 같은 마스크로 잘라서는 안 됩니다. 방위 글자는 광원 주변 대비를 조절하더라도 지형 뒤로 숨기지 않습니다.

### 위험과 검증 방법

| 위험 | 대응·검증 |
|---|---|
| 수평선이 딱딱한 선처럼 보임 | 1픽셀 수준의 기하 경계 AA와 넓은 대기색 변화를 분리합니다. 굵은 수평선을 추가하지 않습니다. |
| 안개·밤바다 밴딩 | 기존 최종 디더링을 활용합니다. 저밝기 화면에서 확인하고, 시간마다 바뀌는 노이즈로 얼룩을 만들지 않습니다. |
| 불빛·파결 반짝임 | 셀보다 픽셀이 커지면 평균 밝기로 전환합니다. 먼 창문을 점광원으로 계속 유지하지 않습니다. |
| 방위 이음매·반복 | 풍경은 360° 주기로 생성하고 끝값·기울기를 연결합니다. 기존 하늘의 3회 반복 좌표를 풍경에 재사용하지 않습니다. |
| 분기 내부 미분 | `fwidth` 등 필요한 미분은 분기 전에 계산합니다. 특히 방위각 ±π 이음매를 검사합니다. |
| 줌에 따른 풍경 미끄러짐 | 돔 좌표 `q`와 외부 방향 `d`를 분리합니다. 줌 0·0.3·0.6에서 같은 지형의 방위가 유지되는지 확인합니다. |
| 실내·바깥 전환 | 지형·수평선·시드는 유지하고 팔레트와 조명만 전환합니다. 현 코드는 보기 전환 시 즉시 다시 그리므로 전환 보간은 별도 작업입니다. |
| 하늘 구름이 땅 위에 붙음 | 기존 구름은 풍경 뒤에 두고, 풍경 위에는 별도의 흐린 대기 성분만 사용합니다. |
| 성능 평균은 통과하지만 특정 장면이 느림 | 전체 지표가 크게 보이는 화면, 밤 도시, 해·달 반사 장면을 각각 측정합니다. |

**실내 적용은 같은 지형·분홍 팔레트·낮은 대비를 추천**합니다. 실내에서만 풍경을 없애면 보기 전환 때 바닥 아래 세계가 사라집니다. 다만 실내에도 ‘실제 야간 도시 조명’을 사용할지는 취향의 문제로 **확실하지 않음**입니다. 1차 검증은 바깥 보기부터 진행하는 편이 좋습니다.

검증 조합은 최소한 다음을 포함해야 합니다.

- 북쪽 이음매를 포함한 360° 회전, 느린 회전과 빠른 회전
- 고도 +10°·0°·−15°·−30°·−55°, 줌 0·0.6
- 해 고도 +15°·0°·−1°·−2°·−6°·−12°
- 달의 위상과 수평선 통과, 산·건물 뒤 가림
- 밝은/어두운 테마, 실내/바깥, 센서 유무, 텍스처 로딩 전후
- Android·iPhone 실기기에서 같은 시드로 충분히 예열한 A/B 성능 비교

## 5. 단계별 구현 순서

1. **기준 측정:** 현재 화면·GPU 시간·정지 시 갱신 횟수를 기록합니다.
2. **기하만 구현:** 2km 기준의 단색 구형 지표와 가림 마스크를 넣고, 줌·기울기·수평선 접점을 확인합니다.
3. **천체 가림 통합:** 기존 0° 마스크와 태양·달 가시성 곡선을 검토해, 수평선에 닿기 전에 사라지는 현상을 해결합니다.
4. **공통 대기색:** 하늘 바탕색 계산을 공유하고 낮·노을·밤의 지표색을 맞춥니다.
5. **산부터 완성:** 3층 능선으로 거리감과 지표 연속성을 검증합니다.
6. **바다 추가:** 반사 없는 수면부터 시작해 해·달 방향 반사를 추가합니다.
7. **도시 추가:** 큰 구역 무늬 → 건물 윤곽 → 밤 불빛 순으로, 단계마다 aliasing과 비용을 확인합니다.
8. **시드 저장·실내 전환:** 같은 세계가 유지되는지 검증하고 분홍 팔레트를 적용합니다.
9. **렌즈 효과 통합·성능 판정:** 광원 가림을 공유하고 +15% 기준을 검사합니다. 초과하면 창문·파결·거리층 세부부터 줄입니다.

첫 구현의 승인 기준은 **수평선과 천체 가림의 일관성, 아래로 펼쳐지는 지표, 안정된 야간 불빛, +15% 이내 측정 결과**로 잡는 것이 적절합니다.
