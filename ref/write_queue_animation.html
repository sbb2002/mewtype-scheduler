충돌이 왜 나는가

아래 두 규칙만 이해하면 이후 애니메이션이 왜 그렇게 흘러가는지 보인다.

규칙 1 · 충돌 판정

GitHub Contents API의 PUT은 "내가 읽었던 브랜치 상태"를 기준으로 커밋한다. 그 사이 다른 파일이라도 같은 브랜치에 커밋이 하나 생기면 409 Conflict. 실제 로그: tweets.json: PUT 409 Conflict ... is at 3fde310… but expected 64b6e38…

규칙 2 · 요청 1건 ≠ 커밋 1개

소식 트윗 1건 인입 = notice added + undo snapshot(admin_state.json) + monitor notice(이벤트 로그) 등 여러 커밋. 개인 트윗 1건 = tweet added (+sweep/archive) + monitor tweet. 커밋이 늘수록 겹칠 기회도 늘어난다.

제어 채널의 콘텐츠 쓰기 14종을 백엔드 POST /write 로 보내 백엔드가 한 번에 하나씩 처리하도록 바꿨다. 콘텐츠 커밋끼리는 줄을 서지만, 문제가 둘 남아 있다.

문제 (a)

백엔드는 concurrency=1 · max-instances=1이라 요청을 한 번에 하나씩만 처리한다. 그런데 잡 안에서 느린 외부 호출(vxtwitter 원문 조회·YouTube videos.list·외부 LLM 번역/참여판정/예고확인/비전 OCR)이 그대로 돈다. 이 동안 /tick·/wake도 뒤에서 기다린다 — 평소엔 문제없다 (/write 중앙값 0.5초, Groq 중앙값 0.43초), 외부 장애가 겹칠 때만 같이 막히는 구조다.

모델당 최대 ≈63초 메인→폴백 ≈126초 5회 판정 최악 ≈630초 /write 타임아웃 60초 gunicorn 120초
문제 (b)

모니터 로그(monitoring/events-*.jsonl)·admin_state.json (undo·마법사)·control.json 쓰기는 여전히 제어 채널이 직접 커밋한다. 큐를 우회하므로 이들끼리, 또는 이들과 큐 잡 사이의 409 충돌 가능성이 남아 있다.

(참고) 이 배포에는 /ingest 개인 트윗 경로가 변수 버그로 500을 내는 별도 장애가 있다 — 여기서는 다루지 않음.

B안 — 모니터 로그 줄이기 + 재시도 2→5회 + 지터(0.3~1.5초)

검토했다가 기각한 방안. 같은 폭주 상황을 다시 재생한다.
