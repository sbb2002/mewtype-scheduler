## 3. 점검 중 드러난 문제 (기능 사용과 별개)

1. **#12 불발이 실제로 반복되고 있다.** 09-23~27에 YouTube 앱 알림 24건이 즉시 확인을 요청했지만 예약되지 않았다(코드 · 배포 스크립트 기준 — Cloud Tasks 쪽 실패 로그는 `log.debug` 라 이벤트 로그에 없음).
2. **업스트림 알림의 24%가 버려진다.** "バンドリ！アワーノーツ" 계정 알림 66건(09-23~27)이 소식 · 예고 어느 쪽으로도 반영되지 않았다(`공식 · 스케줄 아님`). 게임 계정이라 의도된 무시일 수 있지만, 폰(업스트림)에서 이 계정 알림을 계속 중계할 필요가 있는지 확인 필요.
3. **`/undo` 는 운영자의 직전 작업이 아닐 수 있다.** undo 슬롯은 하나뿐이고 자동 작업(URL 확정 예고 등)도 덮어쓴다. 지금 `/undo` 를 누르면 운영자가 한 일이 아니라 09-27 자동 반영이 되돌려진다.
4. **예고 상태 왕복이 여전히 많다.** `announced→watching` 150 · `watching→announced` 137 (09-09~28 합계). 배선 지도에 적힌 기존 문제.
5. **릴레이 로그가 소음이 많다.** 릴레이 279건 중 260건이 `mode: none`(스케줄 아닌 공식 트윗마다 한 줄).

## 4. 웹 관리 페이지 설계에 주는 시사점

**옮길 것 (실사용)** — 화면 우선순위 순
1. **예고 목록 + 편집 · 삭제** (13 · 14d · 14g): 가장 많이 쓴 조작. 한 화면에서 목록을 보고 여러 필드를 한 번에 고치는 폼이 마법사를 대체한다. terminate(재등록 차단)는 삭제 옵션 체크박스로.
2. **예고 원문 수동 투입** (14a): 붙여 넣기 → 파싱 미리보기 → 확정. 지금은 결과를 보고서야 알 수 있는 파싱 결과를 반영 전에 보여줄 수 있다.
3. **유실 원문 재투입** (18) · **모니터 리포트** (17): 목록에서 골라 재투입, 리포트는 웹 모니터와 합치기.
4. **되돌리기** (14j): 웹에서는 **작업 이력 목록**(누가 · 언제 · 무엇을)을 보여주고 골라서 되돌리게 — §3-3 문제(슬롯 하나 · 자동 작업에 덮임)를 함께 해결.

**웹에만 두고 텔레그램에서 뺄 것 (미관측 · 드묾)** — 14b · 14c · 14e · 14f · 14h · 14i · 15 는 기록상 거의 안 쓰였다. 웹 화면에는 소식 · 트윗 탭에 편집/삭제 버튼 정도로 가볍게 두고(자동 경로가 잘못 반영했을 때의 교정 수단), 별도 흐름은 만들지 않는다.

**텔레그램에 남길 것** (사용자 결정): 알림 DM(19 · 20 · 22) + 비상 명령 `/status` `/pause` `/resume` + 로그인 링크 `/admin`.

**없앨 것** — §2의 사장 요소 전부, 명령 별칭, 마법사 상태 슬롯(`pending_ingest` · `pending_notice` · `pending_notice_edit` · `pending_op` · `pending_member`), 60초 만료 로직. 그러면 `ops` 브랜치에 남는 것은 control · suppress · 편집 락 · 작업 이력(undo) 정도로 줄어든다.

**사용자 결정 (2026-09-28)**

- §3-2 아워노츠 계정 알림: 폰에서 계속 보낼 수 있으나 **처리 규칙은 아직 만들지 않는다** — 현재처럼 받고 반영하지 않는다.
