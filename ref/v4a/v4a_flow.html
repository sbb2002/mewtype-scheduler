mewtype-scheduler · v4a 설계안

v4a 흐름도 — 서비스 2개 유지 + 적용 큐 일원화 + 웹 관리 페이지

새 서비스 · 새 제품 없이, 이미 쓰고 있는 Cloud Tasks 큐의 역할을 넓혀 적용 큐로 쓴다. data 브랜치를 쓰는 곳은 쓰기 서비스 하나, 접수 서비스는 적용 큐에 적재하고 바로 돌아가며, "즉시 wake" 같은 지름길은 전부 reconcile(전체 | 영상 하나) 요청으로 통일한다. 텔레그램 마법사 명령은 웹 관리 페이지 하나로 옮기고(로그인 = 텔레그램 일회용 링크), 텔레그램은 알림과 비상 명령만 남긴다. 운영 상태는 새 ops 브랜치로.

현행 26가지 기능(9 · 14번 세부 포함 37행) + 신규 1(관리 페이지 로그인)이 모두 이 구조에서 동작한다 — 묶음 탭 → 기능 칩을 고르면 v4a 경로가 흐른다. 흰 테두리 번호 = v3.8.10에서 바뀐 단계.

원칙

v4a의 모든 변경은 이 다섯 줄로 판단한다.

01

data를 쓰는 곳은 쓰기 서비스 하나

동시 1 · 인스턴스 1 유지 — 정기 reconcile과 작업 적용이 같은 인스턴스에서 한 줄로 선다.

02

접수 서비스는 적재하고 바로 돌아간다

동기 /write(60초 대기 · 429 백오프) 대신 Cloud Tasks 적재. 바쁘면 큐가 알아서 재시도.

03

지름길 대신 reconcile

즉시 wake · 편집 후 재확인 · /resume 후 tick → 모두 reconcile(범위) 적재. 자기 호출 없음.

04

느린 외부 호출은 접수 서비스에서

LLM · vxtwitter · videos.list · yt-dlp · OCR. 번역 재시도도 접수 서비스로.

05

운영 조작은 관리 페이지, 운영 상태는 ops

텔레그램은 알림 + 비상 명령만. 대화 상태를 저장하지 않는다. control · suppress · 작업 이력은 ops 브랜치.

사용자 결정 (2026-09-28)

운영 조작텔레그램 마법사 명령을 웹 관리 페이지 하나로 — 마법사는 급할 때는 되지만 복잡한 수정이 불편했음
로그인텔레그램 일회용 링크 (/admin → 서명된 짧은 수명 링크 DM)
텔레그램 역할알림 DM + 비상 명령 /status · /pause · /resume · /admin 만
드문 기능9b(비YouTube URL → 소식) · 크로스오버 비전 OCR · 11(회원 전용 라이브) · 날짜만 있는 예고 — 유지
아워노츠 계정 알림폰에서 계속 보낼 수 있으나 처리 규칙은 만들지 않음 (현재처럼 받고 반영 안 함)
기능 전부현행 26가지 기능(37행)은 전부 v4a에서 동작

v4a 흐름도

선 색 = 단계 종류. 점선 박스 = 서드파티. NEW 표시 = v4a에서 새로 생기는 구성 요소. 흐린 회색 선 = 전체 배선 골격.

Terminology — v4a 용어

이름 규칙: 서비스는 역할로, 큐는 전달하는 엔드포인트 이름으로, Scheduler 잡은 부르는 동작으로. 현재(v3.8.10) 이름은 docs/TERMINOLOGY.md 기준이며, v4a 용어는 채택 · 구현 시점에 그 문서로 옮긴다.

동작 용어정의
reconcile(범위)"지금 상태가 어때야 하나"를 다시 계산해 data에 맞추는 동작. 범위는 전체(RSS + 추적 중 전부) 또는 영상 하나. 누가 요청하든 같은 함수 — 정기 reconcile 잡은 /reconcile 로, 나머지는 적용 큐 → /apply 로.
적재적용 큐 · 가공 큐에 작업을 넣는 것. 넣으면 바로 돌아가고 결과를 기다리지 않는다.
작업 · 작업 id적용 큐로 전달되는 요청 하나와 그 식별자(태스크 이름으로도 써서 중복 적재 방지). 종류는 현재 writers.py 잡 종류 재사용 + reconcile + 관리 조작. 서로 독립 · 멱등이어야 한다.
작업 결과쓰기 서비스가 작업을 적용한 뒤 monitoring 이벤트 로그에 작업 id와 함께 남기는 한 줄. 관리 페이지가 조회해 반영 · 충돌 · 실패를 보여준다 (선택).
열람 값 · 충돌폼을 열 때 본 필드 값. 제출 때 함께 보내고, 적용 때 현재 값과 다르면(그 사이 reconcile이 바꿈) 충돌로 알린다. 편집 락이 필요 없다.
작업 이력운영자 조작마다 ops에 남기는 기록. 되돌리기는 이력에서 골라 항목 단위로 한다 (선택) — 현재 /undo 는 슬롯 하나 · 파일 통째라 자동 작업에 덮이고 거의 항상 거부된다.
로그인 링크텔레그램 /admin 에 봇이 운영자 chat_id로 보내는 일회용 링크. 서명된 토큰 · 짧은 수명 · 한 번 쓰면 무효 → 세션 쿠키(HttpOnly · Secure · SameSite=Strict).
알림 DM상태 전이 · 유실 · 매일 멤버 현황처럼 운영자가 조작하지 않아도 오는 DM. 텔레그램에 유지된다.
마지막 시도적용 큐가 재시도하다 한도에 이른 전달. 쓰기 서비스가 판별해 유실 큐에 적재한다 (판별 헤더는 확인 필요).
리소스 이름 전환Cloud Run 서비스 이름을 실제로 mewtype-intake · mewtype-writer 로 바꾸는 일. URL이 바뀌므로 폰 Automate URL · Telegram webhook · monitor.html 주소 · OIDC · IAM을 같이 갱신 (아래 "대가").

기능 커버리지

현행 기능 전부가 v4a에서 동작한다. "변경" = 경로가 바뀜(사용자가 보는 동작은 같음). 번호를 누르면 위 흐름도에서 재생된다.

#묶음기능v3.8.10 대비트리거쓰는 곳

대가 · 확인 필요

얻는 것만 있는 구조는 없다. 상세와 근거는 v4a_design.md §10.

항목내용
공개 관리 화면data를 고칠 수 있는 화면이 인터넷에 생긴다. 로그인 링크 · 세션 · CSRF를 제대로 구현해야 하고, 현재 공개 서비스의 ALLOW_UNAUTH=1 이 oidc.verify_request 를 우회하는 문제(메모리 09-17 안건)를 먼저 해결해야 한다 (구현 시 코드 확인 필요).
결과가 비동기조작 결과는 적재 뒤 작업 결과 기록을 관리 페이지가 조회해 보여준다(수 초~). 목록 조회 · 미리보기는 즉시.
항목 단위 되돌리기되돌리기 작업 종류를 새로 만들어야 한다. 되돌리는 사이 그 항목이 또 바뀌었으면 충돌로 알림.
묶음 커밋 없음1건 = 1커밋. v3.8.2 측정(약 3.3초/커밋) 대입 시 60건 버스트는 약 3분 + 정기 reconcile 실행분. raw CDN 캐시가 원래 최대 약 5분 — 추정, 재측정 필요.
순서 · 중복Cloud Tasks는 전달 순서를 보장하지 않고 드물게 중복 전달할 수 있다 (확인 필요) → 작업은 독립 · 멱등(id 기준 upsert)이어야 한다. 작업 id를 태스크 이름으로 써서 중복 적재 방지. 전 작업 종류 점검 필요.
데드레터 없음Cloud Tasks에는 DLQ가 없다 (확인 필요) → 최대 시도 횟수 + 마지막 시도 판별(X-CloudTasks-TaskRetryCount, 확인 필요)로 lost_queue 적재.
번역이 커밋 두 번reconcile이 발견한 방송 제목은 원문으로 먼저, 번역은 가공 큐를 거쳐 나중에 커밋.
리소스 이름 전환Cloud Run 서비스는 이름을 바꿀 수 없어 새로 배포 → URL이 바뀐다. mewtype-telegram → mewtype-intake 전환 시 업스트림 폰 Automate URL(경로 /ingest는 그대로) · Telegram webhook 재등록 · monitor.html 주소 · OIDC audience · IAM을 같이 갱신. 큐 · Scheduler 잡은 v4a 전환 때 어차피 새로 만들어 추가 비용 작음.
ops 이관 · /enrich 인증control · suppress를 읽는 곳(reconcile 포함)을 새 브랜치로. 현재 admin_state의 대기 슬롯 7종 · 편집 락은 버린다. /enrich는 공개 서비스 경로라 앱 안 OIDC 검증에 의존.
