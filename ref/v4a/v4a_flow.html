mewtype-scheduler · v4a 설계안

v4a 흐름도 — 서비스 2개 유지 + 쓰기 큐 일원화

새 서비스 · 새 제품 없이, 이미 쓰고 있는 Cloud Tasks 큐를 우편함으로 쓴다. data 브랜치를 쓰는 곳은 백엔드 하나, 입구는 큐에 넣고 바로 돌아가며, "즉시 wake" 같은 지름길은 전부 reconcile(전체 | 영상 하나) 요청으로 통일한다. 운영 세션 상태는 새 ops 브랜치로 뺀다.

현행 26가지 기능(9 · 14번 세부 포함 37행)이 모두 이 구조에서 동작한다 — 묶음 탭 → 기능 칩을 고르면 v4a 경로가 흐른다. 흰 테두리 번호 = v3.8.10에서 바뀐 단계.

원칙

v4a의 모든 변경은 이 다섯 줄로 판단한다.

01

data를 쓰는 곳은 백엔드 하나

동시 1 · 인스턴스 1 유지 — tick과 큐 작업이 같은 인스턴스에서 한 줄로 선다.

02

입구는 적재하고 바로 돌아간다

동기 /write(60초 대기 · 429 백오프) 대신 Cloud Tasks 적재. 바쁘면 큐가 알아서 재시도.

03

지름길 대신 reconcile

즉시 wake · 편집 후 재확인 · /resume tick → 모두 reconcile(범위) 적재. 자기 호출 없음.

04

느린 외부 호출은 제어 채널에서

LLM · vxtwitter · videos.list · yt-dlp · OCR. 번역 재시도도 제어 채널로.

05

운영 세션 상태는 ops 브랜치로

마법사 · 확인 대기 · 편집 락 · undo · control. 공개 데이터와 충돌하지 않는다.

v4a 흐름도

선 색 = 단계 종류. 점선 박스 = 서드파티. NEW 표시 = v4a에서 새로 생기는 구성 요소. 흐린 회색 선 = 전체 배선 골격.

기능 커버리지

현행 기능 전부가 v4a에서 동작한다. "변경" = 경로가 바뀜(사용자가 보는 동작은 같음). 번호를 누르면 위 흐름도에서 재생된다.

#묶음기능v3.8.10 대비트리거쓰는 곳

대가 · 확인 필요

얻는 것만 있는 구조는 없다. 상세와 근거는 v4a_design.md §9.

항목내용
결과 DM이 비동기명령 결과가 커밋 뒤 백엔드에서 온다. 결과 DM 조립을 /apply 작업 안으로 옮겨야 한다(apply_preview_edit는 이미 이 방식). 조회 · 마법사 질문은 지금처럼 즉시.
묶음 커밋 없음1건 = 1커밋. v3.8.2 측정(약 3.3초/커밋) 대입 시 60건 버스트는 약 3분 + tick 실행분. raw CDN 캐시가 원래 최대 약 5분 — 추정, 재측정 필요.
순서 · 중복Cloud Tasks는 전달 순서를 보장하지 않고 드물게 중복 전달할 수 있다 (확인 필요) → 작업은 독립 · 멱등(id 기준 upsert, undo는 expected_sha)이어야 한다. 전 잡 점검 필요.
데드레터 없음Cloud Tasks에는 DLQ가 없다 (확인 필요) → 최대 시도 횟수 + 마지막 시도 판별(X-CloudTasks-TaskRetryCount, 확인 필요)로 lost_queue 적재.
번역이 커밋 두 번tick이 발견한 방송 제목은 원문으로 먼저, 번역은 가공 큐를 거쳐 나중에 커밋.
ops 이관 · /enrich 인증admin_state · control을 읽는 모든 곳 변경. /enrich는 공개 서비스 경로라 앱 안 OIDC 검증에 의존.
