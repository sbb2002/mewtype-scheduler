## 1. 풀려는 문제

- `bang_dream_on`(アワーノーツ) X 계정을 운영자가 팔로우해서 알림이 업스트림으로 들어온다(09-23 이후 76건/9일). 대부분은 게임 공지(점검 · 사과 배포 등)고 유메미타 관련은 일부다.
- 소식판(글 1건 = 소식 1건)은 「같은 이벤트의 예고 → 개최 → 재공지 → 종료」를 못 다룬다. 날짜가 다르면 LLM 중복 판정(`llm.duplicate_notice`, 같은 날짜만 비교)이 안 걸려서 재공지가 별개 소식으로 올라갔다.
- 결정(운영자): 게임 소식은 소식판에 섞지 않고 **소식 란 첫 줄의 이벤트 배너**로 보인다. 이벤트는 개최일 · 종료일을 가지고, 보류되면 `mm.dd(보류)`로 15일 유지 후 내리고, 재공지가 기간을 알려주면 다시 올린다. 종료일이 지나면 내린다.

## 3. 데이터 — `events.json` (가칭, data 저장소 · 공개 콘텐츠)

`notices.json` 과 같은 성격(프론트가 읽는 공개 파일)이므로 `data` 쪽에 둔다. 운영 상태 전용인 `ops` 로 보내는 파일 목록(`storage.OPS_PATHS`)에는 넣지 않는다.
직렬화 규칙은 전 모듈 공통(`sort_keys=True, indent=2, ensure_ascii=False`, 끝 개행 1개).

```json
{ "generated_at": "…Z",
  "events": [ {
    "id": "ev_<해시>",            // 이벤트 키 — 이름 정규화 + 처음 시작일 기준(재공지로 갱신돼도 안 바뀜)
    "name_ja": "チャレンジライブイベント「アイの奔流 AtoZ」",
    "name_ko": "사랑은 격류 AtoZ 챌린지 라이브",
    "banner_url": "https://pbs.twimg.com/media/….jpg",   // 링크만 저장, 이미지를 복사하지 않음(§9 법률 결정 대기)
    "start_at": "2026-09-30T09:00:00Z",   // UTC ISO. 시각 미정이면 start_time_tbd=true + 날짜만
    "end_at":   "2026-10-08T11:59:00Z",   // 아직 모르면 null
    "state": "announced | hold | live | ended",   // 저장값은 hold 여부 + 날짜. 표시 상태는 §5 에서 파생
    "hold_anchor": "2026-09-28T06:00:00Z",        // 보류 시작 시 표시했던 날짜(원래 시작일). hold 일 때만
    "hold_until":  "2026-10-13T06:00:00Z",        // hold_anchor + 15일. 지나면 내림
    "src_ids": ["2103…", "2105224502036853086"],  // 이 이벤트를 만든/갱신한 트윗 id
    "first_seen": "…Z", "last_updated": "…Z",
    "expires_at": "…Z"            // ended 또는 hold 만료 시 정리 기준(§6)
  } ] }
```

- `events_archive.json`(가칭): 내려간 이벤트 보관(`notice_archive.json` 과 같은 방식, id dedupe).
- 계약 문서: 구현할 때 `docs/SPEC.md` 에 계약을 먼저 추가한다(코드 변경 시 문서 먼저 원칙).

## 4. 인입 흐름

기존 파이프라인 관례를 그대로 따른다: **제어 채널에서 준비(외부 호출) → 적용 큐 잡은 커밋만**(`_prepare_notice` · `_commit_notice` 와 같은 구조, v3.7.1 A-1).

```
폰(Automate) → POST /ingest
  ① vxtwitter/fxtwitter 로 원문 · 작성자 · 첨부 이미지 URL · 게시 시각 확보  (이미 하는 일)
  ② 작성자 핸들이 「게임 계정 허용 목록」에 있나?
       없음 → 지금과 동일(_official_skip_reason 이 건너뜀)
       있음 → 소식 · 스케줄 파이프라인에 **안 태우고** 이벤트 경로로
  ③ 판정 LLM 1회 (아래 §4-1)
  ④ 결과가 none 이 아니면 적용 큐에 `apply_event` 잡 적재 → events.json 커밋 + undo 스냅샷 + LLM 판단 기록
```

- 허용 목록 위치(가칭): `config/channels.json` 에 `game_accounts: {"bang_dream_on": {"name_ko": "…"}}`. 핸들은 fxtwitter 작성자 값으로 확인했다(`bang_dream_on`, 표시명 バンドリ！アワーノーツ).
- `_official_skip_reason`(`telegram_app.py:2573`)은 건드리지 않고, 그 **앞**에서 허용 계정을 분기한다(공식 = BDP 규칙은 그대로 유지).
- 같은 글을 폰이 재전송해도 안전해야 한다 — 이벤트 갱신은 `src_ids` 에 트윗 id 가 이미 있으면 no-op(10-02 중복 인입 시험에서 소식 · 트윗이 같은 방식으로 걸러졌다).

### 4-1. 판정 LLM (글 1건 = 호출 1회)

입력: 글 본문 · 게시 시각(KST 포함) · 현재 활성 이벤트 목록(id · 이름 · start/end · state — 보통 1~2건이라 작다).
출력(구조화 JSON, `json_schema strict`, 근거 `reason` 한 문장 필수):

| action | 뜻 | 서버 처리 |
|---|---|---|
| `none` | 유메미타 · 멤버와 무관 / 같은 이벤트인데 새 사실 없음(당일 재공지 · 독려) | 아무것도 안 함, 기록만 |
| `new` | 새 이벤트 | 항목 생성 |
| `update` | 같은 이벤트의 새 사실(기간 · 곡 · 이미지) | 해당 id 갱신. 보류 중이면 날짜가 확정된 경우에 한해 해제 |
| `hold` | 개최 보류 · 중단 | `hold_anchor`=현재 시작일, `hold_until`=+15일 |
| `reschedule` | 새 날짜 공지 | 날짜 교체, hold 해제 |
| `cancel` | 개최 취소 / 조기 종료 | ended 로 내려감 |

코드가 LLM 출력을 **검증**한다(LLM 값을 그대로 쓰지 않음): 날짜 형식 · `start ≤ end` · 현재 기준 ±1년 이내 · `event_ref` 가 실제 활성 id 인지. 어긋나면 `none` 처리 + monitor `degraded`.
「このあと18:00より」 같은 상대 표현은 게시 시각 + JST 를 프롬프트에 함께 줘서 절대 시각으로 받는다(코드가 UTC 로 변환).
LLM 5회 실패 시: 이벤트는 **등록하지 않음**(잘못 올라간 배너가 소식 중복보다 눈에 띄므로 소식과 반대 기본값) + monitor 이벤트 `degraded` + 관리 페이지 원문 투입으로 복구 가능.

호출량: 허용 계정 인입 글 수와 같다 — 09-23~10-01 기준 하루 평균 약 8건, 많은 날 약 20건(최대 재시도 5회면 최악 5배). Groq 일일 한도는 **확인 필요**(콘솔 확인).

## 5. 표시 상태 파생 (저장 안 함 — `statemachine.derive` 와 같은 발상)

| 조건(지금 시각 기준) | 표시 | 배너 |
|---|---|---|
| hold 이고 `hold_until` 이전 | 보류, `mm.dd(보류)` | 표시(흑백) |
| hold 이고 `hold_until` 이후 | — | 내림 → archive |
| 시작 전 | 예정 | 표시 |
| 시작 ≤ 지금 < 종료(또는 종료 미정) | 진행 중, D-day · 진행률 | 표시 |
| 종료 ≤ 지금 | — | 내림 → archive |

`end_at` 이 null 인 진행 중 이벤트의 상한은 **결정 대기**(§9).

## 6. 정리(sweep)

정기 reconcile(10분)에 이벤트 sweep 를 붙인다(소식 `notice_sweep` 잡과 같은 위치). `expires_at` 지난 항목을 `events_archive.json` 으로 옮긴다.
`expires_at` = ended 는 종료 시각, hold 는 `hold_until`. 프론트는 만료 전이라도 §5 로 숨긴다(서버 지연 대비).

## 7. 프론트

- `config.js`: `EVENTS_URL`(`getDataUrl` — Vercel 이면 데이터 저장소 raw, 로컬이면 `/data/events.json`). 로컬 러너의 `_DATA_FILES`(`local_runner.py:32`)에 `events.json` 추가.

- 이미지는 `<img referrerpolicy="no-referrer">` + 로드 실패 시 이미지 칸만 숨김.
- 카운트다운 · 진행률은 기존 `main.js` 틱에 재사용.

## 8. 관리 페이지 · 되돌리기

- 관리 페이지: 소식 탭 위에 「이벤트」 영역 — 목록 · 수정(이름 · 기간 · 상태 · 이미지 URL) · 삭제. 수동 투입은 이번엔 안 만들고 자동 판정이 놓친 글은 기존 「원문 투입」 이 이 경로로 가게 한다(허용 계정 글이 아니어도 관리자가 넣으면 판정만 거침).
- LLM 판단 기록: `_llm_record(kind="event_judge", undo=…)`. 되돌리기 종류를 `restore_event`(변경 전 항목 스냅샷으로 복원 / 새로 만든 항목이면 삭제)로 `_llm_undo` 에 추가. 「그때 바뀐 항목만 되돌리고 그 뒤 바뀐 건 건너뜀」 원칙 그대로.
- `none` 판정은 검토용(되돌릴 데이터 없음)으로 기록 — 관리 페이지 작업 탭 「LLM 판단」 필터에서 근거를 본다.

## 9. 열린 결정 (운영자)

1. **이름**: 「이벤트 배너」 · `events.json` 가칭 확정(TERMINOLOGY 추가).
2. **동시 이벤트**: 한 번에 몇 건까지 배너로 보일지(시안은 1건). 2건 이상이면 세로로 쌓을지 순환할지.
3. **이미지**: 링크만 저장하고 hotlink 할지, 자체 복사할지. 말풍선 트윗은 법률 자문으로 원문 이미지 재조립을 뺀 전례가 있어(v3.8.0) **사용 가능 여부 확인 필요**. 확인 전엔 이미지 없는 텍스트 배너도 가능하게 만든다.
4. **`end_at` 없는 진행 중**: 상한 일수(예: 30일) 후 자동 내림? 아니면 관리자가 내릴 때까지?
5. **`bang_dream_on` 글을 소식판에도 올릴지**: 권장은 안 올림(이벤트 경로만). 지금 v4a 소식판에 이 계정에서 온 항목이 이미 있다 — 그대로 두고 만료되게 할지.
6. **운영 반영**: 운영은 아직 이 계정 글을 소식으로 올린다(v3.8.10). 이 기능을 넣을 때 운영 소식과 이중 노출을 어떻게 정리할지.
