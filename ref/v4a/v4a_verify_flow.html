v4a 검증 흐름 — 흐름도대로 움직였나

v4a 로컬 시험판(브랜치 v4a)을 실제 구성 그대로 띄워 — Flask 접수 앱 + 쓰기 스레드 q-apply + 가공 스레드 q-enrich + _local/ 저장소 — 업스트림 알림 · 정기 reconcile · 관리 페이지 조작을 흘리고, 관측된 단계를 그대로 흐름도(v4a_flow.html)의 노드 · 경로 위에 재생한다. 외부 서비스(YouTube Data API · RSS · Groq · vxtwitter · yt-dlp · Telegram 전송)만 가짜로 바꿨다 — 그 밖의 코드 경로는 실제 코드다.

묶음 탭 = 시나리오, 기능 칩 = 동작 하나(알림 1건 · reconcile 1회 · 관리 조작 1건). 흰 테두리 번호 = 흐름도(설계)와 다른 단계 — 칩 아래 사유와 그 동작의 확인 결과가 함께 나온다.

흐름도와 다른 점

성격차이설명
로컬 한정접수 쪽이 적용 큐 결과를 기다린다흐름도 원칙 ②는 적재 후 바로 응답. 로컬 시험판은 현행 DM 문구를 유지하려고 submit_and_wait 로 기다린다. Cloud Tasks 는 결과를 돌려주지 않으므로 배포 단계에서 비동기 적재 + 작업 결과 조회로 바꿔야 한다.
로컬 한정업스트림 알림의 결과 DM 을 접수 쪽이 보낸다흐름도 #7 은 쓰기 서비스가 커밋 뒤 DM. 위와 같은 이유(결과를 기다리므로 기존 코드가 그 자리에서 DM).
로컬 한정정기 잡이 적용 큐를 거친다흐름도는 Scheduler → 쓰기 서비스 /reconcile 직접. 로컬은 스케줄러 스레드가 적용 큐에 reconcile 을 적재하고 q-apply 가 실행 — '같은 인스턴스에서 작업과 한 줄로 선다'는 설계 의도와 같은 결과.

보완 필요작업 이력 · 재등록 차단을 접수 쪽이 기록흐름도는 쓰기 서비스가 작업 결과와 함께 ops 에 기록. 로컬은 admin_api(접수)가 적재 결과를 받은 뒤 ops 에 쓴다. 결과를 기다리는 구조라 지금은 순서가 맞지만, 비동기로 바꾸면 쓰기 쪽으로 옮겨야 한다.

미검증#24 생존 신호 · #17 healthchecks/Vercel 조회 · #26 배포 · #10 비전 OCR로컬 시험판 설정에 healthchecks · Vercel 이 없고 배포는 하지 않는다. OCR 은 대상 이미지 소식을 재생하지 않았다.
