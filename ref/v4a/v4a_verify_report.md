## 1. 방법

| 층 | 내용 | 재현 |
|---|---|---|
| 모듈 self-test | 기존 29개 + 신규 7개 모듈의 `__main__` 스모크 | `python -m src.backend.<모듈>` |
| 시나리오 재생 | 로컬 러너와 같은 구성(Flask 접수 앱 + `q-apply` · `q-enrich` 워커 + `_local/` store)을 띄우고 업스트림 알림 · reconcile · 관리 페이지 조작을 흘림. **외부 서비스만 가짜**(YouTube Data API · RSS · Groq · vxtwitter · yt-dlp · Telegram 전송) — 그 밖은 실제 코드 | `python ref/v4a/verify/harness.py` → `trace.json` · `results.json` |
| 흐름도 대조 | 관측 이벤트(요청 · 외부 호출 · 적재 · 작업 실행 · 쓰기 · DM)를 흐름도 노드 이동으로 변환해 동작별로 비교 | `python ref/v4a/verify/gen_verify.py` → `v4a_verify_flow.html` |
| 브라우저 | Chrome 에서 로컬 러너 실동작 — 팬 화면 · 관리 페이지(로그인 · 탭 · 원문 투입 미리보기/확정 · 예고 편집) · 검증 페이지 렌더링 · 애니메이션 | 수동 |

저장소 **읽기**는 기록하지 않았다(쓰기만). 실제 폰 · 실제 API 로는 아직 돌리지 않았다 — 며칠 시험 운영이 그 몫.

## 3. 흐름도와 다른 점

동작 61개 중 45개에 흐름도와 다른 단계가 있다. 대부분이 아래 첫 줄(결과 대기) 하나 때문이다.

| 성격 | 차이 | 판단 |
|---|---|---|
| 로컬 한정 | 접수 쪽이 적용 큐 **결과를 기다린다**(흐름도 원칙 ②: 적재 후 바로 응답) | 현행 DM 문구를 그대로 쓰려는 선택(계획 §1). Cloud Tasks 는 결과를 돌려주지 않으므로 **배포 전 비동기 적재 + 작업 결과 조회로 바꿔야 함** |
| 로컬 한정 | 업스트림 알림의 결과 DM 을 접수 쪽이 보냄(흐름도 #7: 쓰기 서비스) | 위와 같은 원인 |
| 로컬 한정 | 정기 잡이 적용 큐를 거침(흐름도: Scheduler → `/reconcile` 직접) | 설계 의도("작업과 한 줄로 선다")와 같은 결과 |
| 결정 반영 | YouTube 알림 → `yt_notif` 작업(흐름도 #12 는 reconcile(영상)만) | D1~D3 — 흐름도가 결정보다 앞선 것 |
| 결정 반영 | 시작+2분 `search.list` · 원문 보존 `_local/raw` | D4 · D19 |
| 보완 필요 | 작업 이력 · 재등록 차단을 접수 쪽(`admin_api`)이 기록(흐름도: 쓰기 서비스) | 비동기로 바꿀 때 쓰기 쪽으로 옮길 것 |
| 보완 필요 | v3 undo 슬롯 · 편집 락을 쓰기 스레드가 계속 기록(ops `admin_state.json`) | 항목 단위 되돌리기(범위 밖) 구현 때 정리 |
| 미검증 | #24 생존 신호 · #17 healthchecks/Vercel 조회 · #26 배포 · #10 비전 OCR | 로컬 설정에 없음 / 배포 안 함 / OCR 대상 소식을 재생 안 함 |

## 5. 남은 것 · 시험 운영에서 볼 것

- 실제 폰 알림 · 실제 API 로 D1~D4 가 기대대로 움직이는지(특히 D4 `search.list` 가 시작 +2분에 잡히는지 — 검색 지연 가능성, `v4a_decisions.md` §2-2).
- 관리 페이지 삭제의 재등록 차단 선택이 명세(체크박스)와 달리 **확인창 두 번**. 항목 단위 되돌리기 미구현.
- 소식 리트윗 제외(D16)로 크로스오버 공식 계정 리트윗 소식이 사라지는 것이 괜찮은지 운영에서 확인.
- 배포 단계 과제(계획 §7): Cloud Tasks 어댑터 · 비동기 적재 + 작업 결과 조회 · OIDC · 이름 전환 · 원문 보존 위치(공개 저장소 문제) · 사장 코드 정리.
