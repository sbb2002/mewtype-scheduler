## 1. 「이력 보관 기간」을 물은 이유와 결론

물은 것은 새 정책이 필요한지였다. 현행은 이미 다음과 같다(코드 확인).
- **모니터 이벤트 로그**(`monitoring` 브랜치 `events-YYYY-MM-DD.jsonl`, 06:00 KST 경계)는 **삭제 없이 계속 쌓인다**. 매일 06:10 에 일 스냅샷 · 전 기간 요약이 만들어져 리포트 탭이 전 기간을 본다.
- 작업 탭 「최근 자동 처리」는 어드민이 **오늘 · 어제** 이벤트만 읽는 화면(`_cloud_events(days=2)`) — 보관이 아니라 표시 범위.
- LLM 판단 기록(`llm_actions.json`)은 **최근 300건** 유지(`_LLM_ACTIONS_MAX`).

→ **신곡 이벤트도 같은 이벤트 로그에 남기면 보관 · 스냅샷 · 리포트가 자동으로 같게 된다.** 새 보관 정책은 만들지 않는다(질문 철회).

## 3. 확인된 기존 구조 (재사용 지점)

- **탭**: `admin.html` 의 `.tab-btn` 7개 — 예고 · 소식·트윗(한 탭) · 원문 투입 · 작업 · 유실 원문 · 운영 · 리포트. 세부 탭 CSS 는 이미 있다 — `.ing-subtabs` / `.ing-subtab`(원문 투입의 자동 / 수동).
- **읽기 API**: `admin_web.py` `read_functions` 화이트리스트. 쓰기 = `admin_api` 함수 → `writers.py` kind → `/write`(직렬화) → `telegram_app` 커밋 함수.
- **작업 탭 반려**: `llm_actions.json`(ops 브랜치) 기록 1건 = 흐름 1줄. 기록은 `kind` · `summary` · `reason` · `input` · `undo`(되돌리기 정보). 반려 = `_llm_undo`(그때 바뀐 항목만 되돌림) → 이어서 LLM 재판단 / 사용자 판단(`_REVIEW_RUNNERS`, `_llm_review_options`).
- **리포트 타임라인**: `monitor_report.py` `LANES` 배열(트리거 · 운영자 명령 · 업스트림 감지 · 백엔드 상태 · preview · 소식 · 개인 트윗). 이벤트는 `_group` 으로 flow 별로 묶고 모르는 flow 는 무시 → 새 flow 를 로그에 남겨도 기존 리포트는 안 깨진다.
- **이벤트 기록**: `monitor_log.log_events`(실행당 커밋 최대 1개, 변화 없는 실행은 미기록). 필드 `ts · flow · result(ok|degraded|err) · who · detail + 흐름별 필드`.
- **중요한 제약**: tick 은 `mewtype-backend`(`concurrency=1`) 안에서 돈다. 그 안에서 `writeclient.call_write`(= 자기 자신 `/write` 호출)를 쓰면 **교착 위험**. 기존 `record_video_releases` 처럼 tick 안에서는 **gh 로 직접 쓴다**(ops 브랜치 파일은 data 브랜치 HEAD 와 경합하지 않음).

## 4. 설계

### 4.1 데이터 모델 — `songs.json` (data 브랜치)

```json
{
  "songs":   [{ "id", "title", "kind", "who", "date", "reading", "added_at?", "edited_at?" }],
  "rejected": [{ "id", "name_key", "ts", "by" }],   // 삭제 · 반려한 곡 — 자동 감지가 다시 등록하지 못하게 막는 목록
  "seen":    [{ "id", "reason", "ts" }]              // 이미 판단 기록을 남긴 「건너뜀」 — 같은 건너뜀을 tick 마다 다시 기록하지 않게 (최근 200건)
}
```
- 프론트 플레이어는 `songs` 배열만 읽으므로 **영향 없음**(추가 키 무시).
- **반려 · 삭제 시 반드시 `rejected` 에 넣는다.** 안 넣으면 곡이 RSS 최근 15건에 남아 있는 동안 **10분 뒤 다시 등록되는 루프**가 생긴다(기존 `/del` 의 「재등록 차단 12h」와 같은 문제, 여기는 영구).
- 곡명 중복 판정(`name_key`)에 `rejected` 의 `name_key` 도 포함.

### 4.2 감지 로직 개편 (`songs.py` · `handlers._detect_new_songs`)

1. `find_new_songs` 가 **건너뜀 사유도 반환**한다: `(새 곡 목록, [{entry, reason}])` — reason ∈ `name_dup`(곡명 중복, 어느 곡과 같은지 포함) · `feat` · `id_dup` · `rejected`.
2. `rejected` 를 존중한다(곡명 · 영상 ID 둘 다).
3. **판단 기록 남기기**(`llm_actions.json`, §4.3): 등록 1곡 = 1건, 건너뜀 중 `name_dup` 만 1건(`seen` 으로 한 번만). `feat` · `id_dup` · `rejected` 는 기록하지 않는다(노이즈).
4. **이벤트 로그**(`flow="song"`): 등록(ok) · 건너뜀(ok, 검토 대상) · RSS 실패(degraded, **시간당 1회만** — 무상태라 `now.minute < 10` 인 tick 에서만 기록해 10분마다 스팸이 되지 않게 · 이 규칙은 정확히는 가정, 구현 때 검증).
5. 한 tick 의 쓰기는 `songs.json` 커밋 1번 + ops 기록 1번 + 이벤트 1번 이하.
6. `songs.json` 이 없으면(시드 전) 기존대로 건너뜀. 어드민 상태 카드에 「시드 필요」로 표시.

### 4.3 작업 탭 — 판단 기록과 반려 (R2)

`llm_actions.json` 을 재사용한다(새 저장소를 만들지 않는다).
- 새 kind **`song_register`**(등록): `reason` = 규칙 추적(예: 「곡명 `夢我夢中` 이 목록에 없음 · 제목 끝 (Cover) 없음 → original · feat. 아님」), `input` = RSS 항목 스냅샷(video_id · 제목 · 공개 시각 · 설명 일부), `undo` = `{type:"remove_song", id}`.
  - **반려 동작**: 목록에서 그 곡을 지우고 `rejected` 에 추가(재등록 차단). 그 사이 운영자가 곡을 **수정했다면**(= `edited_at` 이 기록 시각 이후) 덮어 지우지 않고 「그 뒤 바뀌었음」으로 건너뜀 — 기존 `restore_fields` 와 같은 원칙(그때 바뀐 항목만).
  - 이어서 **사용자 판단**: 다른 값(kind · who · 제목)으로 다시 등록.
- 새 kind **`song_skip`**(곡명 중복으로 등록 안 함): 검토용(롤백할 변경 없음). 반려 → **사용자 판단 = 강제 등록**(kind · who 선택). 곡명이 같지만 다른 곡인 경우를 구제하는 장치.
- **LLM 재판단**은 신곡 판단이 LLM 이 아니라 규칙이라 **해당 없음** — 버튼을 숨긴다.
- 작업 탭 필터 이름 「LLM 판단」은 부정확해진다 → **새 용어 필요**(후보 「자동 판단」). `docs/TERMINOLOGY.md` 규칙상 **운영자와 정한 뒤 등재**(§8 열린 질문 1).
- `_FLOW_KO` 에 `"song": "신곡"` 추가 → 「최근 자동 처리」(이벤트 로그 오늘 · 어제)에 자동 노출. 흐름 줄 표시 · `_REVIEW_RUNNERS` / `_llm_review_options` 에 두 kind 추가.

### 4.4 어드민 API · 쓰기 (R1, R5)

읽기(`read_functions` 추가): `list_songs` · `songs_status`.
- `songs_status` = ① `songs.json` 유무 · 곡 수 · 독음 미입력 수 ② **지금 RSS 조회**(어드민 서비스에서 직접, 쿼터 0) 성공 여부 · 최신 항목 공개 시각 ③ `find_new_songs` 를 돌린 **등록 예정 · 건너뜀 미리보기**(쓰기 없음 = dry-run) ④ 최근 `song` 이벤트 N건. → 시드 전 확인(R5)과 평소 상태 확인을 겸한다. RSS 실패는 이 조회로 보이므로 tick 쪽 실패 이벤트를 늘릴 필요가 없다.
쓰기(`writers.py` 새 kind `song_edit` → `telegram_app._song_edit_commit`, `/write` 직렬화): `edit_song`(title · reading · kind · who · date) · `delete_song`(삭제 + `rejected` 추가).
- 곡 **직접 추가**(수동 등록)는 요구에 없어 계획에서 제외하고 §8 에 질문으로 둔다(강제 등록은 §4.3 사용자 판단으로 가능).
- 독음 입력칸 옆에 **자동 변환된 한글 독음 미리보기**(`kanaToHangul` 과 같은 규칙을 서버에도 필요 — 파이썬 포팅 또는 프론트에서 계산; 구현 때 결정).
- 어드민 편집과 tick 의 자동 등록이 **같은 파일을 동시에 쓸 수 있다** — 둘 다 sha 재시도(409 재읽기 → 재계산)를 쓰고, tick 쪽은 충돌 시 다음 tick 이 같은 RSS 로 재계산(기존 설계).

### 4.5 화면

**탭 재편 (R4)** — 탭 개수는 7개로 불변(모바일 하단 탭 바 폭 유지):
`현황` · `음반` · `원문 투입` · `작업` · `유실 원문` · `운영` · `리포트`
- **현황** = 세부 탭 `예고` | `소식` | `트윗`(기존 `.ing-subtab` 스타일 재사용). `소식` 세부 탭에 행사 배너 포함(지금 `소식 · 트윗` 탭 안의 칩으로 소식 / 트윗 / 배너를 바꾸던 것을 세부 탭 클릭으로 대체).
- **회귀 방지**: 기존 `#preview-tab` / `#content-tab` 의 **element id · 렌더 함수는 그대로 두고**, 그 위에 `#status-tab` 래퍼와 세부 탭 전환만 얹는다. 예고 세부 탭 맨 위의 「참여 멤버 확인 대기」 카드는 그대로.
- **음반** = ① 상단 카드: 신곡 감지 상태(시드 여부 · 마지막 확인 · RSS 상태 · 「지금 확인」 → 등록 예정 미리보기) ② 곡 목록(검색 · 종류 필터 · 「독음 없음」 필터 · 정렬) ③ 상세: 수정 · 삭제, 자동 등록분 표시(`added_at`).

**리포트 타임플롯라인 (R3)**
- `LANES` 에 `{key:"song", label:"신곡 감지", icon:"🎵", type:"point", rows:["song"]}` 추가. 점 색 = 결과(등록 ok · 건너뜀 · 실패 degraded/err).
- `monitor_report`: `_group` 에 `"song"` 추가, `_song_json`(시각 · 곡명 · 결과 · 상세), `CURRENT_DAY.song`, `buildRows`(표 · 상세 팝업)에 행 추가, 레이아웃(`rowY`)은 `LANES` 가 자동 계산.
- 스냅샷(`monitor_snapshot`)은 `build_day_from_text` 를 재사용하므로 새 키가 자동 포함. **옛 스냅샷에는 `song` 키가 없으므로** 프론트가 없을 때를 허용해야 한다(`Array.isArray` 가드 — 업스트림 행과 같은 방식).

## 5. 구현 단계 (제안 순서)

| 단계 | 내용 | 독립성 |
|---|---|---|
| P0 | `songs.json` 모델 확장(`rejected` · `seen`) + `find_new_songs` 사유 반환 + 반려 존중 + selfcheck | 선행 |
| P1 | 감지 쪽 기록: 판단 기록(`song_register` · `song_skip`, tick 안 직접 쓰기) + `flow="song"` 이벤트 + `_FLOW_KO` | P0 후 |
| P2 | 어드민 API: `list_songs` · `songs_status`(dry-run · RSS 조회) · `edit_song` · `delete_song` + writer | P0 후 |
| P3 | 음반 탭 UI (상태 카드 · 목록 · 수정 · 삭제) | P2 후 |
| P4 | 작업 탭: 두 kind 표시 · 반려(`remove_song` + `rejected`) · 사용자 판단(강제 등록 · 다시 등록) | P1 후 |
| P5 | 리포트: 신곡 행 + `_song_json` + 옛 스냅샷 호환 | P1 후 |
| P6 | 현황 탭 재편(세부 탭) | **독립** — 다른 단계와 병행 가능, 회귀 위험이 있어 따로 검증 |
| P7 | 문서(SPEC · VERSION · CLAUDE.md · TERMINOLOGY) · 시드 절차 · 로컬 통합 시험 | 마지막 |

권장: **P0 → P1 → P2 → P4 → P5 → P3 → P6 → P7**(감지 · 기록 · 점검 기능을 먼저 닫고 화면 재편은 뒤). 시드는 **P2(미리보기) 이후, P4(반려) 까지 끝난 뒤** 하는 것을 권한다 — 시드 직후 첫 tick 이 곡 10개를 즉시 등록하기 때문에(즉시 등록 결정) 반려 수단이 먼저 있어야 한다.

## 6. 테스트 계획

- **단위**: `songs.py`(사유 · 반려 존중 · 곡명 키), `handlers._detect_new_songs`(가짜 gh — 기록 · 이벤트 · `rejected` 재등록 차단 · 충돌), `admin_api` 새 함수(로컬 `V4A_RUNTIME=local` 임시 저장소, 기존 `admin_api` self-test 방식), `monitor_report`(`song` 이벤트 → 행 · 옛 스냅샷 호환).
- **통합**: 로컬 러너(`python -m src.backend.local_runner`) + 가짜 RSS 로 감지 → 작업 탭 반려 → 재감지 시 재등록 안 됨까지 한 흐름.
- **화면**: 헤드리스 Chrome 으로 PC · 모바일(iframe 390px) 캡처 — 탭 재편, 음반 탭, 리포트 타임라인. (이번 세션에서 쓴 방식)
- **실제 RSS**: 이 PC 에서는 RSS 가 404 라 조회가 안 된다 — 어드민 `songs_status` 는 **운영 Cloud Run 에서** 확인해야 한다(미검증으로 남겨 둠).

## 7. 위험 · 주의

1. **tick 안에서 `/write` 자기 호출 금지**(교착). 기록은 gh 직접 쓰기.
2. **반려 · 삭제 후 재등록 루프** — `rejected` 필수(§4.1).
3. **브랜치 HEAD 경합** — 어드민 편집은 `/write` 직렬화 경유, tick 은 한 번에 `songs.json` 커밋 1번. 시드 · 대량 수정은 트윗이 몰리는 시간대를 피한다.
4. **탭 재편 회귀** — 기존 id · 렌더 함수 유지, 래퍼만 추가(P6 를 따로 검증).
